## 📌 背景与问题

**现状**（V2.2 版本闭门后，代码与库内核实）：

- **政策数据三轨并存，gov.cn 抓两遍**：
  1. **轨 A · 六源业务域 POLICY**：`PolicySourceAdapter`（T07）按需拉取 gov.cn/zhengce，按 `INDUSTRY_KEYWORDS` 热词字典（**仅 V2 种子 3 行业：白酒/银行/互联网**）对 `subject.industry` 逐条过滤——**新池 5221 标的 industry 多为 NULL 或非 3 行业，永不命中 → MISSING**。这是详情页政策分区「抓取不到数据」的根因（源抓取本身正常：gov.cn 列表可达、policy_item 在库 35 条）。
  2. **轨 B · policy_item 独立表**：`PolicyFetchJob`（每小时）抓同一 gov.cn/zhengce 落 policy_item（35 条），`PolicyIndustryClassifier`（同源 3 行业字典）标 related_industries——**35 条中 29 条空标签（82.9%）**，政策时事页行业筛选基本筛空；`PolicyTendencyJob` 30min 轮询对逐条做 LLM 倾向判断（ai_tendency）。下游消费：政策时事页 `#/policies`、信息流政策内容（`FeedService.policyContents`，政策主题订阅匹配面）、政策阅读埋点（POLICY/content_ref=policyId）。
  3. **轨 C · 资讯源体系**：33 现役源 7×24 轮询进 news_item（4051 条）→ L0~L3 管道（去重/35 枚举分类/事件提取/热度）。官方政策源 4（ndrc_policy/miit_policy/mof_policy/csrc_news）+ 宏观 2（stats_release/em_macro_indicators）已在体系内，**gov.cn 主站政策库不在其中**——同一站点被轨 A（按需）与轨 B（每小时）抓两遍，且只有轨 C 的产物参与分类/事件/热度/推荐全链路。
- **关联能力已就位但没接**：M21 路 C 行业成员回哺（datacenter 回填 2765 只 + `IndustryDirectory.swPrimaryOf` 映射）与 M22 增量受影响集同源的 `IndustryAssociator` 关联集已覆盖更广标的；L1 管道对政策源条目的行业分类实际散布 10+ 申万行业（监管·政策容器 78 条之外）——**详情页政策分区仍用 3 行业热词字典，两代关联能力断层**。
- **两套源页面**：`#/datasource-config`「业务数据源」（六源按需拉取型）与 `#/info-sources`「资讯源」（33 源轮询采集型）两页分立——V2.1 M19 做过轻整合（改名 + 互链 + 副标，拍板三裁「不合并页面」并预留 #12 双 Tab 合并的变更控制复议条款）；用户本期明确再提「合并一起需要一个入口」——复议触发。

### ⚖️ 拍板一 · 迁移总策略：单批直接切换（读路径先行 → 写路径退役），不做跨版本双写

**裁决**：放弃「渐进双写 → 切换 → 退役」的跨版本路径，**一个批次内按三步有序完成**：①新数据面先行（T200 gov_policy 源接入，旧轨照常运行作对照）；②读路径逐面切换（T201/T202/T203 前半：政策时事页 / 详情分区 / 信息流与订阅）；③写路径退役收口（T203 后半：双 Job 停跑 + 六源 POLICY 摘除 + policy_item 冻结）。每步附对账验收（T207 总账）。

**理由**：①单人自用平台 + policy_item 仅 35 条 + 数据可重抓（gov.cn 公开列表页，新源接入首轮抓取即回灌）——迁移失败恢复成本 ≈ 一轮抓取，双写的稳定性收益撑不起其成本；②双写跨版本意味着「gov.cn 抓两遍」的问题再存活一个完整版本，与用户「合并、去重复」的诉求方向相反；③批内三步走已保留「先建新面再拆旧面」的安全序，旧轨在新读路径验收通过前不下线。**批内 T200 接入至 T203 退役之间 gov.cn 存在短暂双抓窗口（批内数日级），收口断言「退役后 policy_item 零新增 + 六源 POLICY 零调用」兜底。**

**policy_item 处置**：停写后保留只读（35 行历史不迁移不清理——沿「历史不回填」先例），代码读路径全下线后表纳入 M10 留痕生命周期治理处置，退役决策留档。

### ⚖️ 拍板二 · 政策类条目口径（政策时事页与详情分区共用）+ gov_policy 源定位

**gov_policy 源定位**：gov.cn/zhengce 政策库作为**预置资讯源**（category=政策，adapter 形态与端点复用既有 `GovPolicyClient` 能力——实现归架构），7×24 轮询进 news_item，与既有 33 源同引擎同治理（启停/频控/连通性/大盘/软删语义对齐预置源规则）；source_url 去重语义迁移到资讯源跨源指纹体系（实现归架构）。

**「政策类条目」产品口径**（版本化 policy-scope-v1，政策时事页默认视图与详情分区同源）：

```
政策类条目 = ① 源类别 = 政策 的源（ndrc_policy / miit_policy / mof_policy / csrc_news / gov_policy）的 PASS 条目
           ∪ ② 任意源中 L1 主分类 = 监管·政策 的 PASS 条目
```

- 默认仅 PASS（与管道消费口径一致，noise/near_dup 不入政策视图——资讯库仍可查全量）；宏观源（stats_release/em_macro_indicators）统计发布不属政策，**不入默认口径**，政策时事页源筛选可显式纳入。
- 该口径是 news_item 之上的**查询口径非物化新表**——与资讯库 L1 筛选天然可对账（政策时事页结果 ⊆ 资讯库同条件筛选结果，验收断言）。

### ⚖️ 拍板三 · 详情页政策分区修复：行业关联集替代热词字典，无命中兜底宏观段

**过滤口径**（替换 `INDUSTRY_KEYWORDS` 3 行业热词字典）：

```
分区条目 = 政策类条目（policy-scope-v1）中：
  ① matched_subjects 含该标的（直接回联） —— 命中即取
  ∪ ② 条目 L1 main_category / sub_industry ∈ 该标的行业关联集 —— 关联集与 F2/M22 增量受影响集同源
                                              （IndustryAssociator：事件回联 + 资讯归类回联 + 行业成员回哺三路），
                                              不引入第二套关联逻辑
```

**兜底语义**（MISSING 消除的产品设计）：无关联命中时分区**不空白**——呈现「近期宏观政策」段（L1=监管·政策 近期条目，条数沿 M12 政策分区容量）+ 明示文案「暂无与该标的行业直接相关的政策，以下为近期宏观政策」+「全部政策 →」链接跳政策时事页。政策本就是宏观流，硬套行业命中是旧字典的设计错位；兜底段让分区恒有内容且**不冒充关联**（口径明示）。

**呈现分级**：直接回联命中（①）行上标「标的关联」徽章，行业投影命中（②）标「行业关联」徽章，兜底段独立小节——三种来源可区分，可解释。

### ⚖️ 拍板四 · 政策时事页：保留页面切换数据面，ai_tendency 退役由 L2 承接

**裁决**：`#/policies` 保留（数据组第 3 项不动），数据源 policy_item → news_item 政策类条目（policy-scope-v1）。**不裁撤页面**（条目清单 #9 Won't）：政策时事是「按主题纵深浏览」场景（行业筛选/关联自选标的聚合/订阅联动入口），资讯库是「全量抽检」场景——两者是同一数据面的两种视图，裁撤政策页会失去纵深场景；用户诉求的「合并」本质是数据统一（已由拍板一/二达成），页面互链补齐心智（政策页 ↔ 资讯库）。

**升级三件事**：①行业筛选切 L1 口径（申万 31 行业 + 监管·政策容器，与资讯库 L1 筛选同源）+ 新增源筛选（政策 5 源 + 宏观 2 源可选）——现状 3 行业字典且 82.9% 空标签，切换后筛选真正出数（库内政策源条目 L1 已散布 10+ 行业）；②关联自选标的呈现（matched_subjects 回联，行级「标的关联」呈现 + 可跳详情）；③政策详情视图随数据面切换（news_item 条目 + 关联标的 + 关联 L2 政策发布事件），阅读埋点 POLICY 语义延续（content_ref 切 newsId，历史留痕不迁移沿先例留档）。

**ai_tendency 退役**：独立 LLM 倾向判断机制（PolicyTendencyJob 30min 轮询）随 policy_item 退役；政策条目的倾向判断由 **L2 政策发布事件**（方向 + 影响链宏观三分：货币/财政/产业，M17 模板体系）承接——条目有关联事件时详情视图呈现方向与传导链入口。**成本净减项**（一条 LLM 轮询链路消失），倾向能力不倒退（L2 判断更结构化且已通过 M17 验收）。

## ⚖️ 优先级排序

**MoSCoW 粗排**：Must = gov_policy 源接入 + 政策时事页切换 + 详情分区修复 + 双轨退役 + 源页面合并 + 收口对账（缺任一则「政策合并」或「一个入口」诉求不成立）；Should = 资讯库筛选增强 + BUG-M21-04 断言（可延后一版不伤 Must 链）；Won't 见范围节。

**RICE 精排**（组粒度）：

> Reach = 两周迭代内触达（沿 V2.1 口径单人量级相对值：详情页为最高频浏览面）；Impact：2=high，1=medium，0.5=low；Confidence：80% = 复用既有引擎与关联基建 + 含切换验证环节，90% = 呈现层复用已验证组件，100% = 汇总性交付直接可证；Effort = 人天（含验收分摊）。

| 模块 | Reach | Impact | Confidence | Effort(人天) | RICE 分数 |
| --- | --- | --- | --- | --- | --- |
| 详情政策分区修复（T202+T206） | 60 | 2 | 80% | 3 | (60×2×0.8)/3 = 32 |
| 政策时事页切换（T201） | 30 | 2 | 80% | 2 | (30×2×0.8)/2 = 24 |

| gov_policy 源接入（T200） | 25 | 2 | 80% | 2 | (25×2×0.8)/2 = 20 |
| 退役收口（T203） | 15 | 2 | 80% | 2 | (15×2×0.8)/2 = 12 |
| 资讯库筛选增强（T205 内） | 20 | 1 | 90% | 1.5 | (20×1×0.9)/1.5 = 12 |
| 收口总单（T207） | 15 | 2 | 100% | 1.5 | (15×2×1.0)/1.5 = 20 |

排序结论：**依赖约束优先于 RICE**（沿 V2.0~V2.2 既定结论）——T200 是全部政策故事的数据前提必须先行；T203 退役必须等 T201/T202 读路径验收后收口（批内安全序，拍板一）；收口 RICE 高但是版本义务随批不裁。执行序：T200 先行 → T201/T202/T204 三路并行 → T203 收写路径 → T205/T206 补呈现 → T207 收口。

## ⚙️ 非功能需求

- **兼容红线**：旧路由 `#/datasource-config`/`#/info-sources` 带参重定向零断链（大盘 source 定位语义保留）；news-items 端点新参数追加式零破坏（沿 V2.1）；订阅配置零迁移、四类型匹配语义不变；软删源排除与 L0 默认 PASS 口径沿用。
- **成本**：ai_tendency LLM 轮询退役为**净减项**；gov_policy 轮询沿既有源频控与 cost-v2 预算体系（gov.cn 政策量级小时级数条，管道 L1 批量归类边际成本可忽略）；本期无新增提示词类。
- **数据质量**：policy-scope-v1 口径可独立对账（政策页 ⊆ 资讯库同条件结果）；分区三来源分级可复算（关联集同源断言）；「gov.cn 单一抓取面」与「policy_item 零新增」收口断言常驻；contentId 换代版本化留档。
- **性能**：政策类口径为 news_item 之上查询（沿既有索引 idx_na_main 等，SQL 形态归架构）；详情分区从「按需外呼源站 + 缓存」变「库内查询」，首屏时延只降不升（分区时延沿 M9/M12 三态基线验收）。
- **留痕与生命周期**：policy_item 停写冻结后纳入 M10 治理；Job 停跑留痕；六源 POLICY 配置域退役留档。
- **UI 一致性**：`#/sources` 与政策页改版基于 ui-tokens-v2 既有组件（Tab/搜索/徽章/分页复用）；零新增导航分组；trace-v1 走查表同步更新。
