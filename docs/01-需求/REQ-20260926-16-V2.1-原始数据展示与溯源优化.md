### ⚖️ 拍板一 · 资讯库页定位、命名、字段与语义（+ 后端 API 缺口清单）

**定位与命名**：**「资讯库」，路由 `#/news-library`，数据组第 4 项（政策时事之后），全站第 19 页**。裁决理由：

1. **命名三选一**（「资讯库」/「抓取数据」/「原始数据」）：拍板「资讯库」——底层即 M13 命名的「资讯统一库」（news_item），资产视角命名与数据组浏览语义（自选清单/标的详情/政策时事）一致；「抓取数据」是过程视角（运维味，且库里的条目已经过去重/AI 判定，不只是「抓来的」），「原始数据」是技术视角。
2. **放数据组而非运维组**：与「信息流」（分析组，订阅过滤后的个人化消费流）形成**库 → 流**两级心智——资讯库是原始全量底座，信息流是个人化消费视图；运维组已是 8 项最重组，且资讯库的主消费场景是「查数据/抽检」而非「管管道」（管道运维态已有大盘/资讯源两页承载）。
3. 信息流页顶已有「数据源头 → 订阅管理」引导（P1-3），本期补资讯库互链（Should，随故事 1 交付）：「查看原始库 → 资讯库」。

### ⚖️ 拍板二 · 全站溯源标准 trace-v1（三级达标 + 逐页缺口清单）

**口径版本化 trace-v1**（沿 heat-v1 / coverage-v2 / adopt-v1 / ns-v1 版本化先例）：

> **凡页面呈现「资讯衍生信息」**——由 news_item 原始条目经 AI 管道或聚合产生的展示内容（事件卡 / 推荐卡 / 热度榜单与下钻条目 / 日报周报事件引用 / 任何「据资讯 X 得出 Y」的 Y）——必须满足以下三级之一：

| 级 | 形态 | 适用 |
| --- | --- | --- |
| **A 原文外链** | 条目具备可点击原文 url（新窗口直达源站） | 一切新展示面的缺省级；实时查询渲染的页面 |
| **B 引用块** | 原文引用 quote + 来源名 + 发布时间 | url 缺失、或历史物化数据（报告 content）的兜底达标 |
| **C 溯源链** | 条目行级可点，到达满足 A/B 的承载页 | 摘要块 / 榜单行 / 聚合计数场景（一键到详情） |

判定细则：纯统计聚合（计数/分数/环比）不属资讯衍生信息，不适用本标准（其承载的行业名条目可点 = C 级增强）；新报告 content 自本期起含 newsUrl（升 A），历史报告保留 quote（B 兜底，#15 不回填）；豁免面：AI 简报（生成式叙事 + 免责标注，#14 Won't）。

**逐页缺口清单与补法**（本期 4 处，含端点/落点）：

| # | 页面/区块 | 缺口 | 补什么 | 落点 |
| --- | --- | --- | --- | --- |
| 1 | 热度榜下钻 news 行 | 无外链（ItemView 无 url） | 标题变外链 | `GET /industry-heat/{industry}/items` ItemView 补 url（join news_item，字段在表仅未 SELECT）；前端标题 `<a>` |
| 2 | 热度榜下钻 events 行 | 无外链/引用/来源 | newsUrl + quote + sourceName 补入 ItemView | 同上（events 行 join news_item.url + event_item.quote） |
| 3 | 日报/周报事件引用（精选/回顾/政策动向） | 有 quote 无来源名无外链 | content JSON 增量字段 sourceName + newsUrl（新报告起）；前端来源灰字 + 「查看原文」 | DailyReportService / WeeklyReportService content 组装 + ReportEvent 查询补 join |
| 4 | 日报行业动态 / 周报热度总览 / 概览工作台四块 | 行级不可点 | 行级跳转：行业名 → `#/industry-heat?industry=`（下钻展开）；工作台行 → 对应承载页 | 纯前端 |

### ⚖️ 拍板三 · 源页面整合：轻整合（命名统一 + 互链 + 入口归拢），不合并页面

**裁决**：用户疑问「资讯源与数据源是否可以整合一起」→ **心智整合，不物理合并**。三方案对比：

| 方案 | 形态 | 成本 | 裁决 |
| --- | --- | --- | --- |
| A 合并一页 `#/sources` 双 Tab | 双 Tab「业务数据源/资讯源」 | ≥3 人天：新路由 + 旧 hash 重定向兼容 + 两套卡片范式统一重构（降级链编辑 vs 频控/立即抓取硬塞一页） | ❌ Won't（#12） |
| B 轻整合（拍板） | 改名 + 互链 + 大盘入口，路由不变 | ≈1 人天 | ✅ **采纳** |
| C 不动 | 维持现状 | 0 | ❌ 用户困惑已实际发生，不采纳 |

**理由**：①合并解决的只是「发现性」，而发现性用命名 + 互链即可解决；②两页使用场景几乎不重叠——业务六源配好后低频不动（降级链/超时调优），资讯源是日常运维高频页（启停/抓取/连通性/停更复核），合并后一页承载两套交互密度反而下降；③M18 刚建立 UI 2.0 走查基线（18 页基准 20/20），合并重构直接破坏刚验收的基线；④路由不变 = **零兼容成本**（旧 hash 收藏/大盘跳转 `navigate('/info-sources?source=')` 全部继续有效，testid 零变化）。

**轻整合三件事**：

1. **导航改名**（navConfig label，路由不动）：「数据源配置」→ **「业务数据源」**、「资讯源管理」→ **「资讯源」**——同组相邻（现已相邻，顺序不变），前缀区分域、长度一致视觉整齐；
2. **页内副标 + 互链引导条**：两页标题下副标注明运行形态——业务数据源页「按需拉取型 · 行情 / 财务 / 估值 / 公告 / 新闻 / 政策六域」+ 引导「轮询抓取的资讯源管理 → 资讯源」；资讯源页「轮询采集型 · 30 源采集管道」+ 引导「按需拉取的业务数据源配置 → 业务数据源」；
3. **大盘入口归拢**（Could，#11）：抓取大盘页头补「业务数据源」入口（资讯源入口已通过源维度表行点击存在，保持）。

> 若后续使用中仍觉割裂，双 Tab 合并按 #12 走 V2.1 backlog 变更控制复议——本期先以最低成本验证「命名 + 互链是否已消除困惑」。

| 依赖/风险 | 说明 | 对策 |
