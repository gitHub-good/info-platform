## 📌 背景与问题

**现状**（V2.3 M23 收口后，代码核实）：

- **源管理「一个入口」只做到一半**：V2.3 T204 把两页合并为 `#/sources` 双 Tab——入口归一了，但「新增源」仍只在资讯源 Tab 内；两套源仍靠 Tab 切换分置两个视口，搜索过滤一次只作用于当前 Tab（跨 Tab 命中仅轻提示）。用户本轮诉求「数据源只需要一个新增配置，并且基于分组来区分」——指向**分组单列表**形态：一屏之内分组分段呈现、新增入口页头唯一。
- **政策时事与资讯库双视图重复**：V2.3 已把政策数据面统一进 news_item（policy-scope-v1 = 政策源 PASS ∪ 全源 L1=监管·政策），但保留了 `#/policies` 独立页——与 `#/news-library` L1=监管·政策 筛选高度重叠（收口实测 65/68 ≈ 96% 同集）。用户原话「资讯库里有政策时事的数据，无需重复展示」——**数据统一后页面冗余显性化，用户裁掉重复视图**。
- **大盘数字只可看不可查**：全局卡「今日总入库」（含去重拦截副标）、源维度表「今日新增 / 累计条数」均为静态数字——看到异常数字（今日某源暴涨/暴雪）后，要看具体条目需自行跳资讯库手工组合同等筛选（源 + 时间），链路断裂。
- **失败列表不辨恢复且平铺 20 条**：failures() 合并「旁路失败事件（最近 20 条，无论源是否已恢复）+ 现态 lastError」，时间倒序平铺——已恢复源的历史失败长期占位（用户痛点「近期失败展示如果近期有恢复则不展示」）；无折叠，20 条铺满首屏。

**差距**（对照四项诉求）：

| # | 诉求 | 现状 | 差距 |
| --- | --- | --- | --- |
| 1 | 源配置整合、单一新增入口、分组区分 | 双 Tab 两视口；新增入口在资讯源 Tab 内 | 去 Tab 单列表分段分组；新增入口页头唯一；搜索跨全部分段 |
| 2 | 政策时事并入资讯库、不重复展示 | `#/policies` 独立页与资讯库 L1 筛选 96% 同集 | 裁撤政策页 + 旧 hash 重定向资讯库预填 L1=监管·政策 |
| 3 | 大盘今日新增/累计条数点击弹框列表 | 三处数字静态不可点 | 三处可点 + 弹框分页列表 + 数字与列表可对账 |
| 4 | 失败已恢复不展示 + 最多 3 条可展开 | 事件+现态合并不滤恢复，平铺 20 条 | 按源当前 runState 过滤 + 收起 3 条折叠展开 |

**不做的代价**：源管理入口心智仍是「Tab 二选一」半成品；政策数据一双视图长期双份维护（筛选/徽章/空态两套）；大盘异常数字查证链路断裂（运维效率）；失败列表被已恢复历史占位、真问题被淹没。四件均为 V2.3 合并主题的自然延伸收尾——**V2.4 把「合并」从数据面推进到视图面**。

### ⚖️ 拍板一 · 源统一形态：去 Tab 单列表分段分组，「容器换形态、组件不动」

**裁决**：`#/sources` 从双 Tab 改为**单列表分段分组**——资讯源沿服务端 category 既有分组（快讯/媒体/政策/宏观/国际/自建，零新分组逻辑）在前，**「业务数据源」一段收尾**（低频配置域置底）；两面板组件（InfoSourcesPanel / BizSourcesPanel 卡片及交互）**原样复用不动**，仅外层容器从 Tab 切换改为纵向分段渲染。

**新增源入口唯一**：「＋新增源」上移页头（全局唯一按钮），弹出既有资讯源 SourceFormDialog（RSS/JSON 两型 + category 分组选择）。**业务源不可自增**——现状核实：BizSourcesPanel 无任何新增入口，五源为代码注册 adapter（开关/参数/降级链均为配置化编辑），新增业务源 = 开发行为（写代码注册 adapter），不提供也不需要 UI 自增；用户「数据源只需要一个新增配置」由「全站新增入口唯一 + 业务源代码注册」共同达成，分组（category/业务域）承担两类源的区分。

**搜索与概览**：统一搜索跨全部分段过滤（Tab 消亡，跨 Tab 命中提示机制自然退役）；概览条保留（资讯源启用 N/34 · 业务源健康 M/5 · 今日入库，口径不变）。业务段页头「六域——7 源开关」stale 文案随批对齐五域五源。

**路由兼容红线**：`?tab=info|biz` 参数退役——归一层映射 `tab=biz → 段定位参数（业务数据源段滚动定位）`，`tab=info` 静默归一；`?source=` 定位语义保留（大盘失败跳转零断链）；旧 `#/datasource-config` → `#/sources` 业务段定位、`#/info-sources` → `#/sources`（query 透传沿 V2.3 归一层）。

**变更控制注记**：本拍板是对 V2.3 拍板五「双 Tab 形态采纳、分组单列表 Won't（#11）」的正式复议修正——用户一个迭代内再提「单一新增配置 + 分组区分」，触发条件成立；修正仅限**分组载体**（Tab → 分段），V2.3 对「卡片范式硬统一重构」的否定（原 #11 的真实理由）继续成立且本次明确不做（清单 #11）。复议结论版本化留档于本 REQ，同步架构/UI/测试。

### ⚖️ 拍板二 · 政策时事并入资讯库：裁撤页面、重定向预填，零数据迁移零页面重写

**裁决**：**资讯库为主承载，`#/policies` 页裁撤**——导航「政策时事」项移除（全站 19 → 18 页）；`#/policies`（含 `#/policies/{id}` 详情子路由）旧 hash 重定向 `#/news-library?l1=监管·政策`；资讯库新增 **URL 预填筛选能力**（挂载时消费一次 l1/sourceId 等参数为初始筛选态，用户随后自由改筛）。站内 2 处引用改指：Overview 政策时事入口、PolicySection「全部政策 →」出口（V2.3 拍板三兜底段出口）→ 均改跳资讯库预填。

**近似口径留档**：政策页口径 policy-scope-v1 = 政策源 PASS ∪ 全源 L1=监管·政策；重定向预设仅 L1=监管·政策（65/68 ≈ 96% 同集，V2.3 收口实测）——差额 3 条为政策源条目 L1 散布申万行业，可经资讯库源下拉（政策类源）补看。**不在资讯库复刻 policy-scope-v1 组合筛选**（清单 #9 Won't）。

**场景不孤儿**（裁撤无能力损失核验）：政策纵深浏览 → 资讯库 L1 筛选 + 源筛选；关联自选标的 → 标的详情政策分区（V2.3 拍板三，读口不动，**不受影响**）；L2 政策发布事件下钻 → 事件流页 `#/events` + AI 简报；信息流 POLICY 类型条目与政策主题订阅 → FeedService 独立消费面（PolicyScopeQueryService），**不受影响**。政策详情视图（relatedEvents 方向徽章/回联标的 chips）随页退役——事件本体经事件流页仍可见。

**端点与埋点收口**：/policies、/policies/{id} 两端点前端唯一消费方消失 → 退役下线（Should，可延后一版）；PolicyScopeQueryService **保留**（信息流/详情分区消费，断言在册）。POLICY 类型阅读埋点新增归零（页面消失），历史留痕不迁移不报错（沿 M23 contentId 换代先例）。

**变更控制注记**：本拍板是对 V2.3 拍板四「保留政策时事页」与条目清单 #9 Won't 的正式复议推翻——触发条件（用户再提合并诉求）一个迭代内成立；V2.3 保留理由（纵深浏览场景价值）经用户裁决让位于去重复诉求，场景承接面已核验（上文「场景不孤儿」）。版本化留档，同步相关方。

### ⚖️ 拍板三 · 大盘可点数字：三处可点 + 弹框对账，其余明确不可点

**可点清单**（全部点击 → 弹框分页条目列表，复用 news-items 页码模式 + 预填筛选）：

| # | 数字 | 预填筛选 | 弹框标题口径 |
| --- | --- | --- | --- |
| 1 | 全局卡「今日总入库」 | sourceId 无 + 入库日=今日 + l0=ALL | 今日入库 · 全部源 |
| 2 | 源维度行「今日新增」 | sourceId=该源 + 入库日=今日 + l0=ALL | 今日入库 · {源名} |
| 3 | 源维度行「累计条数」 | sourceId=该源 + l0=ALL | 累计条目 · {源名} |

**不可点**（清单 #10 Won't，防蔓延）：去重拦截（=拦截未入库，无可列实体）；活跃源数/失败源数/感知延迟（非条目集合）。

**对账口径**（验收锚，弹框 total 必须与被点数字相等）：大盘今日新增 = source_daily_stats 落库行数（入库日口径、上海时区、含全部 L0 态）；累计 = news_item COUNT(*)（含全部 L0 态）。故弹框必须 **l0=ALL**（端点缺省 PASS 会对不上账）且今日弹框按**入库时间**过滤——现端点仅有 publishedFrom/To（发布时间窗），与入库日口径不同源（RSS 条目常见跨日发布），直接复用必错账 → **news-items 追加 fetchedFrom/To 入库时间窗参数**（页码模式专属，追加式零破坏，实现归架构）。对账断言限定默认源表视图（未归档源）；大盘含归档源计数与端点排除软删源的口径差若现，收口留观察项。

**弹框形态**：Dialog + 既有 Pagination 组件复用；预填筛选只读呈现于标题（口径明示）；支持翻页/条数切换/关闭（Esc 与遮罩）；弹框内不提供二次改筛（保持「数字 → 列表」直查心智，去资讯库做深查——弹框尾「去资讯库深查 →」入口带参跳转）。

### ⚖️ 拍板四 · 失败列表「恢复」定义与折叠形态

**恢复定义**（产品口径，数据面现状核实后定）：失败条目所属源**当前 runState ∈ {fail, backoff}** 才展示；源满足任一即整组不展示——①恢复（runState=ok：最近一轮成功，lastSuccessAt ≥ lastAttemptAt）；②停用/归档（不再运行 = 已处置）。**数据面现状**：failures() 为「旁路失败事件 findRecent(20)〔不滤源当前状态〕+ 现态 lastError」合并——已恢复源的历史失败事件长期占位，即用户痛点；后端需按源当前 runState 过滤（event 行 join 源运行态；实现归架构，产品验收只锁「已恢复/已停用源零展示」）。失败事件留痕**不删**（表数据不动，仅大盘展示过滤——追溯仍走 Job 日志/失败事件留痕面）。

**折叠形态**：收起态最多展示 3 条（时间倒序前 3）+「展开全部 N 条」开关；展开后列表**限高滚动**（下拉滑动查看，沿源维度表 >30 源形态先例）；「去处置」跳转语义与 testid 保留；空态文案「近期无失败记录」保留。
