# ADR-0019：个人信息流阅读埋点延后——readingEvent 契约无信息流条目承接面（T43）

- 状态：已接受（2026-09-22，T43）
- 状态更新：延后已解除（2026-09-25，REQ-20260925-08 立项承接——采纳「决策」选项 2 为主（ReadingEventType 新增 FEED）并吸收选项 1 的稳定内容引用透出，见 docs/01-需求/REQ-20260925-08-信息流阅读埋点.md；本文历史结论不变）
- 状态更新：M11 T80 已落地（2026-09-25）——FeedItem 增量字段 `contentId`，形态 `{type}:{源稳定 id}`（announce/news=externalId、policy=policyId、recommendation=subjectCode，类型前缀防跨类型撞去重键、超长截断至 200、源缺稳定 id 透 null 不用游标 id 兜底）；任务提示中的 anomaly 类型经查不存在于个人信息流（FeedItemType 仅 announce/news/policy/recommendation 四类），无需处置
- 日期：2026-09-22
- 决策人：开发工程师（依 UI 方案 §3.5 交互 4 与任务表 T43 口径；后端本轮冻结不改）
- 补充：ADR-0016（阅读留痕表与推荐个性化）、技术方案 §4.1.6（FeedItem 契约）

## 📌 背景

UI 方案 §3.5 交互 4：「点击条目卡主体或『原文』记阅读埋点（复用既有 readingEvent API，POST /reading-events 去重窗口后端管）」。实现前盘点发现该交互在既有契约下无法正确落地：

- **contentType 枚举只有三类**：`ReadingEventType` = `SUBJECT_DETAIL / POLICY / AI_BRIEF`（ADR-0016），无信息流条目类型。
- **contentRef 语义不匹配**：`POLICY` 要求政策 id，而 `FeedItem.id` 是按 publishedAt 排序后回填的**合成游标序号**（1 起递增、每次请求重算），不是政策 id——用它上报会把留痕记到错误政策上。
- **语义污染**：把公告/新闻/推荐条目的点击映射为 `SUBJECT_DETAIL`（contentRef=标的代码）会虚构"读过标的详情页"事件，直接污染 ADR-0016 推荐个性化的已读衰减评分。
- **本轮约束**：M4 末批任务明确「后端本轮不应改动」，FeedItem 契约已随 383df55 定稿（只加 keywords，不动既有字段语义）。

## 🎯 决策

**T43 前端不实现信息流阅读埋点，交互 4 整体延后**；页面其余交互（高亮/分页/空态/外链）不受影响。后续若要承接，需后端先扩展契约（二选一，届时另立任务评估）：

1. `FeedItem` 透出内容引用（如 `contentRef: {type, id}`，policy 带 policyId、announce/news 带 externalId+subjectCode）；前端复用既有三类 contentType 按引用上报。
2. `ReadingEventType` 新增 `FEED` 类型（contentRef 为信息流条目稳定标识），推荐评分侧决定是否纳入衰减。

## ⚖️ 候选方案对比

| 方案 | 结果 |
| --- | --- |
| 上报 `POLICY` + FeedItem.id | ❌ 合成序号非政策 id，留痕错位 |
| 公告/新闻/推荐点击上报 `SUBJECT_DETAIL` + subjectCode | ❌ 虚构阅读事件，污染推荐个性化评分 |
| 前端本地丢弃埋点（本 ADR） | ✅ 采纳——漏记留痕仅损失"信息流点击"这一未消费信号，不产生错误数据 |
| 本轮顺带改后端补 contentRef | ❌ 违反「后端本轮不应改动」批次边界，且涉及接口契约变更需回架构（角色红线） |

## ⚠️ 影响

- 正面：不产生错误留痕；契约零变更；T43 交付面（PRD 场景 6.1/6.2 验收：展示/高亮/分页/空态）完整。
- 负面：每日推荐的个性化信号缺少信息流点击来源（现有 SUBJECT_DETAIL/POLICY/AI_BRIEF 三类埋点不受影响，ADR-0016 机制照常工作）。
- 需要跟进：若产品侧确认需要信息流点击影响推荐，按「决策」节两选项立项。
