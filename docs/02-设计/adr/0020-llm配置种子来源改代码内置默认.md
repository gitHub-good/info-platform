# ADR-0020：LLM 配置种子来源改代码内置默认——application.yml 删除 `llm:` 段，页面配置即唯一真相

- 状态：已接受（2026-09-22，M4 后配置来源收口）
- 日期：2026-09-22
- 决策人：开发工程师（依用户决策「LLM 模型配置改为页面（runtime_config DB）唯一来源」；架构口径不变，ADR-0017/0018 仍有效）
- 补充：ADR-0017（运行时配置热生效：seed-if-absent + 快照）、ADR-0008（配置驱动多 provider）、ADR-0018（API key DB 密文 > ENV > 空）、ADR-0010（先例：T36 `DataSourceDefaults`）

## 📌 背景

ADR-0017 落地时（T34/T35），LLM 域种子来源是 application.yml 的 `llm:` 段（4 provider + 全局超时/重试/日预算/告警阈值/缓存 TTL），经 `@ConfigurationProperties` 绑定类 `LlmConfig` 承担两个角色：**首启 seed-if-absent 的种子值**与 **DB 缺键时的回落值**。上线运行后用户裁定：模型参数的日常调整（厂商调价、换模型、启停 provider、改预算）全部发生在页面，yml 里的同名配置从此再也不会被修改——双来源只剩维护成本：

- **认知负担**：「改 yml 还是改页面」需要解释 seed-if-absent 语义，且 yml 改动只在首启空库时生效，容易误判为配置失效；
- **部署耦合**：调价/换模型本可纯页面完成（LIVE 级保存即生效），却给人「要动部署文件」的暗示；
- **同类先例**：T36 数据源域已把种子/回落/单测三处收敛到代码内置 `DataSourceDefaults`（单一事实源），LLM 域照此收口即可。

## 🎯 决策

**删除 application.yml 的 `llm:` 段与绑定类 `LlmConfig`，新建 `infrastructure/ai/LlmDefaults`（纯静态、无 Spring 依赖）承载同一份缺省值**，三处用途共用（对齐 T36 先例）：

1. `LlmRuntimeConfigSeeder` 种子值（首启 seed-if-absent 导入 runtime_config，DB 已有键不动——页面改过即权威，语义不变）；
2. `ConfigCenter` LLM 域缺键回落（provider 视图 / boot 级 baseUrl / 全局参数兜底，语义不变）；
3. 纯构造单测的断言基线（原 yml 绑定测试改写为缺省值防漂移测试）。

**迁移范围（yml → LlmDefaults 原样迁移，一个不漏）**：4 provider（deepseek/glm/qwen/kimi 的 name/baseUrl/model/enabled/default/fallback/单价）+ 全局 timeoutSeconds=30 / retry=1 / dailyTokenBudgetPerUser=20000 / budgetWarnRatio=0.8 + 缓存 defaultTtlSeconds=3600 / maximumSize=1000 / TTL 分档（brief-type-1:3600、brief-type-3:3600、brief-type-4:86400）。

**不变项**：① api-key 不内置、不种子（ADR-0018 一等来源不动）——ENV 解析从「yml 占位符 `${DEEPSEEK_API_KEY:}` 启动期求值」平移为 `LlmDefaults#envApiKey` 按需 `System.getenv(NAME_API_KEY)`（命名约定相同，DB 密文 > ENV > 空的解析顺序不变）；② 接口契约、键空间、校验规则、RESTART/LIVE 生效分级全部不动；③ 已有库的 runtime_config 行不受影响（seed-if-absent）。

## ⚖️ 候选方案对比

| 方案 | 结果 |
| --- | --- |
| 保留 yml `llm:` 段不动（现状） | ❌ 双来源认知成本持续存在；yml 值事实上永不更新，是"看起来能配其实不生效"的陷阱 |
| yml 保留但加注释「仅首启种子」 | ❌ 本质仍是双来源，注释救不了语义 |
| **代码内置 `LlmDefaults`（本 ADR）** | ✅ 单一事实源；页面即唯一真相；对齐 T36 `DataSourceDefaults` 先例；缺省改动随代码走版本评审 |
| 直接删缺省、首启零种子 | ❌ 全新库首启页面无基线、网关无默认链（fallback 链/预算/超时全空），可用性倒退 |

## ⚠️ 影响

- 正面：LLM 模型参数（provider/模型/单价/预算/超时/TTL）只剩页面一个入口；ENV key 一等来源不变，部署零改动；`LlmConfig`（277 行绑定类）与 yml 段（54 行）退役，消费点构造依赖减一。
- 负面 / 代价：改「出厂缺省」（如新厂商定价基准）从改配置文件变为改代码 + 发版——但这些值本就只在首启空库时生效，页面已可覆盖一切，实际代价可忽略。
- 行为兼容：已有库无感（DB 值权威）；全新库首启播种结果与旧 yml 种子字节级同值（迁移测试锁定）；无 yml 段下 ENV key 解析照常（集成测试锁定）。
- 测试影响：原 `LlmConfig` 绑定测试改写为 `LlmDefaultsTest` 防漂移测试；ENV 相关单测的注入点从「构造 yml 绑定实例」改为 mockStatic `LlmDefaults#envApiKey`（`System` 不可 mock，ENV 读取收敛到该方法后天然可测）。

## 🔍 后续验证方式

- `LlmDefaultsTest`：内置 provider 清单与逐字段值、全局常量、TTL 分档、ENV 变量命名映射与缺失归一（原 yml 段迁移防漂移）。
- `LlmDefaultsBootstrapTest`（@SpringBootTest，yml 已无 `llm:` 段）：① 全新库首启 5 键（llm.global + 4 provider）由内置缺省播种且类型化视图/boot 级 baseUrl/价格全可用；② DB 已有值 + 再走启动就绪（重启模拟）不覆盖页面权威值；③ ENV key 经 `System.getenv` 解析仍生效。
- 全量 `mvn verify` 回归（910 基线只增不减）。
