# ADR-0061：M22 增量重评触发消费与重算留痕及榜单联动互斥三裁决

- 状态：已接受（2026-09-22，M22 设计阶段）
- 决策人：架构设计师
- 关联：[技术方案-V2.2-M22](../技术方案-V2.2-M22-事件增量与收官.md)（本 ADR 的展开面） · [REQ-20260926-18](../../01-需求/REQ-20260926-18-M22-事件增量与V2.2收官.md)（PM 交接裁量项的裁决输入） · [ADR-0058](0058-M20因子集快照结构与权重模型及双Spike裁决.md)（幂等 UPSERT 口径） · [ADR-0059](0059-M21回联提升路径与粗筛切分及深析降级与合成公式.md)（版本化榜单/深析降级） · 个人知识库方案库（~/knowledge-base/project-development/02-design/solution-catalog.md：03 幂等 ✅ / 06 MQ ❌ / 08 定时任务 ✅ / 10 状态机 ✅ 裁剪）

## 📌 背景

REQ-20260926-18 拍板一把「事件驱动增量重评」交架构裁量六点：触发消费方式、多事件合并去抖窗口（合并后仍 ≤15min）、互斥实现、增量留痕表、命中统计回算形态、分数差阈值缺省。运行库实测（2026-09-27）：event_item 50 事件 / HIGH 日增个位数；ManagedJob 17 个（JobExecutor 每 jobKey CAS 守卫 + 公开 isRunning）；SQLite WAL + busy_timeout=5000 且既有立场为「跨任务并发靠 WAL 排队」；17:30 快照 <2min / 18:00 榜单 4~12min。

## 🎯 决策（三主裁决 + 两随批）

1. **触发消费 = 独立 ManagedJob `INCREMENTAL_REEVAL`（FIXED_DELAY 60s 短轮询扫 HIGH 未消费事件，第 18 Job）**；合并去抖窗 = tick 间隔本身（60s tick + 20s 落库缓冲，同窗事件按标的并集一轮重算，无独立去抖组件）。
2. **增量重算与留痕 = 提取 `FactorSnapshotService` 单标的重算方法（与全量同源投影同纯函数）+ `subject_factor_snapshot.increment_at` 留痕列（V33 ALTER，全量 UPSERT 置 NULL 复位）+ 事件粒度留痕表 `incremental_reeval_log`（UNIQUE(event_id) 判重 + 前后分/联动版本/时效列）**——否决 factor_detail JSON 塞审计信息。
3. **榜单联动互斥 = 三层从简（不建显式锁表）**：WAL busy_timeout（既有）+ 重 Job 让路（tick 查 `isRunning(FACTOR_SNAPSHOT ‖ MARKET_TOP_JOB)` 则整体 DEFERRED 下轮重试，经新 `RunningJobIndicator` 接口依赖倒置，M20/M21 Job 类零改动）+ `insertVersion` 唯一冲突重试一次（DAILY/EVENT 共用）；联动判定 = 新 domain 纯函数 `SqueezeJudge`（判定集「当日 Top10 ∪ 受影响标的」，挤入挤出双向同阈迟滞 `minScoreGap` 缺省 0.5 可配），version+1 追加 trigger_source=EVENT + trigger_events 归因列，不变成员深析成果直继承、仅新入榜补一次深析。
4. **命中统计 = 惰性回算零新表零新 Job**（否决回算 Job 物化 `market_top_hit_stats`）；T+20 时序核实：价格快照 2026-09-26 起、榜单留痕 09-27 起，首测三窗均「样本不足」如实标注（首跑校准条款）。
5. **联动防抖间隔缺省 10min 可配**（`incremental.reeval` 新配置键，错误码 30092；不扩 `market.top` 键避免 PATCH 契约连带变更）。

## ⚖️ 候选方案对比（裁决一消费方式 / 裁决三互斥）

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 独立 Job 60s 短轮询 | 与推荐消费解耦 / 重启免疫（进度全在留痕表）/ 复用 M16 扫描模式 / 可独立热改停启 | 多一常驻 Job（池 15→16 线程） | ✅ 采用 |
| 挂 RECOMMENDATION_FEED 同轮 | 零新 Job | 两条链路耦合（停推荐连带伤增量时效红线；容错/判重口径互相污染） | ❌ 时效红线链路不搭便车 |
| L2 落库后置钩子 | 时延最低 | 写路径同步耦合重计算；触发丢失无补救 | ❌ |
| 事件流订阅 | 标准 MQ 形态 | 进程内事件重启即丢仍需落表扫描兜底；单体伪需求；违蓝图「不新建通道」 | ❌（方案库 06 不采用留痕） |
| 显式互斥锁表/分布式锁 | 互斥最强 | 单体单实例纯增负；与既有「WAL 排队」立场冲突；18 Job 无重复部署面 | ❌ 三层从简已覆盖冲突面 |

## 💡 理由（五维度）

- **成熟度**：扫描判重消费 = RECOMMENDATION_FEED 两迭代验证模式；版本化追加 = M21 在册机制；纯函数判定 = PoolBuilder/TopComposer 同款。
- **社区/学习成本**：零新框架零新概念，全部复用既有基建（ManagedJob/RuntimeConfig/JobRunStats/UPSERT）。
- **可替换性**：消费入口 tick() 单方法，未来换长轮询/订阅零牵连；SqueezeJudge 纯函数可独立替换。
- **运维成本**：任务中心可视/热改/手动补触发全套继承；留痕表即审计即北极星数据源，无第二套统计管道。
- **风险面**：独立 Job 隔离爆炸半径（增量故障不伤推荐、全量自然修复）；零漂移由「同投影同纯函数同 weight_basis」构造保证而非测试保证。

## ⚠️ 影响

- 正面：增量链路全程复用已验证模式；17:30/18:00 双 Job 零重构（拍板四兑现）；北极星时效 SQL 直出。
- 负面/代价：调度池 15→16 线程；判定集不含静态近榜候选——增量版本是「快照式局部正确」，全序修正留给 18:00 全量（边界已留痕）。
- 跟进：增量样本 ≥3 工作日后北极星时效首测（T194）；阈值 0.5 首测校准走变更控制（需求既定）。
