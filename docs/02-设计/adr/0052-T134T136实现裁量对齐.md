# ADR-0052 · M16 T134/T136 实现裁量对齐（任务文本与方案原文的出入，方案为准）


> **勘误（2026-09-26，M16 T138 BUG-01）**：本 ADR 裁决 2 的 SSE 事件名「recommend」与 T133 实际落地（后端 SseConnectionRegistry 发 `recommendation`、push_record 历史 type=recommendation）不一致，曾致前端订阅键断裂。**最终统一为 `recommendation`**（与后端事件名/历史数据一致），裁决 2 的事件名表述以此为准；前端已在 3936036 修复。

- 状态：已接受（2026-09-26）
- 关联：ADR-0048/0049/0050（任务文本出入以方案为准的先例）/ ADR-0051（M16 四裁决与基建扩位）/ [技术方案-V2.0-M16](../技术方案-V2.0-M16-动态主动推荐.md) §4.1/§4.6/§4.7
- 需求：REQ-20260926-13（任务派发单 T134 反馈闭环与采纳统计 / T136 铃铛推荐渲染）

## 背景

M16 最后开发批（T134~T137）任务派发文本与 M16 技术方案（权威）存在三处出入。按「涉及契约与数据口径的全部以方案原文为准落地」的既有裁量（ADR-0048/0049/0050 同款流程），本 ADR 逐条记录留痕。

## 裁决

### 1. retention 两表保留窗口：共享 `recommendationCardDays` 单键 180/30（方案 §4.1 注记），任务文本的「card 90d / feedback 180d 两键 + 页面五→七字段」不落地

- 任务文本：`RetentionLogTable 加 recommendation_card（90d）/recommendation_feedback（180d）两键 + 页面五→七字段`。
- 方案 §4.1 索引预算注记（原文）：`RetentionLogTable 增 RECOMMENDATION_CARD("recommendation_card","recommendationCardDays",180,30) 与
  RECOMMENDATION_FEEDBACK("recommendation_feedback","recommendationCardDays",180,30)`——两表 created_at 同刻落库**同窗同清**
  （沿 NEWS_ANALYSIS 随 newsItemDays 先例，ADR-0046 裁决 1 注记）；mute 表常驻不清。
- **落法**：两枚举项均挂 `recommendationCardDays`（缺省 180、下限 30）；配置面/页面**五→六字段**（TaskCenter 留痕窗口分组），非七字段。
- 理由：同窗同清保证「卡片被清出时其反馈流水一并清出」的近似同轮语义（窗口不一致会出现无卡流水/孤儿操作条回显）；两表日增量同量级（卡 5~15/日、反馈 ≤卡数），分窗无运维收益；页面多一字段即多一处心智负担。

### 2. SSE 推荐载荷 `type` 线格式：`recommend`（T133 已落的 `PushType.eventName`），任务文本载荷示例的 `type:"recommendation"` 不落地

- 任务文本：SSE `event:recommend` 载荷 `{type:"recommendation", ...}`（事件名与载荷 type 不一致）。
- 方案 §3.5 基建扩位：`PushType.RECOMMENDATION(10, "recommendation")` 的第二参为 **SSE 事件名**——但 §4.6 SSE 载荷契约示例又写
  `event: recommend`；T133 落地代码为 `RECOMMENDATION(10, "recommend")`（事件名与载荷 type 同源，`NotificationEvent.of` 统一取
  `eventName`）。
- **落法**：沿 T133 已落实现——SSE `event: recommend` 且载荷 `type: "recommend"`（事件名=载荷 type=history type=前端
  `NOTIFICATION_EVENT_TYPES`/`TYPE_LABELS` 键，四点同源）；前端 T136 铃铛按 `recommend` 键监听与渲染「动态推荐」徽章。
- 理由：SSE 命名事件与载荷 type、history type 若不同名，前端要维护两套键映射；`anomaly/policy/ai_brief` 等既有 9 类均为
  事件名=载荷 type 同源先例；改 T133 已验收代码违背零回归红线。方案 §4.6 示例的 `type:"recommendation"` 视为方案内部笔误
  （§3.5 表格与实现链一致）。

### 3. 采纳数当日口径实现：ACT 埋点 distinct 卡（与 card.adopted 首置同点写入恒等），非按 card 表 updated_at 近似

- 方案 §4.7 采纳统计：`采纳 = COUNT(recommendation_card WHERE adopted=1 AND adopted 当日首置)`——card 表无 adopted_at 列
  （V26 DDL），「当日首置」不可直接从 card 表判（updated_at 会被已读/反馈等无关更新推进，按 updated_at 过滤会漂移）。
- **落法**：`RecommendationFeedbackService` 采纳同点写入——`markAdopted` 条件 UPDATE（`WHERE adopted=0`）返回 1 才落
  `RECOMMENDATION_ACT` 埋点（方案 §4.7 对账断言原文「均先条件置位成功再落 ACT」的机械执行）；stats 端点当日采纳数 =
  当日 ACT 埋点 distinct contentRef。全时恒等断言 `COUNT(adopted=1) == COUNT(DISTINCT ACT)` 成立，且当日归属精确到首置时刻。
- 连带裁量：已采纳卡（条件置 0 行命中）上的重复 USEFUL 不再落第二条 ACT——画像回流热度不重复累计（readStats 聚合本就按
  distinct subjectId 小时窗去重，语义无损）；「不感兴趣不计负画像」（REQ 拍板六-3）不受影响。

## 后果

- 前端 T136 铃铛/通知历史推荐行按 `recommend` 单键消费；任务文本载荷示例不作为前端契约。
- 留痕配置页（TaskCenter RETENTION_CLEANUP 编辑 Dialog）为六字段；存量 `retention.global` 五字段键缺
  `recommendationCardDays` 时执行侧字段级回退 180，保存一次即补齐（seed-if-absent DB 为权威不变）。
- 如后续确需两表分窗（如反馈流水留更长以支撑升级计数审计），走新 ADR 变更 + 键扩展。
