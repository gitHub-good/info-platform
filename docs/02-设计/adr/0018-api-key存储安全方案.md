# ADR-0018：API key 存储安全方案——DB AES-256-GCM 加密存储 + 脱敏回显 + DB 优先/环境变量回落（REQ-20260922-02 / M4）

- 状态：已接受（2026-09-22，M4 设计阶段）
- 日期：2026-09-22
- 决策人：架构设计师（依 REQ-20260922-02 两个待 ADR 技术题之二 + 技术方案增补 §4.7）
- 补充：ADR-0008（api-key 走环境变量不硬编码）、ADR-0015（llm_call_log 留痕不含 key）、ADR-0017（runtime_config 存储模型）

## 📌 背景

现状 LLM provider 的 api-key 仅经环境变量注入 `LlmConfig.Provider.apiKey`（`AbstractOpenAiCompatProvider` 每次调用现读，永不入文件/git）。REQ-20260922-02 提出：

- **红线**：API key 明文永不回显前端、不写入前端 console 与网络日志（"不回显、不留痕"）。
- **功能诉求**：故事 2 场景 4 要求页面可查看脱敏态（"已配置（尾 4 位 ****abcd）"）**并可录入新 key**，保存后仍只显示脱敏态。
- **授权**：存储与传输方案（加密/环境变量同步等）归架构裁定；PM 风险表明示接受"key 仍走环境变量、页面只读状态"的降级实现。

矛盾点：纯环境变量方案无法满足"页面录入新 key"；明文落库违反红线；需要给单人本地场景定一个够用且不过度的安全基线。

## 🎯 决策

**采用方案 B「DB 加密存储 + 脱敏回显 + 双来源回落」：**

1. **存储**：`runtime_config` 的 `llm.provider.{name}` 键内存 `apiKeyCipher` = base64(随机 12 字节 IV ‖ AES-256-GCM 密文) + `apiKeyLast4`（明文尾 4 位，仅供展示）。主密钥 = 环境变量 `CONFIG_SECRET`（≥32 字节；启动时若配置则校验长度，不合法 fail-fast，与 `JWT_SECRET` 同策略）。加密用 JDK 内置 `javax.crypto`（AES/GCM/NoPadding），零新依赖。
2. **运行时解析顺序**：DB（该 provider 已由页面写入）> 环境变量（`LlmConfig` yml 绑定值）> 空串（adapter inert）。环境变量保持一等来源——已按现方式部署的环境零改动，页面写入仅是覆盖。
3. **回显契约**：`GET /api/v1/llm-config` 仅返回 `apiKey: {status: CONFIGURED|NOT_SET, source: DB|ENV, last4}`，任何接口不回明文；录入走 `PUT /llm-config/providers/{name}/api-key`（只写不读）。
4. **不留痕**：明文仅存在于请求体与进程内存瞬时生命周期；`llm_call_log` 与各日志路径均无 key 字段（维持现状）；key 写入路径的日志只记"provider {name} api-key 已更新"，值不落任何日志。
5. **降级**：`CONFIG_SECRET` 未配置时**不阻断启动、不禁读**——写接口返回 30064（503，"API key 写入未启用"），页面显示只读态"key 走环境变量"（即 PM 预案的降级实现，作为运行时降级态而非整体方案）。

## ⚖️ 候选方案对比

| 方案 | 满足页面录入 | 防库文件/备份泄露 | 防前端/日志泄露 | 成本 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A 仅环境变量 + 页面只读状态（PM 降级预案） | ❌ 改 key 仍登服务器 | ✅（不落库） | ✅ | 零 | ❌ 否决（故事 2 场景 4 写路径缺失；保留为 CONFIG_SECRET 缺失时的运行时降级态） |
| B DB AES-256-GCM 加密 + 脱敏回显 + DB>ENV 回落 | ✅ | ✅（无主密钥的库文件/备份拿不到明文） | ✅（契约不回明文 + 日志无 key 字段） | 低（JDK 内置） | ✅ 采用 |
| C 明文落库 | ✅ | ❌ 库文件即密钥 | ✅ | 零 | ❌ 否决（违红线） |
| D 外部 secret 管理（系统 keychain / vault） | ✅ | ✅ | ✅ | 高（跨平台脚本 + 新组件 + 单人本地运维负担） | ❌ 否决（过度设计） |

对照选型五维度：成熟度（AES-GCM 为 JDK 内置标准件）、社区（零新依赖，问题域极小）、学习成本（一个加解密工具类）、可替换性（密文格式自包含，换 KMS/钥匙串只换工具类实现）、运维成本（一个可选环境变量）。

## 💡 理由

单人本地部署的威胁模型要防的是两类现实风险：**库文件/备份被拷走后的 key 批量泄露**（AES-GCM 随机 IV 加密使密文脱离 `CONFIG_SECRET` 无价值）与**前端响应/日志中的明文暴露**（契约层只回脱敏态 + 写路径日志纪律），而不是能接触机器内存的定向攻击者——对后者任何本地方案都无解，D 的重运维不改变这一边界。保留"DB 优先、ENV 回落"的双来源是关键裁剪：既给了页面录入通道（需求），又不强迫迁移现有环境变量部署（存量零改动），`CONFIG_SECRET` 缺失时的只读降级让安全配置与功能交付解耦——不配密钥也能用，配了才可写，与 PM"接受降级实现"的授权一致。

## ⚠️ 影响

- 正面：key 页面可录入可轮换（保存即生效，ADR-0017 热生效链路覆盖）；明文永不落库/不回显/不留日志，红线全满足；环境变量部署路径零改动。
- 负面 / 代价：新增可选环境变量 `CONFIG_SECRET`（未配置则 key 写入功能降级）；轮换 `CONFIG_SECRET` 会使已存密文不可解（需重新录入 key——单人 4 个 provider 量级可接受，README 部署说明需写明）；GCM 每次 12 字节随机 IV，密文长度略增（无影响）。
- 接口契约影响：`PUT /llm-config/providers/{name}/api-key`（只写）与 GET 脱敏字段（status/source/last4）；新增错误码 30064（503）。
- 数据迁移影响：无新表（复用 V15 `runtime_config`，key 相关字段在 provider JSON 文档内）。

## 🔍 后续验证方式

- 单测：加解密往返（含 IV 随机性：同明文两次密文不同）、尾 4 位提取、`CONFIG_SECRET` 长度校验 fail-fast。
- 契约测试：GET 响应体断言无明文 key（含日志输出断言）；写入后仍只回脱敏态、刷新不回显（故事 2 场景 4）。
- 集成：DB>ENV 解析优先级与 env 回落（DB 清空后自动回落 env）；缺 `CONFIG_SECRET` 写入返回 30064、读正常；页面录入 key 后连通性测试与真实调用走新 key。
