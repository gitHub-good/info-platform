## 📌 背景

T47/T48 按 M5 UI 设计与技术方案实现（提交 72324bb / 1334247）。D1~D11 拍板、testid 清单、三态规范、三级校验形态逐字落地；以下六处为**实现层**的小偏差/设计文档内部张力的调和，登记备查。

## 🎯 决策（六处）

1. **保存确认 Dialog 触发口径：`removed.length > 0` 才弹，仅 unknown 不弹直接保存**。UI 方案 §3.3 交互 7 写「有移除或未知 → 弹 Dialog」，§3.4 线框注写「仅未知占位符、无移除项时不弹 Dialog 直接保存（面板警告已足够）」——两处张力，取更具体的 §3.4：unknown 的 amber 提醒在面板与对照栏已实时可见，弹层无增量信息；后端 30068 兜底不受影响（其触发条件本就是未确认移除）。
2. **`SaveFeedbackBar` 增可选 `successLabel` prop（默认「已保存」）**。D10/§4.2 规定激活/删除反馈文案为「已激活 vX.Y · 即时生效：…」「已删除 vX.Y」——组件固定前缀「已保存」无法表达非保存操作语义。纯增量可选参数，既有全部调用方零改动零行为变化。
3. **`ApiError` 增可选 `data` 字段透传结构化错误 data**。对接说明要求 409/30068 时读取 `data {removed, unknown}`，但 `http.ts` 统一错误抛出原先丢弃 `parsed.data`。构造器追加可选尾参（既有两处调用零改动），编辑器按 `err.data as PromptRemovalConfirmation` 消费；非 30068 错误 data 恒 null 无歧义。
4. **草稿 payload 存 `baseVersionId`（D11 只约定 key 含 briefType）**。diff 基准 = 底稿版本内容：跨底稿的旧草稿若原样恢复会把「基于 A 版的正文」配到「基于 B 版的 diff 基准」上，确认清单错位。故恢复提示仅在草稿 `baseVersionId` 与当前底稿一致时出现，跨底稿旧草稿视为过期（被新草稿覆盖时清除）。
5. **无激活版场景「新建版本」预填分段标记骨架 `---SYSTEM---\n\n---USER---\n`**。UI 方案未规定空底稿形态（正常路径恒有激活版作底稿）；该异常修复路径下从白纸起步用户无从知晓标记语法，骨架让校验面板只引导补 json 字样等剩余前提。
6. **场景注册表懒加载时机 = 该场景首张版本卡展开详情时（页面级缓存）**。§3.1 交互 1 说列表视图不请求注册表（分区头注册数从简隐藏），但 §3.2 交互 3 的详情占位符着色需要注册表区分 sky/amber——懒加载挂到首次展开详情，两者同时满足：未展开任何卡时零额外请求，展开后分区头注册数与 amber 标注一并呈现。

## ⚖️ 被否方案与理由

- 1 的替代「按 §3.3 交互 7 有未知也弹」：场景 2（休眠）模板天然含 7 个事件类 unknown，每次保存都强弹一层无操作弹窗，违背 §3.4「不多一层弹窗」的显式意图。
- 2 的替代「激活/删除另写反馈 <p> 不复用 SaveFeedbackBar」：复制 aria-live/配色/role 语义成第二份实现，且 §6.1 交接项 6 明确「操作反馈全部走 SaveFeedbackBar」。
- 3 的替代「编辑器裸调 fetch 绕过 request()」：破坏统一请求层（前端基线红线：业务代码不直接裸调 fetch）。
- 4 的替代「草稿不分底稿一律提示恢复」：diff 基准错位属正确性问题，非体验问题。

## ⚠️ 后果

- 负面：`successLabel`/`data` 均为可选扩展，共享组件语义面略增（各 +1 prop/字段）。
- 正面：仅 unknown 不弹层使休眠场景保存路径少一层无意义确认；30068 兜底、逐项勾选、预勾选已确认项全链路可用（测试覆盖）；草稿跨底稿过期策略消除确认清单错位风险。
- 需要跟进：无（六处均不触及 HTTP 契约与数据模型；若 UI 复审对 1 有异见，改一行条件即回到「有未知也弹」）。
