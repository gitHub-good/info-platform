# ADR-0037：详情分区分页取分区子端点契约 + 翻页绕快照缓存直调源 + 聚合附加 sectionPagination 键

- 状态：已接受（2026-09-22，M12 详情分区分页）
- 日期：2026-09-22
- 决策人：架构设计师（实测依据为 2026-09-22 curl 直连三源，证据留档[技术方案-详情分区分页](/docs/02-设计/技术方案-详情分区分页.md) §1.2/附录 C）
- 关联：ADR-0035（M9 页码分页双模式先例——本批**不适用**，见理由）、ADR-0005（SourceCache）、ADR-0034（公告巨潮降级链）、ADR-0032（数据源配置种子缺省）

## 📌 背景

REQ-20260925-09（M12）为详情页四个列表分区补「看更多」：公告/事件页码分页（真总数）、新闻加载更多（诚实无总数）、政策不翻页只扩容。需求侧锁定三约束：① 翻任一分区仅刷新该分区，其他分区零重拉零闪变；② 切标的重置；③ 分区级 sourceStatus 三态语义与聚合页一致。现状唯一取数路径是全分区聚合端点（SourceCache 按 subjectId 键控的快照缓存），任何翻页方案都要回答四个问题：接口形态、翻页与缓存的关系、首屏总数怎么来、新闻停止条件谁判。前置实测（2026-09-22）：新浪 page 深翻可用（page=2/3/50 均 200×20 条、ctime 跨页衔接无重叠）、东财 `page_index` 深翻 + `total_hits` 恒定可用（1074）、gov.cn「最新政策」HTML 页列表为 AJAX 空壳而 `ZUIXINZHENGCE.json` 静态可取（1100 条）。

## 🎯 决策

1. **契约形态 = 分区子端点**：新增 `GET /api/v1/subjects/{id}/announcements?page=&size=`、`/events?page=&size=`、`/news?page=`；聚合端点零改动。公告/事件返回 `{items, page, size, total, sourceStatus, source}`（公告另带 `paginationSupported`/`moreUrl`），新闻返回 `{items, page, size, hasMore, ...}`。校验复用 M9 `PageQuery` 口径（page≥1、size 1~50 越界 400 拒绝）；公告 page 上限 5（超限 400，产品外呼封顶由此成立）。
2. **翻页绕缓存直调源**：子端点取数走 `SourceAdapter.fetchPage(subject, page, size)`（新增默认方法，抛 UnsupportedOperationException），实现「熔断→弹性→事件旁路→降级」与 `fetch` 同骨架但**不读写 SourceCache**；首屏聚合路径与快照缓存一字不动。
3. **首屏总数 = 聚合响应附加键**：`SubjectDetail` 追加可选 `sectionPagination`（`{"announce": {total, paginationSupported, moreUrl}, "event": {total}}`，仅 ok 分区出现）；列表分区既有键仍为裸数组——非破坏，不升 `/v2`。
4. **新闻停止条件判定归前端**：后端契约无状态（单请求 = 单源页过滤命中 + `hasMore` 源页耗尽信号）；前端持累积 `externalId`（docid）集合判「新增」，单点击最多探 2 源页、连续 2 空页 / hasMore=false / 累计 10 源页三路停止。
5. **配置迁移两件走 Flyway 条件 UPDATE**：V19 仅当 `announcePageSize=3` 置 10；V20 仅当 `policyUrl` 为旧目录页时改指 `ZUIXINZHENGCE.json` 并增 `policyMaxItems=30`（均附 U 脚本回滚；`GovPolicyClient` 增 JSON 分支，输出与 HTML 分支同款 raw 契约，adapter 零改动）。

## ⚖️ 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 聚合接口分区参数化（`/detail?sections=announce&page=2`） | 不加端点；复用聚合编排 | 响应仍是整张 SubjectDetail（其他分区 null，前端合并）；page 归属靠 sections 隐式约定，多分区+page 语义歧义；三种异构分页语义挤一个端点，参数模式爆炸；聚合主路径被翻页改动波及（回归面=存量 1432 用例） | ❌ 否决，原因：三约束（独立刷新/零重拉/三态一致）实现别扭，契约确定性差 |
| B 分区子端点 | 一请求=一分区，三约束天然成立；每端点单一分页语义；纯增量、聚合零改动、可整体废弃 | 新增 3 组 Controller/Service/View（约 +6 类） | ✅ 采用 |
| C 各页独立缓存（键扩 subjectId+page+size） | 翻页命中省外呼 | SourceCache 键类型改 7 源全量波及；页界漂移使页缓存价值低且更难解释 | ❌ 否决，原因：翻页是用户主动低频动作，缓存货架（方案 04）「读多写少」前提不成立 |
| D 列表分区值改对象（`announcements: {items, total}`） | 契约更「正」 | 破坏性变更（前端/1432 用例成套改），不满足升版门槛又强改语义 | ❌ 否决，原因：附加键已够用，零回归红线优先 |
| E 新闻停止判定归后端（带 excludeDocid 清单 / hasMore 即停止） | 前端薄 | 后端无状态无法判「新增」，docid 清单参数上限失控；hasMore 只表源页耗尽不表命中 | ❌ 否决，原因：客户端累积集合是「新增」唯一真相 |

## 💡 理由

- **五维度**：子端点是 REST 通行做法（成熟度/社区无争议、零学习成本、零新依赖）；纯增量端点可替换性最好（废弃即删）；运维成本零新增。
- **ADR-0035 不适用的辨析**：M9 双模式先例的前提是「同一列表资源加过滤条件、同语义」；本批是三个**异构**分页语义（页码+总数 / 源页+耗尽信号 / 无分页），对号入座后子资源分端点是标准解——不是推翻双模式，是它本来就不管这场景。
- **三态一致由构造保证**：`fetchPage` 与 `fetchFresh` 共用同一 `runGuarded` 骨架（熔断/弹性/事件旁路/降级钩子同一段代码），子端点与聚合的 ok/missing/failed/timeout 口径不可能漂移。
- **外呼封顶可证**：公告 5 页×每请求 ≤2 次外呼（东财+巨潮兜底）、新闻前端请求次数即外呼次数（≤2/点击、≤10 累计）、事件零外呼——无需额外限流组件。

## ⚠️ 影响

- 正面：聚合契约零改动（回归面最小化）；首屏总数搭既有取数便车（零新增外呼）；政策扩容连带 `PolicyFetchJob` 每轮摄入 9→30 条（URL 去重幂等，M9 政策时事页受益）；`fetchPage` 绕缓存使分页测试不受 TTL 干扰。
- 负面/代价：+3 端点 ×3 View 的代码面；`sectionPagination.announce.total` 随快照缓存（5min）与子端点实时值短窗不一致（接受，页界漂移同类固有现象）；mock 模式分页为「不报错」口径非真实深翻（PRD 已裁决）；巨潮生效时公告 page>1 返回空列表+`paginationSupported:false`（前端按降级文案处理）。
- 跟进：T90~T93 契约先行供 T94 Mock 启动；校验器 `announcePageSize` 收紧 1~50（存量行先经 V19 迁移再受检）。

## 🔍 后续验证方式

- T90~T92 单测：page 上限 400 / 越界页 200 空列表 / total_hits 透出 / 降级链 page 行为 / news 拒 size / hasMore 口径；聚合既有键字节级断言（附加键纯增量）。
- T96 验收：独立性实证（翻 A 区网络仅 1 个子端点请求）+ 22 GWT；`mvn verify` 1432 基线只增不减。
- 观测：Service debug 日志（page/size/total/毫秒）与 data_source_event 旁路（与聚合同节流口径）；新浪首页偶发慢（实测一次 6.5s）依赖既有 2s 超时 + 30s 负缓存，持续出现再立独立超时议题。
