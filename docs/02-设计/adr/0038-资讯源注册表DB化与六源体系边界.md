# ADR-0038：资讯源注册表 DB 化（info_source 表）与六源业务域体系边界冻结

- 状态：已接受（2026-09-22，V2.0-M13 源接入框架）
- 日期：2026-09-22
- 决策人：架构设计师（依据见[技术方案-V2.0-M13-源接入框架](/docs/02-设计/技术方案-V2.0-M13-源接入框架.md) §3.1）
- 关联：ADR-0017（runtime_config 配置中心——本批资讯源**不入**该体系）、ADR-0032（种子代码内置缺省 + seed-if-absent DB 权威，同系列惯例）、ADR-0033/0034（六源降级链——本批边界冻结不动）、[V2.0 普查报告 §5](/docs/02-设计/V2.0-信息平台普查报告.md)（源注册表 DB 化预判）、ADR-0039（news_item 资讯统一库）、ADR-0040（SOURCE_POLL 调度）

## 📌 背景

V2.0 要求「数据源多渠道维护增删改」：预置源库页面化运营（启停/参数/软删）+ 通用 RSS/JSON 源页面自增即生效（≤10 分钟出数），30 源规模不可能全靠代码硬接入。现状源注册表是**代码事实**（`SourceCode` 枚举 6 值 + `SourceProviders` 注册表），页面只能在已注册 provider 里编排 `datasource.{CODE}` 参数与降级链（ADR-0032/0033）——「用户自增源」无承载面。蓝图裁决 1 已锁定两层范围（预置运营 + 通用 RSS/JSON 配置化；任意网站自由爬虫规则为 Won't）。普查 §5 预判「源 = 类型 + 端点 + 映射 + 频控」落成配置行可行，但与既有六源体系的关系需架构裁决。

## 🎯 决策

### 1. 资讯源注册表落独立表 `info_source`，不入 runtime_config

预置源与用户通用源**统一行模型**：source_code（唯一）/ name / category / adapter_type（rss | json_api | preset，HTML_TEMPLATE 预留不开放）/ adapter_ref（preset 的 bean 名）/ endpoint / config（JSON：映射/包装剥离/headers/条数/游标声明）/ interval_minutes（1~60，兼作频控下限）/ enabled / is_preset / deleted（软删）。运行态分离到 `source_poll_state`（1:1，游标/退避/last_error），统计落 `source_daily_stats`（日 rollup）——配置行（低频编辑、页面域）与运行态（每轮写、调度域）不混表。

种子：`InfoSourceCatalog` 代码常量为预置源单一事实源，`InfoSourceSeeder` 启动 seed-if-absent（按 source_code，存量行不覆盖，DB 为权威）——ADR-0032 同系列；M14+ 每批新源 = 目录加行即补种。

### 2. 六源业务域与资讯源域**并存、边界冻结**

| 维度 | 六源业务域（不动） | 资讯源域（新） |
| --- | --- | --- |
| 驱动 | 请求驱动（按标的拉取 + SourceCache） | 调度驱动（7×24 轮询入 news_item） |
| 注册 | SourceCode 枚举（代码事实） | info_source 表行（DB 事实） |
| 配置 | runtime_config `datasource.{CODE}` + 降级链 | 行内 config/interval/enabled（tick 现读 = 热生效） |
| 失败语义 | 降级链（备源同容切换） | 退避摘除（源内容异质无「同容备源」） |
| 页面 | 数据源配置页 7 卡 | 新页 #/info-sources |

增删改语义沿蓝图裁决 1：**增** = 通用源页面新增（robots 校验硬拦截）/ 预置源启用；**删** = 停用 + 软删（deleted=1：调度摘除、配置归档可恢复、历史条目保留），预置源无物理删除无删除入口（403 + 前端无按钮）；**改** = 参数编辑下一 tick 生效（LIVE）。「新浪 7×24 升级既有新浪源」（M14）= zhibo 频道以 preset 源入 info_source，既有 NEWS（feed.mix 按标的详情）不动——同平台不同频道不冲突。

## ⚖️ 候选方案对比

| 方案 | 结果 |
| --- | --- |
| 泛化合并：SourceCode/SourceAdapter 扩展承载资讯源 | ❌ 需泛化三套强类型体系（枚举/适配器/降级链），1520 测试基线核心面全量波及；请求驱动与调度驱动、降级与退避的语义差异硬塞一套抽象，回归风险与收益倒挂 |
| 资讯源配置并入 runtime_config（如 `datasource.NEWS_FEED.{code}` 键族） | ❌ 键值模型装不下行级多源（30+ 源 × 十余字段）；查询/种子/校验/页面四处开特例；「源从键值变行集」正是本批架构目的，并入等于不做 |
| **独立 info_source 表 + 预置/通用统一模型 + 六源边界冻结（本 ADR）** | ✅ 新域零回归面（六源字节级不动）；行模型天然承载增删改与软删；tick 现读即热生效无需 ConfigCenter 介入；预置目录白名单制天然承载合规红线（普查 🔴 源根本不入目录） |
| 资讯源也走降级链模型 | ❌ 降级链前提是「备源同容」（腾讯行情替代东财行情）；资讯源内容异质，金十挂了新浪 7×24 替代不了它的快讯——退避恢复才是正确语义 |

## ⚠️ 影响

- 正面：「用户自增源」有了承载面且合规可控（robots 保存时硬校验 + 目录白名单双闸）；30 源扩张 = 目录加行 + 页面运营，无代码排期依赖（通用源）；六源域零改动保住回归红线。
- 负面/代价：源配置存在两处（runtime_config 六源 / info_source 资讯源），页面与心智需区分（业务源页 vs 资讯源页，各自入口）；`datasource.{CODE}` 键空间不再增长（新源一律 info_source）——此为有意冻结。
- 行为兼容：存量库零迁移感知（V22 纯新增四表）；数据源配置页与任务中心既有七 Job 视图不变。

## 🔍 后续验证方式

- T100 单测：种子 seed-if-absent 幂等 / 预置源 DELETE 403 / 软删后调度摘除且条目保留 / config 校验字段级拦截。
- T107 验收：六源聚合契约与降级链字节级零回归（1520 基线只增）；页面新增 RSS 源 ≤10 分钟出数。
