# ADR-0017：运行时配置热生效机制选型——自建配置中心快照 + 消费点用时读取 + 任务调度集中化（REQ-20260922-02 / M4）

- 状态：已接受（2026-09-22，M4 设计阶段）
- 日期：2026-09-22
- 决策人：架构设计师（依 REQ-20260922-02 两个待 ADR 技术题之一 + 技术方案增补 §3.1/§3.4/§4.2）
- 补充：ADR-0008（配置驱动多 provider + fallback）、ADR-0010（数据源弹性实现）、ADR-0015（预算计数与成本留痕）、方案库 03/04/08/12

## 📌 背景

REQ-20260922-02 要求配置可视化且分级热生效（日预算/告警阈值/单价/缓存 TTL 保存即生效为 **Must**；任务启停/间隔/cron 热切换为 Should，允许降级"页面明示重启生效"）。设计前逐文件核实现状：

- **静态绑定**：`LlmConfig`（@ConfigurationProperties）、`AggregationService`/各 client/各 Job 的 `@Value` 均启动期注入；`LlmGatewayImpl.timeout`、`LlmCostGuard` 预算/阈值 final 字段、`LlmCache` 默认 TTL/容量、`SourceCache` 全部 TTL（`specFor()` 硬编码）为**构造期固化**。
- **条件装配冲突**：14 个数据源 adapter 以 `adapter.mock.enabled` `@ConditionalOnProperty` 互斥装配（mock/real 二选一，启动期定死）；5 个 Job 的 `@Scheduled(fixedDelayString/cron)` 表达式启动期解析，且 Job bean 与 3 个 `@EnableScheduling` 配置类均受 `*.enabled` 条件装配——`recommendation.schedule.enabled=false`（生产默认）时 `DailyRecommendationJob` 根本不在容器里。
- **留痕链路**：`JobExecutionAspect` AOP 拦截 `@Scheduled` 方法 → `JobExecutionRecorder` → `job_execution_log`。

核心矛盾：Spring 的配置绑定与条件装配都是**启动期一次性**语义，与"保存即生效"天然冲突；同时 `@ConfigurationProperties`/`@Value` 消费点分散在三域十余处，需要一个统一机制而非逐点打补丁。

## 🎯 决策

**采用方案 B「自建配置中心」三件套（详见技术方案增补 §4.1/§4.2/§4.5）：**

1. **SQLite `runtime_config` 单表为权威存储**（域前缀键 + JSON 值 + 各域表驱动校验器，V15/U15）：启动 seed-if-absent 从 yml 导入（DB 已有键不动），之后 yml 不再覆盖页面值——"重启不丢"（PM 红线）由 DB 持久化满足。
2. **内存不可变快照 + 写时整体替换 + `RuntimeConfigChangedEvent`**：读走快照（volatile 引用，热路径零 DB 读零锁）；写 = 校验 → upsert → 换快照 → 发事件。消费点从"构造期取值"改为"用时经 `RuntimeConfigView` 取值"（改造清单见增补 §4.3，文件级）；`baseUrl` 与 LLM 缓存 `maximumSize` 定为 RESTART 级（读启动期冻结快照，页面明示），对齐 PM 分级。
3. **两处条件装配冲突的解法**：
   - mock/real → 14 个 adapter 去条件注解**无条件装配** + 每源一个 `RoutingSourceAdapter` 运行时按 `mode` 路由（bean 结构对外不变，`AggregationService` 零改动；yml `adapter.mock.enabled` 降级为种子默认值，测试 profile 语义平移）。
   - 任务调度 → 5 Job 去 `@Scheduled`/条件注解实现 `ManagedJob` 无条件装配，**集中式 `JobScheduler`**（`ThreadPoolTaskScheduler`，FIXED_DELAY/CronTrigger）按 `job.{KEY}` 配置注册；订阅配置变更事件取消重注册。手动触发与定时调度共用 `JobExecutor`（每 jobKey CAS 运行守卫）与 `JobExecutionRecorder` 留痕链路（AOP 随之退役，字段语义不变）。

**任务启停/间隔/cron 热切换裁定：可行，不启用 PM 降级预案。** 语义为**自下一调度周期生效**（进行中的一轮执行完毕；当前等待中的定时器按新值重排），页面明示。PM 预案「保留 @Scheduled + 页面明示重启生效」记为 Plan B：若 T37 迁移回归超限，可回退为"@Scheduled 保留 + 方法入口 enabled 开关（启停热）+ 间隔/cron 重启生效（明示）"，本 ADR 不关闭该退路。

| --- | --- | --- | --- |
| 成熟度 | 4 | 5 | 5 |
| 社区生态 | 4 | 5（零新依赖） | 5 |
| 学习成本 | 3（scope 代理/bean 销毁时序） | 4 | 5 |

| 关键否决点 | 说明 |
| --- | --- |
| A 否决主因 | `@RefreshScope` 刷新即**整 bean 重建**：`LlmCache` 缓存全失效、`LlmCostGuard` 当日计数清零、`LlmGatewayImpl` 依赖重注入——"调个预算把缓存和计数调没了"直接违背调优初衷；且为单人本地场景引入 spring-cloud-context 过重 |
| C 否决主因 | LLM 每调用/聚合每请求热路径加一次 SQLite 读 + JSON 反序列化，并与业务写竞争单写者（busy_timeout 排队），换来的仅是省一份内存快照 |

## 💡 理由

热生效的本质是"值的获取时机"问题，不是"配置存哪"问题：DB 已是现成的权威存储（ADR-0002），缺的只是（a）一个运行时可写的通道、（b）消费点不再把值冻在构造期。方案 B 恰好只动这两点：bean 结构、有状态组件（缓存/计数器）、既有接口契约全部不动，改造面收敛为增补 §4.3 的文件级清单。条件装配两处冲突各用"结构不动、行为路由"与"收编集中调度"化解——Router 模式让 mock 切换从"换 bean"降为"换分支"，调度中心让"启停/改周期/手动触发"共用一条执行与留痕链路（防重入天然成立，方案库 08「调度中心→执行器→流水→手动补跑」的裁剪采用）。五维度上 B 全维不劣，且是三者中唯一不引入新依赖、不丢运行态的选项（"无聊但成熟"）。

## ⚠️ 影响

- 正面：Must 级热生效参数全部保存即生效（预算/阈值/单价/TTL/超时/mock/启停）；任务可控（手动触发防重入 + 热切换）；配置重启不丢；报表预算上限随改随新（故事 2 场景 2 闭环）；调价只影响未来调用（`llm_call_log` 落死值，ADR-0015 既有设计天然满足 PM 红线）。
- 负面 / 代价：三域十余消费点需按 §4.3 清单改造（已文件级列出，约 2 人天分摊进 T35~T37）；`@Scheduled`/条件装配移除波及既有测试（隔离语义靠"测试 yml 开关 false → 种子 enabled=false → 调度零注册"平移）；AOP 留痕退役改显式调用（语义不变但相关切面测试需迁移）。
- 接口契约影响：新增 4 组接口（增补 §4.4：llm-config / datasource-configs / jobs / overview），纯新增无破坏；错误码新增 30060~30065。
- 数据迁移影响：V15（runtime_config + 三索引）/ U15（回滚），对齐既有 Flyway U 脚本手动执行惯例。

## 🔍 后续验证方式

- 配置中心：快照不可变/并发读写、表驱动校验全规则、expectedUpdatedAt 30065、重启 DB 优先于 yml 种子。
- 热生效集成（可注入 Clock/配置）：改预算下次调用拦截且报表同步；改单价新调用生效历史行不动；切 mock 路由立即切换；改 interval 下一周期按新间隔。
- 任务中心：五任务注册完整性；手动触发留痕 STARTED→SUCCESS；运行中再触发 409/30063；启停立即生效；cron/间隔变更重注册。
- 回归：`mvn verify` 后端全绿（基线 689，重点 adapter 上下文与 Job 单测）、前端 vitest 全绿（基线 56）。
