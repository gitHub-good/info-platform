# ADR-0028：消失确认存储设计——subject_master 内嵌 missing_streak 列（V18）（REQ-20260924-04 / M7）

- 状态：已接受（2026-09-24，M7 设计阶段）
- 日期：2026-09-24
- 决策人：架构设计师（依 REQ-20260924-04 裁决点 2「连续 N 轮确认自动停用」的存储落点 + 技术方案增补 §3.2/§4.1）
- 补充：ADR-0002（SQLite 单机选型）、V1（subject_master DDL）、V17（INSERT OR IGNORE 先例）

## 📌 背景

需求裁决：外部消失 ≠ 退市——单轮仅留痕"疑似消失"，**连续 N 轮（默认 3、可配）持续消失且该市场本轮拉取成功**才自动置 `status=0`；重新出现则计数清零。因此每行标的需要一个"连续缺失轮数"的持久化落点，且要支撑三条硬语义：市场失败不推进计数、回归清零、status 只 1→0。选型约束：SQLite 单库单人量级、subject_master 约 8500 行、每轮 diff 引擎本就全量加载该市场行进内存。

## 🎯 决策

**`subject_master` 加一列 `missing_streak INTEGER NOT NULL DEFAULT 0`（V18，附 U18 回滚）**，计数语义内嵌于主数据行：

```sql
-- V18
ALTER TABLE subject_master ADD COLUMN missing_streak INTEGER NOT NULL DEFAULT 0;
-- U18（回滚）
ALTER TABLE subject_master DROP COLUMN missing_streak;
```

四条配套 UPDATE（见技术方案增补 §4.4，语义全部 SQL 级表达）：

1. 出现行：`UPDATE ... SET missing_streak=0`（回归清零，与名称/行业更新合并同语句）；
2. 缺失行：`UPDATE ... SET missing_streak=missing_streak+1 WHERE subject_code=? AND status=1`（只对启用标的计数，已停用不动）；
3. 阈值停用：`UPDATE ... SET status=0 WHERE subject_code=? AND status=1 AND missing_streak>=?`（`WHERE status=1` 是 status 单向 1→0 的最后防线）；
4. 市场失败不计数：由流程结构保证——缺失推进只发生在"该市场本轮拉取成功"的单市场事务内，拉取失败在事务开启前即放弃（零写入）。

## ⚖️ 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A subject_master 加列 `missing_streak` | 一行一次 UPDATE 完成计数/清零/停用，无 JOIN 零额外查询；与 status/version 同为机制列语义内聚；查询成本为零（diff 基线加载时顺带读出） | 主数据表混入同步机制列 | ✅ 采用 |
| B 独立表 `subject_sync_state(subject_code PK, missing_streak, last_seen_at…)` | 主数据表纯净 | 8500 行双表一致性维护；回归清零/停用跨表两写扩大事务面；每轮 diff 需 JOIN 或双查——单人 SQLite 量级下收益为负 | ❌ 否决，原因：复杂度换纯度不成比例 |
| C 不落库，按 job_execution_log 各轮缺失清单差集推算 | 零 DDL | 推断依赖可清理的流水（job 日志清理在 backlog）；失败轮/成功轮交错时推算脆弱；"哪只连续缺 3 轮"需跨行解析无索引文本 | ❌ 否决，原因：正确性建立在不该承担该职责的数据上 |

## 💡 理由

对照五维度（成熟度/生态/学习成本/可替换性/运维成本）本取舍无外部依赖项，核心判据是**正确性表达成本**：A 把三条硬语义全部压进单行 UPDATE 的 WHERE/SET 子句，读侧零成本（引擎 diff 基线本来就要全量加载该桶行）；B/C 都把同一状态拆到第二处，每条语义要多一次跨数据结构协调。status/version 先例（V1）已确立"主数据表携带机制列"的口径，A 无新开先例。加列 `NOT NULL DEFAULT 0` 对存量 45 行无感迁移，SQLite `ALTER TABLE ADD COLUMN` 为 O(1) 元数据操作。

## ⚠️ 影响

- 正面：V18 迁移一行 + 回滚一行；阈值（3）与计数行为全参数化（`subject.sync.missing-streak-threshold`）；停用守卫 SQL 级可单测。
- 负面 / 代价：主数据表增加一列（U18 可回滚；列仅同步引擎读写，回滚无悬挂消费方）；「连续 N 轮」语义依赖"每轮至多执行一次"（手动+定时并发由 JobExecutor CAS 守卫拦截，既有能力）。
- 接口契约影响：无新端点；搜索/自选等消费方不感知该列。
- 数据迁移影响：V18/U18 成对，对齐既有 Flyway U 脚本手动执行惯例。

## 🔍 后续验证方式

- 单测四路径：单轮缺失仅 streak+1 不停用；连续 3 轮第 3 轮停用且 status=1→0；第 3 轮回归 streak=0 且 status 保持 1；市场拉取失败整桶计数不动。
- 首启建池后观察 1 个月：停用清单（deactivated 计数）人工抽查是否全部为真实退市/长期停牌（假缺失误停用是最坏失效模式，发现即调大阈值并在此记录）。
