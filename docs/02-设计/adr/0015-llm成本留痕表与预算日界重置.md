# ADR-0015：LLM 成本治理数据源与预算计数实现方式（T30）——独立留痕表 + 微元整数成本 + 日界键预算

- 状态：已接受（2026-09-22，T30）
- 日期：2026-09-22
- 决策人：开发工程师（依任务表 T30 + PRD「LLM 外部成本是核心风险，设成本上限与缓存」+ 技术方案 §4.4）
- 补充：ADR-0004（LLM 自建薄抽象网关）、ADR-0005（缓存与限频：Caffeine + 令牌桶）、ADR-0008（多 provider + fallback）、Spike-2 §8.3/§9

## 📌 背景

任务表 T30「成本治理报表 + 缓存/限频调优」要求：LLM 成本可观测（调用留痕 + 报表）、可治理（上限/告警）。实现前盘点 T19 现状发现三处与既有建议/遗留注释的偏差需要拍板：

- **Spike-2 §8.3 建议报表数据源为 `ai_brief.cost_tokens`**：但 `ai_brief` 只覆盖「简报生成成功」这一条路径——政策倾向判断（T28）不写该表；fallback 链全部失败的调用无记录（T21 直接置 status=2）；缓存命中根本不产生 ai_brief 行；无 provider/model/成本金额/耗时维度。按该建议实现，报表的失败率、命中率、跨场景分布全部缺数。
- **T19 `LlmCostGuard` 注释明示「严格跨日重置留 T30」**：计数键为 `userId` + `expireAfterWrite(24h)`，从首次写入起算的近似日重置——上午 8 点首次调用则次日上午 8 点才归零，与用户「当日预算」直觉不符。
- **成本金额无估算口径**：留痕只有 token 数，元口径需要单价×用量换算，单价随厂商调价波动（Spike-2 §8.1 DeepSeek-flash 空闲/高峰输入 1.0/2.0 元、输出 4.0/8.0 元），不能硬编码进代码。

## 🎯 决策

**三件套落地，全部配置驱动、既有 REST 契约零变更：**

1. **独立追加型留痕表 `llm_call_log`（V13/U13）承接全部成本观测**：每次 `LlmGateway.chat` 落一行——缓存命中（`cache_hit=1`，0 token 0 成本，provider 记原响应来源）/ 成功（token + 成本）/ 失败（attempted 链）/ 预算拒绝（REJECTED）四态，含 user/provider/model/scene_key/token/成本/耗时。`ai_brief.cost_tokens` 保持原职责（简报任务回溯），二者不合并。留痕经 `LlmCallLogger` 旁路写入，落库失败记 ERROR 不阻断调用主链路。
2. **成本估算 = token × 元/百万token = 微元（1e-6 元），整数存储**：单价配置化（`llm.providers[].input/output-price-per-million`，未配默认 0 即不估算，GLM 免费档为 0），`cost_micros` 整数列防浮点累加漂移，报表求和精确；厂商调价只改 yaml。
3. **预算计数改日界键 `userId:yyyy-MM-dd`（系统时区）**：换日取新键即严格跨日归零（T19 遗留修复）；旧键由 `expireAfterWrite(48h)` 兜底逐出。新增告警阈值 `llm.budget-warn-ratio`（默认 0.8）：用量首次越线记一次 WARN、报表置 WARNING 状态，100% 才拦截；报表告警状态与守卫执行同源（`LlmCostBudget` 端口暴露 `dailyBudgetTokens()/budgetWarnRatio()`）。

**缓存参数核对结论（Spike-2 §9）**：TTL 按 brief_type（个股 1h / 每日推荐 24h / 政策 1h）与 maximumSize 均已配置化且取值合理，T30 仅补 `brief-type-3` 显式项与配置注释，不改值；GLM/DeepSeek 限频为账号级高并发（2500 并发），个人量级远低于此，不引入全局 RPM 限频（YAGNI，由单用户日预算 + fallback 承担）。

## ⚖️ 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 独立 llm_call_log 留痕表（每次 chat 一行，四态） | 全场景/全维度可观测；失败与拒绝可见；报表口径完整；追加型流水无锁竞争 | 新增一张表 + 网关旁路写入（每调用 +1 次 INSERT，SQLite WAL 个人量级可忽略） | ✅ 采用 |
| 复用 ai_brief.cost_tokens 聚合（Spike-2 §8.3 原建议） | 零新表 | 只覆盖简报成功路径；失败/拒绝/缓存命中/政策倾向/provider 维度全缺；需反向改 T21 写入逻辑 | ❌ 否决 |
| 成本金额 REAL 浮点列 | 直观 | 累加漂移；分 provider 求和展示位不稳定 | ❌ 否决（微元整数） |
| 预算计数维持 24h TTL | 零改动 | 跨日不严格（T19 已标注遗留）；重启清零且与报表口径不一致 | ❌ 否决（日界键） |
| SQLite 持久化预算计数（每日行） | 重启不丢 | 写放大 + 与留痕表数据重复；内存计数 + 留痕表观测已满足个人量级 | ❌ 否决（记待办跟进项） |

## 💡 理由

成本治理的第一性需求是「知道钱花在哪、哪些是白花的」：失败调用与预算拒绝恰恰是治理动作的直接证据（fallback 是否在救火、限流是否在拦人），只统计成功路径的报表回答不了这些问题，故留痕表必须四态全收。微元整数是精度与实现成本的平衡点——单次简报 ~0.007 元（7200 微元），浮点 double 在万次累加后末位不稳定，而整数列求和精确且 SQLite INTEGER 亲和天然适配。日界键用「换键」替代「等过期」：不引入定时任务、不引入持久化，一行键结构变更即修复 T19 遗留，且时钟可注入保证可测。告警阈值配置化的动机同单价：个人量级 0.8 合理，换预算偏好时改配置即可。

对照选型五维度：成熟度（追加型流水 + Caffeine 键控 + 整数计价，全部常规手段）、社区（零新依赖）、学习成本（一张表一个旁路写入器）、可替换性（留痕表不耦合 ai_brief，未来加 Redis/ClickHouse 聚合只换仓储实现）、运维成本（SQLite 单文件，无新组件）。

## ⚠️ 影响

- 正面影响：LLM 成本全维度可观测（含省钱口径的缓存命中率与拦截口径的 REJECTED）；预算严格跨日且提前告警（80% WARN）；单价/阈值全部配置化，调价调参不动代码；`ai_brief` 契约零变更。
- 负面影响 / 代价：每次 LLM 调用多一次 INSERT（SQLite WAL 下微秒级，个人量级可忽略）；留痕表无清理任务（每日数十行，按年膨胀在个人量级无害，超出再议分区/归档）；预算计数仍是内存态，重启当日清零——拦截会放宽到预算上限内，属可用性优先的取舍（报表口径以留痕表为准，不受影响）。
- 接口契约影响：新增 `GET /api/v1/llm-cost-report?window=today|7d|30d`（缺省 7d，非法 400/2001），纯新增无破坏；受 JWT 保护（仅 `/auth/login` 白名单）。
- 数据迁移影响：新增 V13（建 `llm_call_log` + created_at 索引）/ U13（回滚），Flyway 社区版 U 脚本手动执行（对齐既有 U1~U12 惯例）。
