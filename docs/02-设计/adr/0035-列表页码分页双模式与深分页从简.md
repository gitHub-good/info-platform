# ADR-0035：列表页码分页取同端点双模式 + LIMIT/OFFSET 从简与护栏——政策/Job 日志页码化（REQ-20260925-06 / M9）

- 状态：已接受（2026-09-22，M9 列表分页组件化）
- 日期：2026-09-22
- 决策人：架构设计师（深分页数据为 2026-09-22 本机 sqlite3 CLI 对生产库只读实测；依据见[技术方案-列表分页与查询条件](/docs/02-设计/技术方案-列表分页与查询条件.md) §3）
- 补充：主方案 §4.4「分页：游标分页防深分页（方案 05）」——本批不推翻游标模式，页码模式与其并存

## 📌 背景

REQ-20260925-06（M9）要求政策时事、Job 执行日志两检索/审计型列表由「加载更多」（游标）改标准页码分页组件（跳页/每页条数/总数），携带 Job 状态筛选与政策关键词搜索；信息流保留无限滚动、订阅页维持现状。待裁决核心：页码模式接口形态（双模式 vs 独立端点）、`total` 返回与深分页成本（`job_execution_log` 为增长型大表）、越界页语义、参数校验方式。现状：两接口均 `ORDER BY id DESC` 游标分页（id 自增主键全局唯一，天然全序）、响应无 total、`policy_item` 14 行 / `job_execution_log` 12,385 行（2026-09-22 实测）。

## 🎯 决策

### 1. 同端点双模式：`page` 参数出现即页码模式，游标模式字节级不动

- `GET /api/v1/policies?days=&industry=&keyword=&page=&size=` / `GET /api/v1/job-logs?jobName=&status=&page=&size=`——`page` 缺席走既有游标路径（零改动），出现则返回 `{列表(字段同游标模式), total, page, size}` 新 record（`PolicyPagedView`/`JobLogPagedView`，不与 `nextCursor` 混装）。
- 校验规则（接口层 `PageQuery` 共用件单点）：`page≥1`（上限 1,000,000 防 offset 溢出）；`size` 缺省 20、1~50，**超限 400 拒绝**（不截断——契约确定、前端选择器仅 10/20/50 不会触发）；`page×cursor` 互斥 400；页码专属参数（size/keyword/status）缺 `page` 400（`2001 PARAM_INVALID`）。
- 非破坏性变更（纯新增可选参数、响应形态由参数显式选择），不升 `/v2`。

### 2. 越界页 = 200 + 空列表 + 如实回显 page/size/total

offset 语义天然如此、实现零分支；「收敛末页」被否（多一跳且回显 page 与请求不符，契约失真）；「400」被否（浏览期间数据收缩是常态非调用方错误）。配套前端约定：改筛选必回第 1 页；响应空列表且 total>0 时前端检测 `page > ceil(total/size)` 自动回第 1 页重拉（承接 PRD「不出现空白页」）。

### 3. 深分页从简：LIMIT/OFFSET + 精确 COUNT，护栏双阈值留档

2026-09-22 实测（12,385 行）：全表 COUNT 0.57ms、status 过滤 COUNT 1.1ms、最深页 `OFFSET 12000` 0.13ms、组合过滤深页 `OFFSET 5000` 0.25ms——毫秒/亚毫秒级，keyset 混合无收益。护栏（触发即走变更控制）：`job_execution_log > 50 万行` 或页码列表接口 `P95 > 100ms`（debug 耗时日志观测）→ 优先落地 backlog「job_execution_log 清理」（保留 N 天，治本），清理不可行再议 keyset 混合/近似 total（需新 ADR）。

### 4. 其余裁定

- 排序保持 `ORDER BY id DESC`：主键唯一即全序，同参数页序确定，无需补唯一列；页码与游标两模式同序同过滤（同一 wrapper 组装），可互相对照回归。
- Job 状态筛选：等值 `eq(status, 持久化名)`，**不建索引**（3 值低基数选择性差，全扫实测毫秒级）；非法值显式转 400（2001）。
- 政策关键词：`title/summary LIKE %kw%` 参数绑定 + 手工转义 `\ % _` + `ESCAPE '\'`（MyBatis-Plus `like()` 不转义）；trim 后长度 2~64（1 字符 400 防单字全表模糊）；大小写口径 = SQLite 内置行为（ASCII 不敏感、中文原样），PRD 主场景中文关键词一致。
- 不加列表缓存（组合键空间×单人量级收益倒挂）、零 DDL（无回滚脚本义务）。

## ⚖️ 被否方案与理由

| 被否方案 | 理由 |
| --- | --- |
| 独立端点 `/policies/page`、`/job-logs/page` | 查询方式编码进路径（类动词化），同资源两 URI 两套过滤语义；端点/文档/测试面翻倍；双模式参数级实现可随时再拆，可逆性好 |
| 升 `/api/v2` | 非破坏性变更（可选参数 + 显式选择的响应形态），不满足升版门槛 |
| size 超限截断至 50 | 静默截断制造契约歧义（前端传 100 回 50 条但 size 回显多少？）；400 显式拒绝可测可防 |
| 越界页收敛到末页 / 400 | 见决策 2（多一跳 + 回显失真 / 把常态当错误） |
| keyset 混合实现页码跳页 | 页码跳页 = 随机访问，keyset 只能顺序前进；需服务端累积游标或多次请求；当前量级毫秒级无收益（实测） |
| 近似 total（count 截断上限） | 审计场景要「共多少条」精确感知与「第 x/y 页」不失真；精确 COUNT 毫秒级无必要省 |
| status 建索引 | 低基数索引 SQLite 优化器大概率弃用；实测 FAILED 过滤深页 0.25ms |
| 关键词上 FTS5 | 时间窗先收窄（窗内百级），LIKE 实测毫秒级；FTS 触发器/影子表/中文分词复杂度与量级不匹配 |
| 列表结果缓存（方案 04） | days×industry×keyword×page×size 键空间大，单人毫秒级查询收益趋零 |
| 排序补唯一列（如 id DESC, created_at DESC） | id 主键本身唯一，单键即全序；补列是无效复杂度 |

## 💡 后果

- 政策/Job 日志两页获得页码分页（跳页/每页条数/总数）+ 筛选组合能力；`Pagination` 通用组件沉淀供后续列表页（订阅页 Could 留口）复用。
- 游标消费方零感知：信息流/订阅页不动，两接口游标路径零改动；前端删除两页旧游标 api 函数（已核实无其他消费方）。
- 净增 `PageQuery`/`PolicyPagedView`/`JobLogPagedView`/两 Filter record/`Pagination.tsx`，改造两 Controller/两 Service/两 Repository 端口与实现/两页面；任务 T60~T66 合计 9 人天（Must ≈7.5）。
- 已知限制：浏览期间新写入导致的页界漂移与 count/页数据微错位（两 SQL 非同快照）接受（PRD 非功能裁决 + SQLite 单写者间隙极小）；`job_execution_log` 增长最终触发护栏时需先做清理。
