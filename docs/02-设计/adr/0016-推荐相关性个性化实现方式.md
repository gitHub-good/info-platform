# ADR-0016：推荐相关性个性化实现方式（T29）——阅读留痕表 + 指数衰减评分 + 提示词 v1.1 随迁移播种

- 状态：已接受（2026-09-22，T29）
- 日期：2026-09-22
- 决策人：开发工程师（依任务表 T29 + PRD 场景 2「推荐内容与用户订阅主题/已读标的相关性命中率 ≥70%（抽样人工标注）」+ 技术方案 §4.1.6）
- 补充：ADR-0005（缓存与限频）、Spike-2 §7.4（每日推荐模板）与 §11.5；T23（每日推荐排序）/ T27（信息流命中引擎）实现

## 📌 背景

任务表 T29 要求把每日推荐从「订阅主题/自选标的静态上下文」升级为「含用户历史阅读行为的个性化相关性排序」，命中率 ≥70%（抽样人工标注口径）。实现前盘点 T23/T27 现状：

- **T23 上下文装配的 `subscribedThemes` 是「暂无」桩**：`DailyRecommendationContextBuilder.formatThemes` 自 T26 订阅落地后从未接入真实 `subscription_config`，LLM 拿不到任何订阅信号。
- **全系统无阅读行为数据**：无表、无埋点、无画像——PRD 场景 2 的「已读标的」无从谈起，是本任务核心缺口。
- **规则兜底理由只有活跃度文本**（涨跌幅/公告/新闻计数），标注员无法判定「是否命中订阅主题/已读标的」，≥70% 无法验证。
- **前端 `BriefContent` 类型没有 `topRecommend` 字段**：briefType=4 的推荐结果在 AI 简报页不可见。

## 🎯 决策

**四件套落地，推荐接口既有契约零变更（响应仅增量字段）：**

1. **独立追加型留痕表 `reading_event`（V14/U14）**：`user_id/subject_id(可空)/content_type(SUBJECT_DETAIL|POLICY|AI_BRIEF)/content_ref/created_at`。写入方为 `POST /api/v1/reading-events`（前端三页面静默埋点，fire-and-forget）；**幂等友好 = 服务层 1 小时窗口去重**（同 user+type+ref 窗口内重复返回 `recorded=false`，不报错不落重复行），前端再叠会话级 once 守卫——双层防 React StrictMode 双触发与前端重试；窗口外重复阅读照常留痕（次数是热度输入）。无 UNIQUE 约束（去重走查询预检），个人量级竞态兜底为偶发重复行（无害，画像按事件衰减求和，多一行权重≈+1）。
2. **相关性评分 = 活跃度 + 订阅命中 + 已读热度（指数时间衰减）**：`relevanceScore = activityScore（既有 |涨跌幅|+公告×2+新闻） + 标的订阅命中 6.0 + 订阅主题命中 4.0（行业/名称/代码 contains 任一主题词） + 已读热度加分 ≤10.0`。已读热度 = `Σ 0.5^(距今天数/7)`（半衰期 7 天：一周前阅读权重减半、一个月前 ≈0.05），热度 3.0（约 3 次近期阅读）即拿满 10 分——饱和防单一标的垄断。规则兜底排序从活跃度切换为该综合分；**空画像（新用户）退化为既有活跃度排序，行为不变**。画像装配失败整体降级为空画像（WARN 不上抛），个性化是增强信号，不拖垮推荐主链路。
3. **每日推荐提示词 v1.1 随 V14 播种**：v1.0 置废、v1.1 启用（版本迭代机制本就是 V8 既定约定「编辑即新版本行」）。v1.1 新增三个占位符 `{{subscribedSubjects}}`/`{{readingProfile}}`（既有 `{{subscribedThemes}}` 从「暂无」桩修复为真实订阅主题词），system/user 段明确「排序优先考虑与订阅主题、订阅标的、已读标的相关性」且「理由须点明命中的个性化因素」。模板变更耦合进 V14 迁移（而非单独数据脚本），保证表结构与提示词版本一次回滚一致。
4. **推荐理由即人工标注载体**：兜底路径理由逐因子列明（如「个性化相关：已读热度+6.7；标的订阅+6.0；命中主题「半导体」+4.0；信息面活跃：涨跌幅1.2%，公告2条，新闻5条；综合分20.9」），随 `ai_brief.content.topRecommend[].reason` 持久化；前端 AI 简报页新增「每日推荐 Top5」分区渲染 No./标的/理由——标注员按「是否命中订阅主题/订阅标的/已读标的」逐条判定即可执行抽样。

## ⚖️ 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| reading_event 追加流水 + 查询期聚合画像 | 无状态写入；画像窗口/衰减可随时调整；对齐 llm_call_log 模式 | 每次推荐多一次窗口查询（个人量级毫秒级） | ✅ 采用 |
| 画像预聚合表（user_subject_profile 定时汇总） | 查询零聚合 | 写放大 + 双表一致性 + 定时任务；30 天窗口个人量级无必要（YAGNI） | ❌ 否决 |
| 去重靠 DB UNIQUE(user,type,ref,date) | 强一致 | 一天内多次真实阅读只记一次，热度失真；冲突路径复杂 | ❌ 否决（1h 窗口查询去重） |
| 评分权重交给 LLM（prompt 里给画像让模型自行加权） | 免维护公式 | LLM 路径失败/超时时兜底无个性化；权重不可解释、标注口径漂移 | ❌ 否决（规则分可解释 + LLM 用同一画像） |
| 前端新建独立推荐页展示理由 | 展示专属 | 信息流/推荐页本身不在 T29 范围；AI 简报页已可承载 briefType=4 结果 | ❌ 否决（复用 BriefContentCard 增分区） |

## 💡 理由

命中率 ≥70% 的验收口径是「抽样人工标注」，第一性需求是**可判定**而非精确的最优化：理由里逐因子写明命中了哪个主题词、哪个订阅/已读标的、各加多少分，标注从「猜模型意图」变成「核对事实陈述」。规则分与 LLM 用同一份画像（Personalizer 单一来源），两条路径口径一致；权重（6.0/4.0/10.0）为具名常量，标注发现系统性偏差时改一处常量即可调参。指数半衰期 7 天是「近期兴趣优先、陈旧兴趣淡出」的最简单可解释实现，无需拟合。提示词随迁移播种保证「表 + 模板」原子演进，回滚 U14 同时回到 v1.0 行为。

对照选型五维度：成熟度（追加流水 + contains 匹配 + 指数衰减，全部常规手段）、社区（零新依赖）、学习成本（一张表一个纯函数评分器）、可替换性（评分器无状态，未来换 TF-IDF/向量相似度只换 `RecommendationRelevanceScorer` 实现）、运维成本（无定时任务、无新组件）。

## ⚠️ 影响

- 正面影响：PRD 场景 2 数据链路闭环（阅读→留痕→画像→排序→理由→展示→标注）；`subscribedThemes` 桩修复，LLM 获得真实订阅信号；兜底路径 rank 修复为 1..5（对齐 `DailyRecommendationResult` javadoc，T23 实现 bug）。
- 负面影响 / 代价：埋点接口无读取端点（画像内部消费，运维排查走库表）；主题匹配是 contains 级（同义词/近义主题词不命中，M3+ 可升级语义匹配）；每日推荐幂等键仍为全局单份（T23 已知限制，多用户共享当日简报），个性化画像取的是触发者画像。
- 接口契约影响：新增 `POST /api/v1/reading-events`（200 `{recorded}` / 400 2001），纯新增无破坏；`GET /recommendations/daily` 与 `content.topRecommend[].reason` 字段语义不变（内容增厚）；前端 `BriefContent` 增量加 `topRecommend` 可选字段。
- 数据迁移影响：新增 V14（建 `reading_event` + 双索引 + 每日推荐模板 v1.1 播种与 v1.0 置废）/ U14（回滚表 + 模板版本），Flyway 社区版 U 脚本手动执行（对齐既有惯例）。
