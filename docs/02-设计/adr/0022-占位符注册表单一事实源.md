# ADR-0022：占位符注册表单一事实源——装配器自带描述符 + 注册表聚合 + 同源单测（REQ-20260922-03 / M5）

- 状态：已接受（2026-09-22，M5 设计阶段）
- 日期：2026-09-22
- 决策人：架构设计师（依 REQ-20260922-03 故事 4 场景 3「校验基准与对照区同源」+ 技术方案增补 §3.2/§4.3/§4.5）
- 补充：ADR-0007（DDD 四层，领域层纯净约束）、方案库 03（幂等，不相关；本 ADR 为自研点的取舍记录）

## 📌 背景

4 个 AI 场景的模板占位符（`{{key}}`）实际注入清单分散在三处上下文装配代码（设计前核实）：`BriefContextBuilder`（场景 1/2 共用，17 键）、`PolicyTendencyService.buildContext`（场景 3，7 键，私有静态）、`DailyRecommendationContextBuilder.toContext`（场景 4，6 键）。M5 需要两个新消费方：

1. **编辑器对照区**（T46 只读接口）：该场景能写哪些键、各自注入什么；
2. **保存校验 V5**（T45）：新版模板出现注册表之外的占位符 → 警告级提示（不拦截，计入 warnings 回显，对齐 PRD"仅警告"与 UI 方案 D7）。

PRD 明确要求二者口径一致（故事 4 场景 3）。若注册表是一份独立维护的硬编码清单（比如常量类或数据库表），三个装配器日后加键/删键时注册表不知——**两份清单必然漂移**，且漂移直接造成"校验误报 unknown"或"对照区展示永远注入不了的键"。

## 🎯 决策

**清单登记在装配器自己身上，注册表只做聚合，防漂移靠同源单测：**

1. `domain/ai/PlaceholderDescriptor`（record `key + description`，纯 JDK）。
2. 每个装配器新增 `providedPlaceholders()`（实现 `application/ai/PlaceholderProvider` 接口；Policy 侧为 public static 方法，**不拆 buildContext 类结构**）：描述符常量与 `ctx.put` 调用**同文件同序**维护——改键必须触碰同一文件，评审自然可见。
3. `application/ai/PromptPlaceholderRegistry`（@Service）注入 `List<PlaceholderProvider>` 聚合为 `Map<BriefType, List<PlaceholderDescriptor>>`；只读接口（`GET /api/v1/prompt-placeholders`）与校验器 V5 **注入同一 Registry 实例**——"对照区"与"校验基准"物理上是一份数据。
4. **同源单测闸门**：代表性满样本输入下断言 `build()` / `toContext()` / `buildContext()` 的输出 keySet == `providedPlaceholders()` keySet；构造器加键漏登记 → 测试红。

对生成链路为**纯增量**（只加方法，既有装配路径一行不动），对齐 PM"生成链路零改动"卖点。

## ⚖️ 候选方案对比

| 方案 | 漂移风险 | 结论 |
| --- | --- | --- |
| A 独立注册表硬编码第二份清单（常量类/DB 字典表） | 高：与 `ctx.put` 无绑定，无机械机制提醒同步 | ❌ 否决 |
| B 运行时推导（调真实 build() 收集 keySet） | 推导结果不稳定：`BriefContextBuilder` 在 subject 为 null 时少 3 键、每日推荐侧需 mock 五个仓储依赖才能跑通；且描述文案无处安放 | ❌ 否决 |
| C 装配器自带描述符 + 聚合 + 同源单测（本决策） | 低：同文件维护 + 单测机械闸门；描述文案与键同址 | ✅ 采用 |

（五维度：C 全维不劣——零新依赖、零 DDL、纯 JDK 类型可单测、可替换性满分；A 的"集中一处好看"不构成架构优势，分散的事实源本就该由拥有事实的类自述。）

## 💡 理由

单一事实源的本质不是"清单放在一个文件"，而是"**改一处必须牵动另一处**"。C 用两条绳索绑住同步：代码组织上描述符紧邻 `ctx.put`（改键者必然看到），验证上同源断言把"漏登记"从潜伏问题变成红灯。B 看似最"自动"，但占位符集合是数据依赖的（subject 为 null、画像为空时键集缩水），运行时推导要么注入复杂样本要么结果残缺，还丢失"一句话用途说明"这一 PRD 明确要求的字段——自动化的收益抵不过语义损失。

## ⚠️ 影响

- 正面：对照区与校验基准同源由结构保证（同一 Registry bean）；场景 2 休眠现状（事件类占位符无注入来源）被如实暴露为 unknown 警告而非被清单掩盖；未来新场景（走变更控制）只需实现 Provider 即自动进对照区与校验。
- 负面 / 代价：三装配器各加一段描述符常量（约 30 行/处）；`PolicyTendencyService.buildContext` 需提升为包内可见供同源测试（无行为变化）。
- 接口契约影响：新增只读端点 `GET /api/v1/prompt-placeholders`（含 `dormant`/`note` 字段披露场景 2 休眠）。
- 需要跟进：T45 校验器 V5 以 Registry 为构造依赖（软依赖 T46 先行，任务表已校准）。

## 🔍 后续验证方式

- 同源单测：三装配器 keySet 断言（防漂移闸门，进主干测试基线）。
- 契约测试：注册表端点返回 4 场景 17/17/7/6 键（场景 1 与 2 共用 BriefContextBuilder 清单）。
- 回归：三装配器既有单测全绿（纯增量改动零行为变化）。
