## 🎯 1. 背景与目标

### 背景（设计前代码核实结论）

| 复用点 | 核实结果 | 本批复用方式 |
| --- | --- | --- |
| ManagedJob 收编（6 个既有 Job） | 实现接口注册为无条件 bean 即收编：任务中心可视 / 手动触发（202+executionId）/ 启停热切换；jobKey 冲突启动期 fail-fast（`JobRegistry`） | `RetentionCleanupJob implements ManagedJob`，第 7 个，调度中心零改动 |
| runtime_config 配置体系 | 单表 key-value + 域前缀键（`llm.` / `datasource.` / `job.` / `aggregation.`）；校验器按 `supports(key)` 路由（未知键 2001）；种子 seed-if-absent DB 为权威；消费点用时读取即热生效 | 新增 `retention.` 域前缀一键（§3.1） |
| job_execution_log 留痕通道 | `JobExecutor` 每 jobKey CAS 守卫 + `Recorder.start/success/failed` 显式驱动；`success` 恒记 `(0,0)` 且 `markSuccess` 将 error_message 置 null；`JobLogView` 暴露 processedCount/errorCount/errorMessage，Job 日志页已渲染 | 通道最小扩展：可选接口上报计数 + SUCCESS 行明细（§3.2 / §4.4） |
| 四表时间列 | 均存整秒 ISO-8601 UTC 文本，字典序即时间序；索引：`job_execution_log` 有 `idx_job_log_time(created_at)`（V15）、`llm_call_log` 有 `idx_llm_call_log_created(created_at)`；`data_source_event` / `reading_event` 的 created_at 仅在复合索引右侧 | 删除谓词统一 `created_at < cutoff`（字符串比较）；不补索引（量级不值，§5） |
| JdbcTemplate 先例 | `SubjectRepositoryImpl` 批量 upsert / 计数 UPDATE 已用 JdbcTemplate（MyBatis-Plus 无对应能力的场景惯例） | 删除端口实现走 JdbcTemplate（§3.3） |

### 目标（对齐 PRD，可量化）

- 四表按各自窗口（默认 30/14/90/90 天，下限 7/2/35/35）每日清理一次 + 手动触发，`created_at` **严格早于** now−窗口 的行删除、窗口内行全数保留。
- 窗口经 runtime_config 可配、保存即热生效（下一轮清理按新窗口）；非法值保存拒绝（2001 字段级）、执行期读到缺失/非法值回退代码内置默认——「设 0 清空」两层防御下不可达。
- 每轮清理留痕：SUCCESS 行 `processed_count` = 四表删除合计 + 逐表明细可读（§3.2 载体）；任务中心可见可启停，Job 日志页可筛。
- 业务口径零影响：概览 24h / 数据源徽章 / 成本 30d / 画像 30 天 / Job 日志页（T74 回归红线）。

### 验收红线逐条对齐

| PRD 红线 | 方案落点 |
| --- | --- |
| 四表独立窗口判定、严格早于边界（场景 1/2） | 逐表 cutoff = now − 窗口，**整秒截断**后字符串比较 `created_at < ?`——两侧同为整秒 ISO-8601 格式，字典序=时间序，相等即保留（契约 §4.3 注明，按契约断言） |
| 空轮 SUCCESS processed=0（场景 3） | 删除数合计 0 照记 SUCCESS（通道既有语义） |
| 手动触发同通道共守卫（场景 4） | ManagedJob 收编天然获得（JobExecutor 唯一执行通道） |
| 首轮 1.6 万行收敛不阻塞页面（场景 5） | 每批 500 行独立事务循环删（§3.4），32 批亚秒~秒级；WAL 读写不互斥 |
| 白名单只动四表（场景 6） | 表名收 `RetentionLogTable` 枚举（编译期常量），方法签名不收字符串（§3.3） |
| 误配两道防御（故事 2 场景 3/4） | 保存：`RetentionConfigValidator` 逐字段 ≥ 表下限整型，PARAM_INVALID 原值保留；执行：`RetentionWindows` 字段级缺省/非法回退默认（§4.2） |
| 留痕合计 + 逐表明细可读（故事 3 场景 1） | processed_count=合计 + SUCCESS 行 error_message 复用为「留痕明细」（§3.2，ADR-0036） |
| 单轮失败不停摆（故事 3 场景 4） | 单表失败 catch 续跑其余表，轮末有失败才汇总抛出 → FAILED + error_message（§4.5） |

### 非目标（防范围蔓延）

- push_record / 业务表（ai_brief / policy_item / anomaly_event / subject / prompt_template 等）不纳入（REQ Won't 裁决）。
- 软删 / 回收站 / 删除前导出归档 / 独立指标端点 / 留痕趋势视图（Could）不做。
- 不为 data_source_event / reading_event 补 created_at 单列索引（稳态量级毫秒级全扫，§5）。
- 清理轮自身留痕行不豁免不特判（受同一 30 天窗口治理，自恰）。

## ⚖️ 3. 形态决策（PM 交接清单五项，裁决与被否方案）

### 3.1 retention 键空间：**独立 `retention.global` 域文档**（调度键 `job.RETENTION_CLEANUP` 并列另立）

两键分工：`job.RETENTION_CLEANUP` 只装调度语义（enabled / scheduleType=CRON / cron），入 `JobRuntimeConfigSeeder` 第 7 键；窗口天数装 `retention.global` 单文档四字段。

**理由**：① `job.{KEY}` 文档由通用 `JobRuntimeConfigValidator` + `JobScheduleSettings` 六键一套规则消费，并入窗口字段须在校验器 / 种子 / 任务中心视图三处为单键开特例分支（每表下限不同的整型 vs 通用 cron/interval 规则），通用框架被单 Job 污染；② 调度参数与数据治理参数变更节奏与消费方不同——JobScheduler 只订阅 `job.*` 键变更重注册，retention.global 每轮现读，改窗口不会触发调度取消/重注册瞬间；③ 键空间惯例对齐（`llm.global` / `datasource.{CODE}` / `aggregation.global` 均域前缀独立键）；④ 先例固化风险：并入 job 文档会诱导后续每个 Job 把业务参数塞进调度文档。

| 被否 | 理由 |
| --- | --- |
| 并入 `job.RETENTION_CLEANUP` 文档 | 上述①②④；且 PATCH /jobs/{jobKey} 契约被混入非调度字段，语义失真 |
| 每表一键（retention.job_execution_log …四键） | 四字段恒同读同写（一轮全用、一页全编辑），拆四键徒增键数与部分写中间态 |

### 3.2 逐表明细留痕载体：**SUCCESS 行 `error_message` 复用为「留痕明细」**（零 DDL）+ 每轮 INFO 单行摘要

- 现有字段盘点：job_execution_log 可承载位仅 `processed_count`（int，合适——记合计）/ `error_count`（失败行数语义，不用）/ `error_message`（TEXT，SUCCESS 行恒 NULL——`markSuccess` 显式置 null，是被 PM 点名的首选项）。
- **裁定**：`processed_count` = 四表删除合计；SUCCESS 行 `error_message` 写固定格式明细 `job_execution_log=15230; data_source_event=0; llm_call_log=0; reading_event=0`（段序=枚举序，全表恒四段）。`JobLogView` / Job 日志页已渲染 errorMessage（truncate + title），**页面即读**——「复用既有留痕表与页面」字面满足。每轮另发一条 INFO 摘要日志（运维侧留档，含窗口与耗时）。
- **语义约定（记入契约与 ADR-0036）**：error_message 列语义由「FAILED 异常摘要」扩展为「终态附加信息」——FAILED = 异常摘要（不变）；SUCCESS = 留痕明细（仅计数型 Job 使用）。T73 可顺带将 Job 日志页列头文案「异常信息」调整为「明细 / 异常」（一句话改动，UI 裁量，非必须）。
- 通道扩展（最小）：`JobExecutionLog.markSuccess` / `JobExecutionRecorder.success` 各增带 detail 参数的重载（原签名不动、语义不变）；`JobExecutor` 成功路径按新可选接口 `JobRunStats` 读取 (processed, detail)——**六个既有 Job 不实现该接口，行为字节级不变（0,0,null）**。

| 被否 | 理由 |
| --- | --- |
| 新增 `detail` 列（V19/U19 DDL） | 语义最干净，但为 1/7 Job 的明细加列：迁移 + 实体 + 视图 + 前端列全链路改动，与「轻量批 + 零 DDL 优先」倒挂；PM 已首选项点名 error_message |
| 仅 INFO 日志记明细（不加任何字段） | 「逐表可读」只剩日志文件一途，Job 日志页 SUCCESS 行明细细读不到，故事 3 场景 1 验收面弱化 |

### 3.3 删除端口：**枚举白名单 + 单端口 + JdbcTemplate 子查询分批**

- `domain/retention/RetentionLogTable` 枚举 = 白名单**单一事实源**：四项各携 `physicalName`（物理表名常量）/ `minDays`（下限）/ `defaultDays`（缺省窗口）/ `jsonField`（配置字段名）。
- `domain/retention/ExpiredLogDeleter` 端口：`long deleteExpiredBefore(RetentionLogTable table, Instant cutoff, int limit)` 返回本批实际删除行数。**签名收枚举不收字符串**——业务表名无从传入；实现里表名取自枚举常量（编译期定死）拼接 SQL 骨架，cutoff/limit 一律 `?` 参数绑定，无注入面。
- 实现 `infrastructure/retention/ExpiredLogDeleterImpl` 用 JdbcTemplate（`SubjectRepositoryImpl` 先例）：`DELETE FROM {t} WHERE id IN (SELECT id FROM {t} WHERE created_at < ? LIMIT ?)`——SQLite 默认构建未开 `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`，`DELETE … LIMIT` 不可用，子查询形态可移植且内层可走 created_at 索引。
- 不改四表现有仓储端口：删除是横切生命周期关注点，集中一处可审计；四端口保持域内读写职责。

| 被否 | 理由 |
| --- | --- |
| 四仓储端口各扩 deleteExpiredBefore | 删除逻辑散四处、白名单失去单点；四份近似 SQL 难审计 |
| MyBatis `${}` 动态表名 Mapper | 与 JdbcTemplate 等价但引入字符串拼接模板面，枚举 + JdbcTemplate 更直白 |

### 3.4 删除批大小：**每批 500 行、批间独立事务、循环删至返回 < 500**

- SQLite WAL 单写者：500 行/批的 DELETE 毫秒级提交，写锁持有窗口短，业务写（ANOMALY_DETECT 10s 轮询留痕等）在 busy_timeout=5000 内排队无感；页面查询走 WAL 快照不被阻塞（故事 5 红线）。
- 首轮 15,987 行 ≈ 32 批，整轮亚秒~秒级；稳态日增 ~3.7k 行 ≈ 8 批/日。
- 批大小为代码常量（`RetentionPolicy.BATCH_SIZE=500`），**不入配置键**——执行细节非运维参数，避免配置面蔓延。

### 3.5 CRON 时刻与页面载体

- **CRON `0 30 3 * * ?`（每日 03:30）**：避开 06:00 标的池同步（开市前任务）与 09:00 每日推荐、09:30 开市后查询高峰，取凌晨低峰；FIXED_DELAY 轮询 Job 全天运行无法避开亦无需避开（毫秒级批 + WAL）。种子 `enabled=true`（首启默认启用，首轮即收敛存量）；CRON 型任务测试隔离天然友好（03:30 不会在测试生命周期内到来，需要时以 `retention.cleanup.enabled=false` 属性关闭，对齐六 Job 惯例）。
- **页面载体（Should）：任务中心 RETENTION_CLEANUP 行「编辑调度」Dialog 扩展四窗口字段**。理由：①窗口的操作心智挂在「这个清理任务」上，任务中心看到即可就地调，上下文连续；②数据源配置页聚合 7 源健康与路由语义，塞跨表清理参数破坏页面域；③`ScheduleEditDialog` 已有按 jobKey 条件渲染先例（userIds 仅 DAILY_RECOMMEND 显示），扩展一个条件分组（四数字输入 + 下限校验 + 含义文案）改动量 ≈1 人天，不需降级。保存时两次 PATCH 分域提交（cron 走既有 PATCH /jobs/{jobKey}，窗口走新 PATCH /api/v1/retention/windows），字段分组展示、错误就地渲染。**降级出口**：若前端排期紧张，Must 不受影响——接口通道（§4.3）已可完整调窗，页面延后一版不阻塞验收。

### 4.2 窗口读取与两道防御

- **保存侧**：`application/retention/RetentionConfigValidator implements RuntimeConfigValidator`（supports `retention.global`）。表驱动：按枚举遍历四字段，缺失 / 非整型 / `< minDays` → 收集字段级原因，抛 2001 PARAM_INVALID（多条 "; " 连接，对齐 `JobRuntimeConfigValidator` 惯例）；DB 原值保留继续生效。未知多余字段不拒绝（读侧忽略，与 job 域惯例一致）。
- **执行侧**：`application/retention/RetentionWindows`（record，四 int）+ `resolve(JsonNode doc)` 静态工厂——**每轮现读** `ConfigCenter.document("retention.global")`（键缺失 → 全默认）；逐字段独立解析：字段存在且为整型且 ≥ minDays → 采信，否则**回退该表 defaultDays**（字段级回退：一个字段被绕过校验写坏，其余好字段不受牵连）。「DB 无配置 = 用默认，不是全删」。
- 热生效：窗口读取在每轮 `run()` 内现读（用时读取即热，不依赖事件）；改大窗口不复活已删行（REQ 裁决，自然满足）。

```json
  "data": {
    "windows": { "jobExecutionLogDays": 30, "dataSourceEventDays": 14,
                 "llmCallLogDays": 90, "readingEventDays": 90 },
    "limits":  { "jobExecutionLogDays": {"min": 7, "default": 30},
                 "dataSourceEventDays": {"min": 2, "default": 14},
                 "llmCallLogDays": {"min": 35, "default": 90},
                 "readingEventDays": {"min": 35, "default": 90} },
    "updatedAt": "2026-09-22T01:00:00Z" } }
```
- PATCH body：`{ "jobExecutionLogDays": 7, "dataSourceEventDays": 14, "llmCallLogDays": 90, "readingEventDays": 90, "expectedUpdatedAt": "…" }`（四字段必填全量；expectedUpdatedAt 不符 → 30065；非法值 → 2001 字段级 msg，原值保留）。含义文案（「任务执行日志 · 保留最近 N 天」等）由前端静态维护，口径交 UI（REQ 场景 5）。
- 幂等：PATCH 全量替换，同 body 重复提交结果一致（方案 03 天然满足）。

### 4.4 留痕通道扩展（可选接口，非破坏性）

```java
// application/jobrun/JobRunStats（新增可选接口）
public interface JobRunStats {
    /** 本轮处理条数（JobExecutor 在 run() 正常返回后读取，写入 SUCCESS 留痕）。 */
    int lastProcessedCount();
    /** 本轮留痕明细（null = 无明细，error_message 保持 NULL）。 */
    String lastRunDetail();
}
```

- `JobExecutionLog.markSuccess(Instant, int, int, String detail)` 重载（原三参方法委托 `detail=null`，既有语义不变）；`JobExecutionRecorder.success(entry, processed, error, detail)` 重载同理。
- `JobExecutor.runGuarded` 成功路径：`job instanceof JobRunStats s ? s.lastProcessedCount() : 0`（detail 同理）——六个既有 Job 零感知。FAILED 路径不动（`failed(started, ex.toString(), 0, 0)`）。
- 并发安全：JobExecutor 每 jobKey CAS 守卫保证同 Job 串行，JobRunStats 实现用普通字段即可（轮首重置）。

### 4.5 RETENTION_CLEANUP 执行流（`application/retention`）

```java
RetentionCleanupService.runOnce():
  windows = RetentionWindows.resolve(configCenter.document("retention.global"))   // 每轮现读
  for table in RetentionLogTable.values():            // 枚举序固定，明细段序由此确定
    try:
      cutoff = clock.instant().minusDays(windows.of(table)).truncatedTo(SECONDS)   // 整秒截断
      do { deleted = deleter.deleteExpiredBefore(table, cutoff, 500); total += deleted }
      while (deleted == 500)                          // 循环删至无过期行，每批独立事务
      counts[table] = total
    catch (ex): failures.add(table.physicalName() + ": " + ex)   // 单表失败不停摆，续跑其余表
  INFO 单行摘要（四表=行数 + 窗口 + 耗时）             // 运维日志留档
  stats = (Σcounts, "job_execution_log=n1; data_source_event=n2; llm_call_log=n3; reading_event=n4")
  if failures 非空: throw RetentionCleanupException(成功表明细 + 失败表原因)   // → FAILED + error_message
```

- `RetentionCleanupJob implements ManagedJob, JobRunStats`：jobKey=`RETENTION_CLEANUP`；jobName 走默认派生（`RetentionCleanupJob`，Job 日志页筛选与任务中心「最近执行」自动联动）；displayName=`留痕数据清理`；description=`按保留窗口清理四张留痕表过期行（任务日志/数据源事件/LLM 调用/阅读行为），窗口可配热生效，误配双重防御`；scheduleType=CRON；`run()` 委托 service。
- 自恰性：本轮自身 STARTED 行 created_at=now，永不落删除界内，无需豁免；STARTED 悬挂行按同窗口清理不特判（REQ 非功能裁决）。
- 判定列：job_execution_log 用 `created_at`（`idx_job_log_time` 在列，与 start_time 同刻写入语义等价——`countSince` 先例）；其余三表 created_at 为唯一时间列。

## 🛡️ 5. 非功能设计（逐项过）

- **性能**：首轮 15,987 行 = 32 批 × 毫秒级 DELETE，整轮亚秒~秒级，远低于任何超时预算；稳态 ≈8 批/日。`data_source_event` / `reading_event` 无 created_at 单列索引 → 每批内层子查询全表扫（稳态 1.4 万 / 十行级），SQLite 字符串比较毫秒级——**不补索引**（DDL 与收益倒挂，留痕健康视图 Could 再议）。
- **容量**：清理后稳态 job_execution_log ≈11 万行（3.6k×30，距 ADR-0035 50 万护栏 >4 倍）、data_source_event ≈1.4~3 万行、llm_call_log / reading_event 百~十行级——按月抽查行数应稳定在稳态量级，持续增长即缺陷信号（REQ 护栏联动）。
- **安全**：新端点受 JWT（不入白名单）；删除目标表仅枚举四常量可达（无外部字符串入口）；配置值经校验器整型+下限双重把关（保存侧）+ 解析回退（执行侧）。
- **可观测**：SUCCESS 行 processed_count + error_message 明细（页面可读）；每轮 INFO 摘要（窗口/行数/耗时）；FAILED 行 error_message 含成功表计数与失败原因；配置变更走 RuntimeConfigService 既有键级审计日志。
- **降级预案**：单表删除异常 → 续跑其余表，轮末汇总 FAILED（下一轮按调度继续）；配置键整键缺失/损坏 → 全默认窗口执行（绝不全删）；PATCH 写库失败 → 50000，快照不动旧值生效（RuntimeConfigService 既有）；手动触发运行中 → 409/30063（既有守卫）。

## 🧪 6. 测试要点（可测性预留，测试工程师承接）

- **删除端口（T70）**：空删返回 0；窗口内行全保留；`created_at` 恰等于 cutoff 的边界行**保留**（严格早于，按契约断言）；cutoff 带秒以下精度时截断后判定（构造 .123 偏移用例）；批量拆批（>500 行分多批、计数合计准确、循环终止）；白名单——subject / policy_item / anomaly_event / push_record / ai_brief / prompt_template / runtime_config 等业务表行数不变。
- **清理服务与 Job（T71）**：四表独立窗口同时生效（30/14 两窗口交叉用例）；空轮 SUCCESS + processed_count=0 + 明细四段全 0；明细格式断言（表名=行数、段序固定）；热改窗口下一轮按新界（Clock 注入）；配置缺失/绕过写非法值 → 回退默认且不按 0 全删；单表抛错 → 其余表照删、轮末 FAILED、error_message 含两侧信息；下一轮正常继续。
- **配置与接口（T72）**：四字段非法矩阵（0/负数/非整数/低于下限/缺失 → 2001 字段级，原值保留）；expectedUpdatedAt 不符 → 30065；合法保存后 GET 回读一致；种子 seed-if-absent 幂等（DB 已有键不动）。
- **通道扩展回归（T71）**：六个既有 Job SUCCESS 行仍 (0,0) 且 error_message 为 NULL（通道非破坏性锚点）。
- **四链路回归 + 收敛演练（T74）**：概览 24h（windowRuns/windowFailed/徽章 errors24h/最近一条）清理前后一致；成本报表 30d 数字不变；推荐画像 30 天内容同口径；Job 日志页 30 天内记录/排序/筛选不变、仅窗口外总数下降；真实库首轮手动触发收敛演练（期间页面可用）+ 1356 基线只增不减。
