> 把分散的多源金融信息收敛为统一详情视图 + AI 结构化简报 + 实时异动/事件推送 + 政策时事聚合 + 个性化订阅的轻量级单体平台；先底座后 AI，技术未决项先 Spike 不阻塞主方案。

## 🎯 1. 背景与目标

### 背景

用户环境已有点状的行情、财务、估值、公告、新闻、事件监控、自选 watchlist 等能力，但分散在不同入口、代码体系不一、限频不一，未形成决策闭环。人工拼接一只标的的完整观点需多次跳转；重大公告/异动靠人工巡检常滞后；政策面散落在新闻流中无聚合；全量推送噪声大。

### 目标（对齐 PRD，可量化）

- 信息聚合：接入 6 类数据源（行情/财务/估值/公告/新闻/政策事件），统一详情视图，单源缺失降级不阻断。
- AI 分析：自选标的与重大事件生成结构化简报，事实回链率 100%，关键数值幻觉校验覆盖。
- 实时动态：异动推送 ≤15s，事件推送 ≤30s。
- 政策时事：政策与时事专题流，标注关联行业与倾向性判断。
- 个性化订阅：主题/标的/事件类型订阅，每日推荐相关性命中率 ≥70%（抽样标注）。
- 标的覆盖：首期股票（A 股/港股）/指数/板块；预留基金/债券扩展接口。

### 非目标（防范围蔓延）

- 不做自动下单/交易执行、回测/量化、组合级深度 P&L 归因、社交社区。
- 不自建数据爬虫（首期复用现成 API/RSS，爬虫单列合规 Spike）。
- 不实现基金/债券/衍生品标的类型（仅预留接口）。

## 🗺️ 2. 方案总览

### C4 · Context（系统上下文，7 元素）

```
            ┌──────────────┐
            │ 个人投资者    │ 主用户
            │ (浏览器 SPA)  │
            └──────┬───────┘
                   │ HTTPS / SSE
            ┌──────▼───────────────────┐
            │ 信息整合与 AI 分析平台    │
            │ (本系统)                 │
            └──┬──┬──┬──┬──┬───────────┘
               │  │  │  │
   行情/财务/估值 公告 新闻 政策源      LLM 服务
   (现成 API)   (API)(API)(RSS/API)  (外部厂商)
```

核心思路（外行能懂）：一个后端服务把行情、财务、公告、新闻、政策等多源数据通过统一适配层"翻译"成同一套标的视角；前端一个详情页分区展示，任一源挂了就显示"暂无数据"而不阻断其他分区；AI 用大模型把聚合信息压成结构化简报并回链原文、回查数值防幻觉；自选清单的异动和重大事件通过定时轮询 + 事件驱动经 SSE 实时推给浏览器。

### C4 · Container（容器，8 元素）

```
┌─────────────────────────────────────────────────────────────┐
│ 浏览器 SPA : React18 + TS + shadcn/ui                       │
│   ├ 详情聚合页  ├ watchlist 管理页  ├ 政策时事页          │
│   ├ AI 简报页   ├ 个人信息流/订阅页                        │
└────────────────────────┬────────────────────────────────────┘
                         │ REST /api/v1/* + SSE
┌────────────────────────▼────────────────────────────────────┐
│ 后端单体 : Java21 + Spring Boot 3 (java -jar 单包)         │
│ 模块化单体(ADR-0001) + 内部 DDD 四层(ADR-0007):           │
│   接口层     Controller / 参数校验 / 鉴权 / 协议转换       │
│   应用层     Service 用例编排 / 事务边界 / 发领域事件      │  依赖只能向下
│   领域层     实体/值对象/领域服务/业务规则 (纯净不引框架)  │  领域层定接口
│   基础设施层 Repository 实现 / 中间件 / 适配器 / LLM 厂商  │  基础设施层实现
│   层内按 6 域分包: aggregation ai push policy subscription  │
│   common; 跨域协作走领域事件, 不 import 内部类             │
└──┬───────────────┬──────────────┬──────────┬───────────────┘
   │               │              │          │
 SQLite 3         本地磁盘        LLM 厂商   6 类数据源
 (主库, WAL)      (导出/缓存文件) (多provider) (外部 API/RSS)
```

> 6 业务域落到 DDD 四层的方式见下方；DDD 四层与 ADR-0001 模块化单体不冲突——前者是模块内/层内结构，后者是整体部署形态（详见 ADR-0007）。

**6 业务域在 DDD 四层的落点**（选整体四层、层内按域分包，而非"每域内嵌四层"：对齐 index.md 默认骨架、横切 common 天然落基础设施层、小团队更易导航；单拆某域为服务时抽其各层切片即可，演进缝仍保留）：

- **aggregation**（多源聚合）：接口层 `SubjectDetailController`；应用层 `AggregationService` 编排并行取数 + 降级；领域层 聚合根 `SubjectDetail`、值对象 `SourceResult`/`SectionStatus`；基础设施层 6 个 `SourceAdapter` 实现 + Caffeine。
- **ai**（AI 简报）：接口层 `AIBriefController`；应用层 `AIBriefService` 用例编排 + 发 `AiBriefDoneEvent`；领域层 `Brief` 实体/状态枚举/幻觉校验规则；基础设施层 `LlmGateway` 实现 + 提示词版本表 Repository + 多 LLM 厂商 provider。
- **push**（异动/事件推送）：接口层 `NotificationController`(SSE)；应用层 `PushService` 编排 + 事件监听；领域层 异动判定规则/推送幂等规则；基础设施层 SSE 通道 + `push_record` Repository。
- **policy**（政策时事）：接口层 `PolicyController`；应用层 `PolicyService`；领域层 `PolicyItem` 实体/倾向判断规则；基础设施层 `PolicyAdapter`(RSS) + Repository。
- **subscription**（订阅/信息流）：接口层 `SubscriptionController`；应用层 `SubscriptionService`/`FeedService`；领域层 订阅匹配规则/相关性规则；基础设施层 Repository。
- **common**（横切）：横切四层——接口层 鉴权过滤器/统一响应/全局异常；基础设施层 缓存/令牌桶限频/`@Scheduled`/弹性四件套/配置；不持有独立业务领域，被各域复用。

## ⚖️ 3. 候选方案对比

### 3.1 整体架构形态（单体 / 模块化单体 / 微服务）

| 维度(1-5,高优) | A 单体 | B 模块化单体 | C 微服务 |
| --- | --- | --- | --- |
| 成熟度 | 5 | 5 | 4 |
| 社区生态 | 5 | 5 | 4 |
| 学习成本 | 5(最低) | 4 | 2(高) |
| 可替换性 | 3 | 4 | 5 |
| 运维成本 | 5(最低) | 4 | 2(高) |

**选择：方案 B 模块化单体。** 理由：本平台有 5 个清晰业务域（聚合/AI/推送/政策/订阅），逻辑拆分利于演进与并行开发；但"个人/小团队量级、轻量级"约束下，微服务的部署/监控/链路追踪/分布式事务成本远大于收益。模块化单体=代码按域分包、模块间只走接口、单包部署，保留"未来单拆某域为服务"的缝（对齐方案 02 演进路线）。被否方案 C 理由：为架构图好看提前上分布式，复杂度自付。

### 3.2 LLM 网关（直连单一厂商 / 自建抽象网关 / 现成网关框架）

| 维度(1-5,高优) | A 直连单一厂商 | B 自建薄抽象网关 | C 现成框架(LiteLLM) |
| --- | --- | --- | --- |
| 成熟度 | 5 | 4 | 3 |
| 社区生态 | 5 | 5 | 3 |
| 学习成本 | 5(最低) | 4 | 3 |
| 可替换性 | 2(绑定厂商) | 5 | 4 |
| 运维成本 | 5 | 4 | 3(多一组件) |

**选择：方案 B 自建薄抽象网关。** 理由：LLM 厂商/模型迭代快、成本/可用性波动大，必须防锁定（A 否决）；但个人量级引入 LiteLLM 作为独立服务运维成本不划算（C 否决）。自建一个 `LlmGateway` 接口 + provider adapter + 提示词版本表 + 成本上限 + 缓存，足够且可控。被否方案 C 的跟进条件：若后续多 provider 路由/熔断/fallback 复杂化，重新评估引入 LiteLLM（记于 ADR-0004 后续验证）。

> 两项关键技术决策（统一数据访问层、LLM 网关）PM 指出需先 Spike，主方案给出基于合理假设的默认设计，详见第 8 节「Spike 调研计划」，标为「技术未决-先 Spike」，不阻塞主方案推进。

### 3.3 内部分层方式（经典无分层分包 / DDD 四层 / 六边形端口适配器）

| 维度(1-5,高优) | A 经典无分层分包 | B DDD 四层 | C 六边形端口适配器 |
| --- | --- | --- | --- |
| 成熟度 | 5 | 5 | 4 |
| 社区生态 | 5 | 5 | 4 |
| 学习成本 | 5(最低) | 4 | 3 |
| 可替换性 | 3 | 4 | 5 |
| 运维成本 | 5 | 4 | 4 |

**选择：方案 B DDD 四层。** 理由：6 业务域有清晰业务规则（异动判定/幻觉校验/订阅匹配/倾向判断），领域层抽离后可脱离框架单测、可移植，并为"未来单拆某域为服务"留缝；与 ADR-0001 模块化单体不冲突——模块化单体是整体部署形态，DDD 是模块内/层内结构，二者正交。被否方案 A 理由：无分层约束易把业务规则写进 Controller、领域逻辑散落、改表牵一发动全身（方案 01 常见坑）。被否方案 C 理由：端口数随外部依赖增长（6 数据源 + 多 LLM 厂商 + SSE），个人量级过度，DDD 四层已含依赖倒置足够解耦。决策记 ADR-0007（补充 ADR-0001）。

## 🔧 4. 详细设计

### 4.1 接口设计（RESTful，统一响应 `{code,msg,data,traceId}`，错误码 0/1xxx/2xxx/3xxx/5xxx）

#### 4.1.1 标的详情聚合查询

```
GET /api/v1/subjects/{subjectId}/detail?sections=quote,finance,valuation,announce,news,policy
```

- 说明：sections 可选，默认全部分区；单源缺失不阻断，返回体含 `sourceStatus` 标注每分区状态。
- 响应 200：
```json
{
  "code": 0, "msg": "ok", "traceId": "x",
  "data": {
    "subject": {"subjectCode":"SH600519","name":"贵州茅台","market":"A_SHARE","type":1},
    "quote": {"price":1680.00,"changePct":1.2,"source":"行情源","updatedAt":"..."},
    "finance": {"...":"..."},
    "valuation": {"pe":25.0,"...":"..."},
    "announcements": [{"title":"...","url":"...","publishedAt":"..."}],
    "news": [{"title":"...","url":"...","publishedAt":"..."}],
    "policies": [{"title":"...","url":"..."}],
    "sourceStatus": {"quote":"ok","finance":"ok","policy":"missing","...":"ok"}
  }
}
```
- 错误码：`30001` 标的不存在（404 语义）；`30002` 全部分区均缺失（仍 200，前端兜底）；`50000` 聚合异常。

#### 4.1.2 自选 watchlist 管理

```
GET    /api/v1/watchlists                       列表
POST   /api/v1/watchlists        Idempotency-Key   创建清单
GET    /api/v1/watchlists/{id}
POST   /api/v1/watchlists/{id}/items  Idempotency-Key  body:{subjectId, anomalyThreshold}  添加标的
DELETE /api/v1/watchlists/{id}/items/{itemId}
PATCH  /api/v1/watchlists/{id}/items/{itemId}  修改异动阈值
```
- 数据权限：只能操作自己 user_id 的清单（行级校验，防越权）。
- 幂等键：`Idempotency-Key = 用户Id+清单名`（创建）/ `用户Id+清单Id+subjectId`（加标的）。
- 错误码：`30010` 清单不存在；`30011` 标的已在清单（409）；`30012` 越权（403）。

#### 4.1.3 异动/事件订阅与推送

```
GET  /api/v1/notifications/stream        SSE 长连接（token 走 query 或 header）
GET  /api/v1/notifications?cursor=&type= 历史推送（游标分页）
```
- SSE 事件类型：`anomaly` / `event` / `policy` / `ai_brief` / `daily_recommend`。
- 客户端断线自动重连 + 按 `lastEventId` 补拉 history。
- 错误码：`401` SSE 鉴权失败；`30020` 推送通道未配置不重复发送。

#### 4.1.4 AI 简报生成（异步）

```
POST /api/v1/ai-briefs   Idempotency-Key   body:{subjectId, briefType}
     -> 202 { data:{ taskId } }
GET  /api/v1/ai-briefs/{taskId}
     -> 200 { data:{ status, content, sourceLinks, disclaimer } } | 404
```
- `briefType`：1 个股 / 2 事件归因 / 3 政策解读 / 4 每日推荐。
- 幂等键：`subjectId + briefType + yyyyMMdd`，重复请求直接返回上次结果（防重放）。
- `status`：0 处理中 / 1 完成 / 2 失败 / 3 待核实（数值校验不符）。
- 成本上限：单用户日配额（token 预算），超限返回 `30030` 配额用尽（429 语义）。
- 全部响应附 `disclaimer: "AI 生成，非投资建议"`。

#### 4.1.5 政策时事流

```
GET /api/v1/policies?days=7&industry=&cursor=
GET /api/v1/policies/{id}   含关联自选标的 + ai_tendency(利好/利空/中性)
```
- 错误码：`30040` 政策条目不存在。

#### 4.1.6 个性化主题订阅与个人信息流

```
GET   /api/v1/subscriptions?type=&cursor=
POST  /api/v1/subscriptions  Idempotency-Key  body:{subType, subKey, channel}
DELETE /api/v1/subscriptions/{id}            退订（后续不推送不入流）
GET   /api/v1/feed/personal?cursor=         个人信息流（订阅命中 + 每日推荐）
GET   /api/v1/recommendations/daily        Top5 推荐（盘前生成）
```
- `subType`：1 主题 / 2 标的 / 3 事件类型 / 4 政策主题。
- 幂等键：`userId + subType + subKey`。

### 4.2 数据模型（SQLite DDL，命名小写下划线，三必备字段 id/created_at/updated_at + version 乐观锁）

```sql
-- 标的主数据表（统一内部主键，外部代码映射）
CREATE TABLE subject_master (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  subject_code  TEXT    NOT NULL,            -- 内部统一代码 如 SH600519
  market        TEXT    NOT NULL,             -- A_SHARE / HK / INDEX / SECTOR
  subject_type  TINYINT NOT NULL,             -- 1股票 2指数 3板块 4基金(预留) 5债券(预留)
  name          TEXT    NOT NULL,
  external_codes TEXT,                        -- JSON: {"tushare":"600519.SH","akshare":"sh600519"}
  industry      TEXT,                         -- 行业/概念
  status        TINYINT NOT NULL DEFAULT 1,   -- 1启用 0停用
  created_at    TEXT    NOT NULL,
  updated_at    TEXT    NOT NULL,
  version       INTEGER NOT NULL DEFAULT 0,
  UNIQUE(subject_code)
);
CREATE INDEX idx_subject_type   ON subject_master(subject_type);
CREATE INDEX idx_subject_market ON subject_master(market);

-- 自选清单 + 清单项
CREATE TABLE watchlist (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL,
  name       TEXT    NOT NULL DEFAULT '默认清单',
  remark     TEXT,
  status     TINYINT NOT NULL DEFAULT 1,      -- 1启用 0删除
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  version    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_watchlist_user ON watchlist(user_id);

CREATE TABLE watchlist_item (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  watchlist_id      INTEGER NOT NULL,
  subject_id        INTEGER NOT NULL,
  anomaly_threshold DECIMAL(5,2) DEFAULT 3.00, -- 异动阈值%
  status            TINYINT NOT NULL DEFAULT 1,
  created_at        TEXT NOT NULL,
  updated_at        TEXT NOT NULL,
  version           INTEGER NOT NULL DEFAULT 0,
  UNIQUE(watchlist_id, subject_id),
  FOREIGN KEY(watchlist_id) REFERENCES watchlist(id)
);
CREATE INDEX idx_wlitem_subject ON watchlist_item(subject_id);

-- 订阅配置
CREATE TABLE subscription_config (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL,
  sub_type   TINYINT NOT NULL,                -- 1主题 2标的 3事件类型 4政策主题
  sub_key    TEXT    NOT NULL,                -- 主题词/subjectId/事件类型枚举
  channel    TINYINT NOT NULL DEFAULT 1,       -- 1应用内 2邮件(预留)
  status     TINYINT NOT NULL DEFAULT 1,      -- 1订阅中 0已退订
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  version    INTEGER NOT NULL DEFAULT 0,
  UNIQUE(user_id, sub_type, sub_key)
);
CREATE INDEX idx_sub_user_type ON subscription_config(user_id, sub_type);

-- 推送记录（幂等防重推）
CREATE TABLE push_record (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id         INTEGER NOT NULL,
  subject_id      INTEGER,
  push_type       TINYINT NOT NULL,           -- 1异动 2事件 3政策 4AI简报 5每日推荐
  ref_id          TEXT,                       -- 关联事件/简报id
  content         TEXT    NOT NULL,
  idempotency_key TEXT    NOT NULL,           -- = userId + pushType + refId
  status          TINYINT NOT NULL DEFAULT 0,  -- 0待推 1已推 2失败
  pushed_at       TEXT,
  retry_count     INTEGER NOT NULL DEFAULT 0,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  version         INTEGER NOT NULL DEFAULT 0,
  UNIQUE(idempotency_key)
);
CREATE INDEX idx_push_user_status ON push_record(user_id, status);

-- AI 简报（异步任务 + 事实回链 + 成本）
CREATE TABLE ai_brief (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  subject_id      INTEGER,
```

### 4.3 核心流程（关键分支：超时/重试/幂等/降级）

#### 流程 1 · 标的详情聚合查询（多源并行取数 + 降级）

```
前端 ─GET /subjects/{id}/detail─> AggregationService
AggregationService ─并行(CompletableFuture)─> 6 个 SourceAdapter
  ├ QuoteAdapter     ─查 Caffeine(TTL 5s)─命中?直接返回 / 未命中─> 行情源 API(超时1.5s, 重试0, 降级返回 null + 记 data_source_event)
  ├ FinanceAdapter   ─超时2s, 重试0(只读), 降级 null
  ├ ValuationAdapter ─超时2s, 降级 null
  ├ AnnounceAdapter  ─超时2s, 重试1(幂等只读), 降级返回空数组
  ├ NewsAdapter      ─超时2s, 降级空数组
  └ PolicyAdapter    ─失败/缺失 ─> 记 data_source_event, 该分区 sourceStatus="missing"
AggregationService ─收集(任一失败不抛异常, 不阻断其他)─> 组装统一 DTO
AggregationService ─200 + sourceStatus─> 前端
约定: 各 adapter 超时级联收敛(下游之和 < 上游 2s 预算); 缓存空值+短 TTL 防穿透; 缺失记 WARN 事件
```

#### 流程 2 · AI 简报生成（异步 + 幻觉校验 + 事实回链）

```
前端 ─POST /ai-briefs(Idempotency-Key)─> AIBriefController
Controller ─查幂等表─ 已完成? ─> 直接返回上次结果
  └ INSERT ai_brief(status=0) ─> 返回 202 + taskId
前端 ─GET /ai-briefs/{taskId}─> 轮询 / 或 SSE 订阅结果事件

异步 Worker:
  领取(status=0) ─> CAS 置处理中(WHERE id=? AND status=0, 影响 0 行=被并发领走, 跳过)
  ─ 经数据访问层取上下文(行情+财务+事件+新闻, 各带超时降级)
  ─ 加载 prompt_template(version, status=1)
  ─ LlmGateway 调用(按配置选 default provider, 失败按 fallback 切下一个 enabled 厂商; 超时 30s, 重试 1 次幂等, 成本上限校验 token 预算)
      └ 失败: status=2, 记 ERROR 告警; 超时 30min 自动置失败兜底
  ─ 解析结构化输出(JSON mode)
  ─ 幻觉校验: 提取数值 ─回查数据源 ─不符? 标 status=3 待核实 + 不展示为已确认结论
  ─ 写 source_links(原文链接, 回链率 100%)
  ─ status=1 完成, 写 cost_tokens
  ─ 发 Spring AiBriefDoneEvent ─> PushService ─> SSE 推送订阅用户(幂等)
```

#### 流程 3 · 异动检测 + 事件驱动推送

```
@Scheduled(每 10s) AnomalyJob ─> 遍历活跃 watchlist_item
  ├ 读行情(缓存 5s TTL) ─> 计算日涨跌幅
  ├ < 阈值? ─> 跳过
  └ >= 阈值 ─> INSERT anomaly_event(业务键去重) ─> 发布 Spring AnomalyEvent
PushService @EventListener(异步, 幂等):
  ─ 查 subscription(该 subjectId / 异动类型 / status=1)
  ─ INSERT push_record(idempotency_key=userId+pushType+refId, UNIQUE 防重推)
      └ 已存在? ─> 跳过(防重)
  ─ SSE 推送给在线用户 ─> status=1 已推
  ─ 推送失败重试 1 次 ─> 仍失败 status=2, 记 ERROR 告警
事件入库链路(重大公告/事件): EventSourceAdapter 入库 ─> 发布 EventEvent ─> 同样走 PushService
约定: 异动从触发到推送 <=15s; 事件入库到推送 <=30s; 幂等键=userId+pushType+refId; 断线靠 history 补拉
```

### 4.4 关键技术点

- **DDD 分层组织**（ADR-0007，补充 ADR-0001）：后端整体按 DDD 四层、层内按 6 业务域分包。依赖只能向下（接口层→应用层→领域层→基础设施层），禁止跨层/跨域直接调用；领域层保持纯净——不 import Spring/MyBatis/HTTP/Jackson 等框架类型，实体与业务规则可脱离容器单测、可移植；依赖倒置——`Repository`/`SourceAdapter`/`LlmGateway` 等端口接口定义在领域层，实现在基础设施层；跨域协作走应用层发布/订阅领域事件（Spring ApplicationEvent），不跨域 import 内部类，保留"未来单拆某域为服务"的缝。
- **统一数据访问层**（ADR-0003，先 Spike）：`SourceAdapter` 接口（`fetch(subjectId) -> SourceResult`），每源一个实现 + 字段映射表（JSON 配置）+ 主表 `external_codes` 把外部 code 映射到内部 `subject_id`。每个 adapter 外裹弹性四件套（超时/降级）+ Caffeine。
- **数据存储·SQLite**（ADR-0002）：单库 WAL 模式；单写者模型，连接池 1~5（写串行、读并发）；监控 `database is locked` 等待与超时并告警；升级触发线——多人并发写 / 单表千万行 / 多端网络访问 → 迁移 PostgreSQL（Flyway 脚本可复用）。库文件放应用数据目录不进 git，备份 `VACUUM INTO 'backup.db'`。
- **LLM 网关**（ADR-0004 + ADR-0008 补充，先 Spike-2）：配置驱动接入多家知名厂商（DeepSeek、GLM/智谱，预留通义/文心/Kimi）。`LlmGateway` 端口接口定义在领域层，基础设施层按 provider 实现 adapter。切换/fallback 机制：调用时取 `default: true` 的 provider，主 provider 超时/限频/错误则按 `fallback` 指向切下一个 `enabled: true` 厂商，全部失败才置简报失败并告警。保留：提示词版本表驱动、同 prompt+context 缓存（Caffeine，TTL 按 brief_type）、成本上限=单用户日 token 预算、结构化输出（JSON mode）、数值回查幻觉校验、长文本走异步（流程 2）。

  ```yaml
  # application.yml（密钥走环境变量，不入库不入 git）
  llm:
    providers:
      - name: deepseek
        base-url: https://api.deepseek.com/v1
        model: deepseek-chat
        api-key: ${DEEPSEEK_API_KEY}      # 环境变量注入, 不硬编码
        enabled: true
        default: true
        fallback: glm
      - name: glm
        base-url: https://open.bigmodel.cn/api/paas/v4
        model: glm-4
        api-key: ${GLM_API_KEY}
        enabled: true
        default: false
        fallback: deepseek
      # 预留: qwen / wenxin / kimi (enabled=false, 按需启用)
    timeout-seconds: 30
    retry: 1            # 仅幂等请求重试, 指数退避
    daily-token-budget-per-user: 20000
  ```
- **事务边界**：幂等记录与业务操作同事务（方案 03）；AI 简报状态用 `WHERE status=?` 乐观锁（方案 10 裁剪）；推送记录 `UNIQUE(idempotency_key)` 是最后防线。
- **缓存一致性**：Cache-Aside + 删缓存 + TTL 兜底；行情 TTL 5s、财务/估值 TTL 1h、政策列表 TTL 10min；热 key TTL 加随机抖动防雪崩。
- **分页**：游标分页（`WHERE id > #{lastId} LIMIT 20`），防深分页（方案 05）。
- **可测性预留**：幂等键、任务状态查询接口（`GET /ai-briefs/{taskId}`）、`sourceStatus` 字段、推送 history 接口——供测试断言与回放。

## 🛡️ 5. 非功能设计（逐项过）

- **性能目标**：
  - 详情页首屏 ≤2s：并行取数 + 缓存，最慢源超时 1.5~2s 收敛。
  - 异动推送 ≤15s：轮询 10s + 处理 5s 内。
  - 事件推送 ≤30s：事件入库即发，异步消费 <30s。
  - AI 简报 ≤10s 返回受理（202）；实际生成 30s~2min，前端任务轮询/SSE。
- **容量预估**（个人/小团队量级）：标的主数据 ≈1 万条；watchlist 单用户 ≤200 只 ×10 用户=2000；推送记录日均 ≈500 条/年 ≈18 万；AI 简报日均 ≈50 条/年 ≈1.8 万。均远低于 SQLite 升级线（单表千万级），不采用分库分表（ADR-0002）。
- **安全**：
  - 鉴权：JWT 短期 1h + Refresh；接口校验 + 行级数据权限（只看自己 watchlist/订阅），防越权。
  - 脱敏：不存敏感数据；LLM 调用不传未授权数据。
  - 限流：登录限流防撞库；AI 简报按用户日 token 配额（成本上限）；数据源按各自限频配令牌桶。
  - 合规：AI 内容全局"非投资建议"免责；来源+时间戳可见；不给买卖时点建议；不爬非授权数据。
- **可观测**：指标=各数据源 QPS/延迟/失败率、LLM 调用数/token/成本/延迟、推送成功率/延迟、缓存命中率；日志=traceId 串联、数据源缺失记 WARN、AI 校验失败记 WARN、推送失败记 ERROR；告警=数据源连续失败、LLM 成本超预算、推送失败率超阈值、异动 job 卡死。
- **降级预案**：数据源挂→该分区"暂无数据"+记事件不阻断；LLM 挂→AI 简报返回"AI 服务暂不可用"，每日推荐用规则兜底（信息面活跃度排序）；缓存挂→直查源接受延迟上升；SSE 断→客户端自动重连+补拉 history；DB 挂→只读缓存降级+告警人工介入。

### Spike 调研计划（技术未决-先 Spike，不阻塞主方案）

#### Spike-1 · 统一数据访问层与标的主数据映射

- **调研目标**：摸清 6 类源（行情/财务/估值/公告/新闻/政策）实际 API 字段、限频、代码体系，产出映射矩阵与 `SourceAdapter` 接口契约。
- **验证假设**：各源字段可经 JSON 映射表配置化；外部 code→内部 `subject_id` 可主表 `external_codes` 一次性映射。
- **产出物**：数据源字段对照表 + 限频参数表 + `SourceAdapter` 接口契约 + 主数据初始化脚本。
- **工期**：≤2 人天。
- **验证后可能调整**：若某源字段频繁变动→改用 schema 注册中心；若限频极紧→引入分布式限流（Redis 令牌桶）。

#### Spike-2 · LLM 网关、提示词与成本/缓存治理

- **调研目标**：选定 LLM 厂商+模型，验证结构化输出（JSON mode）与数值校验可行性，测出单次成本与延迟基线。
- **验证假设**：单一 provider 够用但需抽象防锁定；结构化输出可解析；关键数值可回查。
- **产出物**：LLM provider 选型对比 + 提示词 v1 模板 + 成本/延迟基线报告 + 缓存策略（TTL 按 brief_type）。
- **工期**：≤2 人天。
- **验证后可能调整**：若多 provider 路由/fallback 复杂→引入 LiteLLM；若成本超预算→优先缓存 + 降级模型。

## 🧾 决策留痕（ADR 摘要）

> 完整 ADR 落项目 `docs/adr/`，编号递增，只追加不修改。变更了新增一条并标记替代关系。

### ADR-0001 · 架构形态：模块化单体

- 背景：5 业务域 + 个人/小团队轻量级约束。
- 决策：模块化单体（代码按域分包+接口隔离，单包部署），Spring ApplicationEvent+@Async 作进程内异步（裁剪方案 06）。
- 补充：模块内/层内代码组织采用 DDD 四层，与模块化单体整体部署形态正交、不冲突（见 ADR-0007）。
- 被否：单体（缺演进缝）/ 微服务（运维复杂度自付）。
- 后果：正面=迭代快、部署简；负面=模块边界靠纪律守住（ArchUnit/依赖检查）；未来单拆某域为服务已留缝。

### ADR-0002 · 技术栈与存储：取基线 + 裁剪 RBAC/分库分表

- 背景：无特殊诉求，先取个人技术栈基线。
- 决策：Java21 + Spring Boot 3 + MyBatis-Plus + SQLite(WAL) + Caffeine + Logback；前端 React18+TS+shadcn/ui。不采用 RBAC（方案 11，JWT+单用户表够用，留接口）；不采用分库分表（方案 05，未到瓶颈）。
- 被否：MySQL/PG（未到升级线）/ Redis（未到多实例共享线）/ 完整 RBAC（个人量级过度设计）。
- 后果：`java -jar` 单包即起；升级触发线见后端基线（多人并发写/单表千万/多端网络访问→PG；多实例共享→Redis）。

### ADR-0003 · 统一数据访问层：SourceAdapter + 主数据映射（先 Spike-1 确认）

- 背景：多源字段差异、代码体系不一、限频不一（PM 技术未决项 1）。
- 决策：`SourceAdapter` 接口 + 每源实现 + JSON 字段映射表 + `subject_master.external_codes` 主数据映射；每 adapter 裹弹性四件套（超时/降级）+ Caffeine；幂等键用业务语义键（subjectId+type+date）。
- 被否：直连各源（字段漂移无收口）/ 引入重量级数据中台（过度设计）。
- 后果：字段映射集中可维护；Spike-1 若发现某源字段高频变动→改 schema 注册中心。

### ADR-0004 · LLM 网关：自建薄抽象（先 Spike-2 确认）

- 背景：外部 LLM 成本/延迟/可用性/模型迭代/幻觉（PM 技术未决项 2）。
- 决策：自建 `LlmGateway` 接口 + provider adapter（防锁定）+ 提示词版本表 + 成本上限（token 预算）+ 缓存；AI 简报异步任务（方案 12）+ 状态乐观锁（方案 10 裁剪）+ 数值回查幻觉校验。
- 补充：强化为配置驱动多 provider（DeepSeek/GLM 等，api-key 走环境变量）+ 运行时切换默认 + fallback，核心决策不变（见 ADR-0008）。
- 被否：直连单一厂商（绑定）/ LiteLLM 独立服务（个人量级运维不划算）。
- 后果：可替换性好；跟进=若多 provider 路由复杂化重新评估 LiteLLM。

### ADR-0005 · 缓存与限频：Caffeine Cache-Aside + 令牌桶

- 背景：读多写少（详情/行情热点/政策列表）+ 各源限频不一 + LLM 成本。
- 决策：Caffeine Cache-Aside + 删缓存 + TTL 兜底（行情 5s/财务 1h/政策 10min）；数据源按各自限频配令牌桶；LLM 按用户日 token 预算限流。
- 被否：Redis（未到多实例共享线）/ 裸 ConcurrentHashMap（无 TTL 防 OOM）。
- 后果：本地缓存红线=必设 maximumSize+expireAfterWrite，禁当持久层；多实例时升 Redis。

### ADR-0006 · 实时推送：SSE + Spring 事件驱动

- 背景：应用内通知单向推送 + 个人量级 + ≤15s/≤30s 延迟。
- 决策：SSE（Server-Sent Events）单向推送 + 客户端自动重连 + history 补拉；异动检测 @Scheduled 轮询（方案 08）+ 事件入库发布 Spring 事件 → PushService 幂等推送（方案 03）。
- 被否：WebSocket（双向过度，多一份握手复杂度）/ 纯轮询（延迟与成本不可兼得）。
- 后果：单向推送足够；断线重连兜底；事件驱动优先于轮询降成本。

### ADR-0007 · 分层方式：DDD 四层（补充 ADR-0001）

- 背景：ADR-0001 定模块化单体（按域分包），需明确模块内/层内的代码组织方式，让业务规则可单测、可移植，并为单拆某域为服务留缝。
- 决策：后端整体按 DDD 四层组织（接口层/应用层/领域层/基础设施层），层内按 6 业务域分包。依赖只能向下、禁止跨层/跨域直接调用；领域层保持纯净（不 import 框架/中间件类型）；依赖倒置（端口接口在领域层定义、基础设施层实现）；跨域协作走应用层领域事件。SQLite 数据访问走基础设施层 Repository 实现。
- 与 ADR-0001 关系：补充而非替代——模块化单体是整体部署形态，DDD 是模块内/层内结构，二者正交、不冲突。
- 被否：经典无分层分包（业务规则易散落 Controller，方案 01 常见坑）/ 六边形端口适配器（端口数随外部依赖膨胀，个人量级过度）。
- 后果：正面=领域层可脱离容器单测、单拆某域为服务时各层切片可整域迁移；负面=多一层分包纪律，靠 ArchUnit/依赖检查守住边界（领域层不引框架、禁跨层调用）。

### ADR-0008 · LLM 网关强化：配置驱动多 provider + fallback（补充 ADR-0004）

- 背景：ADR-0004 定自建 LlmGateway 薄抽象防锁定；用户要求可自定义配置接入 DeepSeek、GLM 等知名厂商，运行时可切换、支持 fallback。
- 决策：配置驱动接入多家知名厂商（DeepSeek、GLM/智谱，预留通义/文心/Kimi）。providers 列表配置（name + base-url + model + api-key 走环境变量不硬编码 + enabled + default + fallback）；运行时可切换默认 provider，主 provider 超时/限频/错误按 fallback 顺序切下一个 enabled 厂商。保留 ADR-0004 的提示词版本表 + 成本上限 + 缓存 + 结构化输出 + 幻觉校验。
- 与 ADR-0004 关系：补充而非替代——核心决策（自建网关、防锁定、薄抽象）不变，强化为多 provider 配置驱动 + fallback。
- 被否：直连单一厂商（绑定，ADR-0004 已否）/ 运行时硬编码 provider 切换（改厂商要改代码，违背配置驱动）/ 引入 LiteLLM（个人量级运维不划算，ADR-0004 已否，跟进条件保留）。
- 后果：可随时增减厂商、切换默认、降级容错；负面=多 provider 配置与密钥管理需文档化（密钥不入库，走环境变量/配置中心）。
