## 🎯 1. 背景与目标

### 背景（设计前核实，2026-09-22）

| 事实 | 核实结果 |
| --- | --- |
| 政策列表接口 | `GET /api/v1/policies?days=&industry=&cursor=`（`PolicyController.list` → `PolicyService.listPolicies` → `PolicyRepository.findRecent`），`id < cursor LIMIT 20` newest-first；响应 `{policies[], nextCursor}`，无 total |
| Job 日志接口 | `GET /api/v1/job-logs?jobName=&cursor=`（`JobLogController.list` → `JobLogQueryService.list` → `JobExecutionLogRepository.byJobNameCursor`），同款游标分页；响应 `{items[], nextCursor}` |
| 排序 | 两处均 `ORDER BY id DESC`——**id 为自增主键、全局唯一，天然全序**（无同界并列，无需补唯一列） |
| `job_execution_log.status` | `TEXT NOT NULL`，值域 `STARTED/SUCCESS/FAILED`（`JobExecutionStatus.persistentName()`），已有 `idx_job_log_name_time(job_name, created_at)`、`idx_job_log_time(created_at)` 两索引，status 无索引 |
| `policy_item` 关键字段 | `title NOT NULL`、`summary` 可空、`related_industries` JSON 文本（industry 过滤现状 `LIKE '%"行业"%'`，引号作 token 边界）、`idx_policy_published/idx_policy_created` 两索引 |
| 前端现状 | `Policy.tsx`（游标追加 + 行业下拉 + days 写死 7）、`JobLog.tsx`（游标追加 + jobName 下拉 + URL 预过滤）；`api/policy.ts`、`api/jobLog.ts` 各一个游标函数；AbortController/翻页失败保留重试基线已具备 |
| 错误码 | `2001 PARAM_INVALID`（400）既有，本批参数校验复用；`Result{code,msg,data,traceId}` 包装既有 |
| 数据量 | `policy_item` 14 行；`job_execution_log` **12,385 行**（2026-09-22 实测） |

### 目标（对齐 PRD，可量化）

- 两接口页码模式：`page≥1`（默认 1）、`size` 1~50（默认 20，超限 **400 拒绝不截断**）、响应含 `total + page + size`（列表字段与游标模式完全一致）。
- 筛选与分页任意组合：政策 `days + industry + keyword`；Job 日志 `jobName + status`；全部 AND 语义、总数按组合结果刷新。
- 通用分页组件一处实现两页复用（页码跳转/上一页下一页/每页条数 10/20/50/总数，键盘可达，暗色 token）。
- 游标模式向后兼容：`page` 参数缺席时行为逐字节不变（信息流/订阅页不受影响，回归项）。
- 页码列表查询 P95 ≤ 50ms（当前实测 ≤1.3ms，见 §3.2）。

### 非目标（防范围蔓延）

- 不动 `/api/v1/feed/personal`、`/api/v1/subscriptions`（需求裁决：消费流保留无限滚动、订阅页维持现状）。
- 不做分页状态进 URL、政策倾向筛选、Job 日期范围（需求 Won't/Could）。
- 不为 `status` 建索引、不上 FTS5、不加列表缓存（理由见 §3.3 与 ADR-0035 被否清单）。
- 零 DDL：无新表、无新列、无索引变更（回滚无需脚本，见 §5）。

## ⚖️ 3. 核心选型（裁决与依据）

### 3.1 页码模式形态：**同端点双模式**（`page` 出现即页码模式）vs 独立端点

| 维度 | A. 同端点双模式（**入选**） | B. 独立端点 `/policies/page` |
| --- | --- | --- |
| REST 语义 | 同一资源集合的分页方式差异放查询串——资源命名不动 | 把查询方式编码进路径（类动词化）；同资源两 URI，过滤条件被迫分裂两套语义 |
| 游标兼容 | `page` 缺席 = 既有路径，**字节级不变**，回归面最小 | 旧端点保留 + 新端点并存，端点数翻倍，OpenAPI/测试面翻倍 |
| 前端适配 | `api/policy.ts` 增一个函数，类型新增两个 record | 同样增函数，但多维护一组端点常量与文档 |
| 校验集中 | 模式互斥（page×cursor）在 Controller 一处判定 | 天然无互斥问题（B 的唯一优势），代价是 URI 膨胀 |
| 五维度速评 | 成熟度 5（业界分页参数惯例）/ 学习成本 5 / 可替换性 5（参数级，随时可再拆端点） | 成熟度 4 / 运维成本 3（端点数×2） |

**裁决 A**：双模式同端点。模式判别规则（两条，Controller 一处实现）：

1. `page` 参数**出现**（含 `page=1`）→ 页码模式；`page` 缺席 → 游标模式（既有行为）。
2. 防呆：`page` 与 `cursor` 同时出现 → 400；页码模式专属参数（`size`/`keyword`/`status`）出现而 `page` 缺席 → 400（`2001`，msg 注明缺 `page`）——契约确定性优先于宽容。

> 版本化说明：非破坏性变更（纯新增可选参数 + 新响应形态由参数显式选择），不升 `/v2`（接口规范「破坏性变更才升版本」）。响应 record 按模式二选一：`PolicyListView`（游标）/ `PolicyPagedView`（页码），不用「全字段可空大 record」混装，契约各自闭合。

### 3.2 深分页实测（2026-09-22，本机 sqlite3 CLI，生产库只读查询）

| 查询 | 结果 | 耗时 |
| --- | --- | --- |
| `SELECT COUNT(*) FROM job_execution_log` | 12,385 行 | **0.57ms** |
| `COUNT(*) WHERE job_name='PolicyFetchJob'` | 43 行 | 0.02ms |
| `COUNT(*) WHERE status='FAILED'` | 7 行 | 1.1ms |
| `ORDER BY id DESC LIMIT 20 OFFSET 12000`（当前最深页） | 20 行 | **0.13ms** |
| `WHERE status='SUCCESS' ORDER BY id DESC LIMIT 20 OFFSET 5000`（组合过滤深页） | 20 行 | 0.25ms |
| `SELECT COUNT(*) FROM policy_item` | 14 行 | <0.1ms |

**结论**：当前量级下 COUNT 全扫与最深 OFFSET 均毫秒级甚至亚毫秒级，`LIMIT/OFFSET + 精确 COUNT` 完全够用——**从简采用，不做 keyset 混合**。SQLite 的 OFFSET 成本 = 索引顺走 offset 行，12k 行量级线性项可忽略；COUNT 无 WHERE 走行数元数据/单遍扫，有 WHERE 全扫亦毫秒级。

**护栏（触发即走变更控制，联动 backlog 清理项）**：

- 行数阈值：`job_execution_log` **> 50 万行**（按当前增速外推数年之外），或
- 性能阈值：页码模式列表接口 P95 **> 100ms**（服务 debug 日志耗时观测，见 §5）。
- 触发后动作：① 先落地 README M9 候选 backlog「job_execution_log 清理」（保留 N 天，治本——审计价值随账龄衰减）；② 清理仍不可行再议 keyset 混合（页码跳页需前向累积游标，复杂度高）或近似 total——均需新 ADR。

### 3.3 被否的深分页/性能方案

| 被否方案 | 理由 |
| --- | --- |
| keyset（游标）混合实现页码跳页 | 页码跳页 = 随机访问，keyset 只能顺序前进；「跳第 N 页」需服务端累积 N 页游标或客户端多次请求，复杂度高；当前量级毫秒级无收益（实测 §3.2） |
| 近似 total（count 上限截断，如 `total≤1000`） | 单人审计场景要「共多少条」精确感知，近似值制造「第 x/y 页」失真；精确 COUNT 毫秒级无必要省 |
| `status` 建索引 | 低基数（3 值）索引选择性差，SQLite 优化器大概率仍全扫；实测 FAILED 过滤深页 0.25ms，不值得一个索引位 |
| 关键词上 FTS5 | 时间窗（days）天然先收窄范围，窗内百级条目 `LIKE %kw%` 实测毫秒级；FTS 触发器/影子表/中文分词复杂度与量级严重不匹配，超预期再议（PRD 同口径） |
| 列表结果缓存 | 见 §2 采用清单（键空间×单人量级，倒挂） |

### 3.4 越界页语义（裁决：**200 + 空列表，如实回显**）

- `page` 超出总页数（如 total=8、size=20、page=2）→ **200 + 空列表 + 如实回显请求的 `page/size` 与真实 `total`**——offset 语义天然如此，实现零分支。
- 被否「服务端收敛到末页」：需先 COUNT 再改写 page 再取数（多一跳），且回显的 page 与请求不符，前端状态机反而复杂、契约失真。
- 被否「400 报错」：越界不是调用方错误（浏览期间日志被清理/政策出窗都会导致），报错制造噪音。
- **配套前端约定**（§4.4）：筛选变化必回第 1 页（正常流程不产生越界）；若响应空列表且 `total>0`（数据收缩 race），前端检测 `page > ceil(total/size)` 自动回第 1 页重拉——承接 PRD 故事 2 场景 2「不出现空白页」。
- `page=1` 且空结果 → 正常空态（分页导航隐藏，PRD 故事 2 场景 3）。

### 3.5 排序稳定性（裁决：保持 `ORDER BY id DESC`，无需补列）

id 为自增主键、全局唯一，单一排序键即全序——同参数连续请求页序确定，不存在「同界漂移」。浏览期间**新数据写入**导致的页界前移/跨页重复为 newest-first 固有现象，PRD 非功能已裁决接受、不作缺陷。页码模式与游标模式**同序同过滤**（同一 wrapper 组装，§4.1/§4.2），同参数下两模式页内容可互相对照（回归断言用）。

## 🔧 4. 详细设计（到类级，可直接开发）

### 4.1 后端 · 政策列表页码模式 + 关键词搜索

**契约**（`GET /api/v1/policies`，Bearer）：

```
游标模式（既有，不变）：GET /api/v1/policies?days=7&industry=&cursor=
页码模式（新增）      ：GET /api/v1/policies?days=7&industry=&keyword=半导体&page=2&size=20
```

| 参数 | 规则 |
| --- | --- |
| `page` | 出现即页码模式；≥1；上限 1,000,000（防 offset 溢出，`(page-1)×size < 5×10^7 < int max`）；与 `cursor` 互斥 |
| `size` | 仅页码模式；缺省 20；1 ≤ size ≤ 50，**越界 400 拒绝**（2001，msg「size 超过上限 50」/「size 至少为 1」） |
| `keyword` | 仅页码模式；trim 后空 = 缺席（不过滤）；非空时长度 ≥2 且 ≤64，否则 400（2001，msg 注明「关键词至少 2 个字符」）；匹配口径见下 |
| `days` | 既有语义不变（≤0 取 7、>90 截 90，实现层既有 clamp） |
| `industry` | 既有语义不变（null/blank 不过滤） |

**页码模式响应**（200，列表字段与游标模式逐字段一致）：

```json
{
  "code": 0, "msg": "成功", "traceId": "…",
  "data": {
    "policies": [
      { "id": 4512, "title": "…", "source": "国务院政策",
        "publishedAt": "2026-09-21", "summary": "…",
        "relatedIndustries": ["电子", "半导体"] }
    ],
    "total": 45, "page": 2, "size": 20
  }
}
```

越界页示例：`page=99` 且 `total=45` → 200，`policies: []`，`total/page/size` 如实回显。

**关键词匹配口径（写明，测试断言依据）**：

- 范围：`title LIKE %kw% OR summary LIKE %kw%`（两字段任一命中）；`summary` 为 NULL 时 `NULL LIKE` 不命中（SQL 天然语义，正确）。
- **转义（必须）**：MyBatis-Plus `like()` **不做通配符转义**，自由文本必须手工转义后走参数绑定 + `ESCAPE '\'`：

```java
/** LIKE 模式串：转义 \ % _ 后包 % 通配（防用户输入通配符误当语义）。 */
private static String likePattern(String raw) {
    return "%" + raw.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_") + "%";
}
// wrapper 组装（.apply 走 {0} 参数绑定，不拼接）：
//   .and(q -> q.apply("title LIKE {0} ESCAPE '\\'", pat)
//              .or().apply("summary LIKE {0} ESCAPE '\\'", pat))
```

- **大小写口径**：SQLite `LIKE` 对 ASCII 字母**不区分大小写**（内置行为，无需 `PRAGMA case_sensitive_like`），非 ASCII（中文）按字节原样匹配——即英文关键词大小写互命中、中文关键词精确匹配。PRD 主场景为中文关键词（"半导体"），口径一致，记入 ADR-0035。
- 既有 `industry` 过滤的 `like()` 未转义：值来自固定行业下拉（封闭值域），风险可忽略，本批不扩散改动（记 §7 开放问题）。

**SQL 形态**（RepositoryImpl，`WHERE` 由私有方法一处组装、findPage/count 两用）：

```sql
-- 页数据（page=2, size=20 → LIMIT 20 OFFSET 20）
SELECT id, title, source, published_at, summary, related_industries, ai_tendency, source_url
  FROM policy_item
 WHERE published_at >= '2026-09-15'                      -- days 窗（既有）
   AND related_industries LIKE '%"电子"%'                 -- industry 非空时（既有）
   AND (   title LIKE '%半导体%' ESCAPE '\'
        OR summary LIKE '%半导体%' ESCAPE '\' )           -- keyword 非空时（新增）
 ORDER BY id DESC
 LIMIT 20 OFFSET 20;
-- 总数（同一 WHERE）
SELECT COUNT(*) FROM policy_item WHERE …同上…;
```

| 类/文件 | 动作 |
| --- | --- |

### 4.2 后端 · Job 日志页码模式 + 状态筛选

**契约**（`GET /api/v1/job-logs`，Bearer）：

```

SELECT COUNT(*) FROM job_execution_log WHERE …同上…;
```

## 🛡️ 5. 非功能设计（逐项过）

| 项 | 结论 |
| --- | --- |
| 性能目标 | 页码列表接口 P95 ≤ 50ms（实测最深页 + COUNT 合计 ≤ 1.7ms @ 12,385 行）；政策页码查询 ≤ 5ms（14 行基线，时间窗先收窄） |
| 容量 | `job_execution_log` 12,385 行（2026-09-22）持续增长型——护栏线 50 万行 / P95 100ms（§3.2），触发走清理优先；`policy_item` 时间窗内百级以内 |
| 安全 | 纯只读 GET、JWT 既有防线；`size≤50` 上限即「防攻击性大页」校验（拒绝式）；keyword LIKE 参数绑定 + ESCAPE 转义（防通配符注入式全表模糊）；无敏感数据新增 |
| 可观测 | 两 Service `log.debug` 带 page/size/total/耗时毫秒（护栏观测数据源，对齐 `getPolicy` 先例）；不新增指标件（从简） |
| 降级预案 | 查询失败走既有错误三态（页面错误条 + 重试）；无外部依赖新增，无独立降级路径 |
| 可测性预留 | 契约确定性规则（互斥 400/越界空页/如实回显）均可精确断言；`page=1` 与游标首页同参数可互相对照（§3.5）；`data-testid` 全量预置（§4.3） |
| 数据库规范 | 零 DDL：表/列/索引全沿用（命名/三字段/索引现状已合规）；**无变更 SQL 故无回滚脚本义务**；`SELECT` 显式列（PO 映射既有） |
| 兼容性 | 游标模式字节级不动（`page` 缺席路径零改动）；`/feed/personal`、`/subscriptions` 消费方零感知；前端删除的两游标函数无其他消费方（已核实） |

> count 与页数据两条 SQL 非同快照（SQLite 单写者下间隙极小）：浏览瞬间写入导致的 total/页内容轻微错位与页界漂移同源，PRD 已裁决接受。

## 📝 决策留痕摘要

本方案全部关键决策见 [ADR-0035](/docs/02-设计/adr/0035-列表页码分页双模式与深分页从简.md)：页码模式取同端点双模式（独立端点被否）、size 超限 400 拒绝、越界页 200 空列表如实回显、LIMIT/OFFSET + 精确 COUNT 从简（实测 12,385 行毫秒级；护栏 50 万行 / P95 100ms 触发清理优先）、`ORDER BY id DESC` 主键全序无需补列、status 不建索引、关键词 LIKE ESCAPE 转义与大小写口径。
