### 目标（对齐 PRD，可量化）

- 4 场景全部模板版本一页可见：分组列表、激活标识、占位符数量、异常空态警示。
- 编辑/新建全页面化：保存即落新版本并激活（沿 T29 升级语义），版本号服务端受控生成（默认升次版本、可选升主版本），下一次生成即用新值。
- 版本安全三通道：编辑即新版本（旧版必留）、激活切换（回滚任意保留版本）、置废版本物理删除（守卫：激活不可删）；任何操作后每场景恒有且仅有一个 `status=1`。
- 占位符对照：编辑器内展示该场景注册表（与上下文构造器同源）+ 一键插入；保存校验的 diff 基准与对照区同源。

核心思路（外行能懂）：生成链路每次生成都现查数据库拿"当前激活模板"，改完模板下一次生成天然用新值——所以本期**只造管理面，不动生成面**。管理面 = 一组带事务的增删改查接口：保存 = 校验 → 生成新版本号 → 旧版置废 + 新版激活（一个事务）；切换 = 目标版激活 + 其余置废；删除 = 只许删本就没在用的置废版。校验器复用渲染器同款分段逻辑，占位符对照清单直接登记在三个上下文构造器自己身上（单一事实源），接口与校验用同一份。

## ⚖️ 3. 候选方案对比

### 3.1 版本号生成与排序（PRD 风险表"字典序错序"的对策）

| 方案 | 思路 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A 零 DDL：TEXT 保持 `v{major}.{minor}`，服务端受控生成 + Java 数值排序 | 生成器解析既有版本取 `max`，MINOR +1 或 MAJOR +1 归零；列表与"最新"判定在 Java 按数值排序 | 无迁移无数据回填；与 V8/V14 存量（v1.0/v1.1）零冲突；字典序仅残留在防御性 `ORDER BY version DESC`（唯一激活不变量成立时无实际作用） | DB 层面无法用 ORDER BY 表达真实版本序（靠应用层保证） | ✅ 采用（ADR-0021） |
| B version 改双 INTEGER 列（major/minor） | DDL 加两列 + 存量回填 + 读取改造 | DB 可排序 | 违背最小改动：本期无人需要 SQL 层版本排序；迁移 + PO/实体/仓储连带改造 | ❌ 否决 |
| C 零填充字符串（v01.09 → v01.10） | 字典序恢复正确 | 无应用层排序 | 存量 v1.0/v1.1 需回填；展示观感差；99 之后仍要扩位 | ❌ 否决 |

**选择 A。** 版本序只被两处消费：列表展示序（Java 排）与"取激活"（唯一激活不变量下 `ORDER BY version DESC` 仅是防御兜底）。为此改表代价不成比例。生成规则与冲突处理见 §4.2。

### 3.2 占位符注册表同源机制（PRD 故事 4 场景 3"校验基准与对照区同源"）

| 方案 | 思路 | 漂移风险 | 结论 |
| --- | --- | --- | --- |
| A 独立注册表类硬编码第二份清单 | 新建 `PlaceholderCatalog` 静态写 30 键 | **高**：清单与三个构造器的 `ctx.put` 无任何绑定，构造器加键注册表不知 | ❌ 否决 |
| B 运行时推导（调真实 build() 取 keySet） | 构造代表性样本跑构造器，收集输出键集 | 依赖样本完备性：`BriefContextBuilder` 在 subject 为 null 时少 3 键、`DailyRecommendationContextBuilder` 需 mock 五个仓储依赖——推导结果不稳定 | ❌ 否决 |
| C 装配器自带描述符（colocated）+ 注册表聚合 + 同源单测 | 每个构造器新增 `providedPlaceholders()` 返回 `List<PlaceholderDescriptor>`（key+一句话说明），与 `ctx.put` 同文件同序维护；`PromptPlaceholderRegistry` 聚合三处暴露 `Map<BriefType, …>`；单测断言代表性输入下 `build()` 输出 keySet == 描述符 keySet | **低**：清单就在 `ctx.put` 旁边，加键必同文件；同源单测为机械闸门 | ✅ 采用（ADR-0022） |

**选择 C。** 关键性质：对生成链路是**纯增量**（只加方法不动既有代码路径），校验器与只读接口共用同一 Registry 实例，"对照区清单"与"unknown 校验基准"物理上是一份数据。

### 3.3 确认放行机制（"移除拦截 + 确认放行"如何在请求中表达；对齐 UI 方案 D7 联判）

| 方案 | 思路 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A 无状态确认数组（仅移除类） | POST body 携带 `confirmedRemovedKeys`（键名数组）；服务端**每次重算 diff**，diff 出的移除键必须全部出现在数组中才放行；unknown 类不拦截、只以 `warnings` 回显 | 无服务端状态；重放/改模板后旧确认自动失效（diff 重算）；与 PRD"仅警告/不阻断"及 UI D7（amber 不需勾选）逐字对齐 | 请求体稍宽 | ✅ 采用 |
| B 确认令牌（两阶段提交） | 首次保存 409 返回 confirmToken，带 token 重试放行 | 语义显式 | 令牌需存储/过期管理，单人场景过度；token 有效期内底稿被并发改掉还需版本比对——绕回 A 的重算 | ❌ 否决 |
| C 移除类也仅前端提示不拦 | 后端不拦 | 最简 | 违背 PRD 裁决（移除默认拦截是 Must） | ❌ 否决 |
| D unknown 也逐项确认放行（首版设计） | unknown 与移除共用确认数组 | 防警告被忽略 | 违背 PRD"仅警告/不阻断"原文；场景 2 休眠模板含 7 个事件占位符，每次编辑都强制勾选 7 项——体验劣化无安全收益 | ❌ 否决（自我修正，采纳 UI 联判） |

**选择 A。** 交互闭环（UI 方案 D7"保存确认 Dialog"承载）：保存 → 服务端重算 diff → 未确认的移除键存在 → 409/30068 携带 `{removed:[{key,description}], unknown:[{key}]}`（unknown 仅随单展示，不是拦截条件）→ 前端 Dialog 内逐项勾选"确认移除"（amber 警告直接展示）→ 重提交带 `confirmedRemovedKeys` → 放行。`unknown` 的存在意义是让 Dialog 一次看全两类提示；硬校验失败不进 Dialog（前端预检直接禁用保存按钮，UI D7）。

## 🔧 4. 详细设计

### 4.1 数据模型：prompt_template 零 DDL（ADR-0021）

**裁定：不加列、不加表，迁移序列停留在 V15/U15，本期无 V16/U16。** 理由：

- `created_by`：单人系统（ADR-0002 裁剪 RBAC），该列恒为同一用户，无信息量；PRD Won't 明确"审计日志不做（版本行本身即留痕）"。
- 备注/描述列：不在冻结需求内（故事与验收标准均未要求），按最小改动不加。
- 版本管理所需能力（唯一版本 `UNIQUE(brief_type, version)`、二值状态、留痕的 created_at/updated_at）V8 已全部具备。

既有 DDL（V8，引用不改）：

```sql
CREATE TABLE prompt_template (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  brief_type  TINYINT NOT NULL,                 -- 1个股 2事件归因 3政策解读 4每日推荐
  version     TEXT    NOT NULL,                 -- 语义版本 v{major}.{minor}
  template    TEXT    NOT NULL,                 -- ---SYSTEM---/---USER--- 分段 + {{key}} 占位符
  status      TINYINT NOT NULL DEFAULT 1,       -- 1启用(ACTIVE) 0废弃(RETIRED)
  created_at  TEXT    NOT NULL,
  updated_at  TEXT    NOT NULL
);
CREATE UNIQUE INDEX uq_prompt_template_brief_version ON prompt_template(brief_type, version);
```

### 4.2 版本号生成器（`PromptVersionGenerator`，新增纯函数类）

```
输入：briefType 的全部既有 version 集合 + versionStrategy（MINOR|MAJOR，默认 MINOR）
解析：^v(\d+)\.(\d+)$；非法格式（手工改库产物）忽略并记 WARN，不参与 max 计算
MINOR：candidate = (maxMajor, maxMinor + 1)        # v1.1 → v1.2；v1.9 → v1.10（正确，排序在 Java）
MAJOR：candidate = (maxMajor + 1, 0)               # v1.9 → v2.0
输出：v{major}.{minor}
兜底：UNIQUE(brief_type, version) 冲突 → 30067 类冲突错误（409 语义，见错误码表）；
      场景无任何合法版本（防御）→ 从 v1.0 起
```

- 用户**不传版本号**（PRD 风险表裁定"不让用户自由填写"）；接口只传 `versionStrategy`。
- 排序口径：列表接口与"最新版"判定在 Java 按 (major, minor) 数值降序；`findActiveByBriefType` 的 `ORDER BY version DESC` 保持原样，仅作唯一激活不变量被破坏时的防御兜底（其字典序缺陷已由不变量 + Java 排序双保险覆盖，ADR-0021）。

### 4.3 校验器（`PromptTemplateValidator`，新增纯函数类，规则表）

输入：`(briefType, newTemplateText, activeTemplateText?, registry)`；输出：`ValidationResult{ hardErrors[], removed[], unknown[] }`。

| # | 规则 | 级别 | 判定逻辑（与运行时同源） |
| --- | --- | --- | --- |
| V1 | 含 `---SYSTEM---` 且含 `---USER---` 且 SYSTEM 在 USER 前 | 硬拦截 | 复用渲染器同款切分逻辑（§4.8 提取 `PromptSections` 共享；缺任一标记或顺序颠倒 = 渲染时抛 `IllegalStateException` 的同款条件） |
| V2 | system 段含 "json" 字样（大小写不敏感） | 硬拦截 | V8 播种不变量（DeepSeek JSON mode 前提，Spike-2 §5.2）；system 段 = V1 切分结果 |
| V3 | 模板非空且长度 ≤ 65536 字符 | 硬拦截 | 防御性上限（SQLite TEXT 无压力，防误贴全量数据） |
| V4 | 占位符移除 diff：`removed = placeholders(base) − placeholders(new)` | 确认拦截（危险级） | 占位符提取用渲染器同款正则 `\{\{\s*(\w+)\s*\}\}`（提取逻辑一并入共享工具）；**基准 = 请求 `baseVersionId` 指向的底稿版本行**（UI 方案联判点 3：前端编辑底稿可能是置废旧版，diff 基准与前端一致才不会确认清单错位），缺省/无效时回落该场景当前激活版，无激活版基准为空集；每项附注册表 description（查不到则"（无来源说明）"） |
| V5 | 无来源占位符：`unknown = placeholders(new) − registry(briefType)` | 警告级不拦截 | 注册表 = §4.5 单一事实源；结果计入 `warnings` 回显（保存确认 Dialog amber 展示 + 201 响应回带）；场景 2 的 eventTitle 等休眠占位符如实落入此类 |

放行条件：`hardErrors` 为空 **且** `removed ⊆ confirmedRemovedKeys`（unknown 不参与放行判定）。

- hardErrors 非空 → `BusinessException(30067)`，msg 逐条列明（如 `缺少 ---USER--- 分段标记`、`system 段须含 json 字样（JSON 输出模式前提）`）。
- 待确认未齐 → 控制器返回 409 / code 30068，`data` 携带 removed/unknown 清单（§4.4.3；unknown 仅随单展示）。
- 前端预检镜像同一规则表（体验级；后端为权威；diff 基准同口径 = 底稿版本，UI 联判点 3）。

### 4.6 事务与激活唯一不变量

- `PromptTemplateAdminService`（应用层，新增）持编排与事务边界（Controller 薄）：
  - **create**：`@Transactional` ① 校验（§4.3，纯函数事务外执行，失败不耗事务）→ ② 生成版本号（§4.2）→ ③ `UPDATE prompt_template SET status=0 WHERE brief_type=? AND status=1`（先置废）→ ④ INSERT 新行 `status=1`。步骤 ③④ 同事务，任何时刻对外可见状态恒为"恰好一行激活"（SQLite WAL 下事务原子可见）。
  - **activate**：`@Transactional` ① 目标行存在校验（30066）→ ② 同场景其余置 0 → ③ 目标行置 1。已是激活则 ③④ 无变化，幂等。
  - **delete**：无显式事务必要（单行 DELETE）；先查（30066/30069 守卫）后删。
- 并发防护：单用户低频操作 + 前端二次确认；不设乐观锁列（V8 头注既有裁定沿用：低频配置表无并发 UPDATE 竞争）；UNIQUE 索引是脏数据最后防线。
- 手工改库绕过页面（PRD 风险表）：接口路径承诺不变量；列表 `activeCount` 异常检测 + 前端警示兜底可见性（§4.4.1）；`findActiveByBriefType` 的 `LIMIT 1` 既有防御使双激活不致崩溃。

### 4.7 即时生效链路验证（已验证事实，写入方案供测试与评审引用）

**结论：模板内容与激活版本变更后，下一次生成即用新值，无需任何失效动作、无需重启。PM 核实 + 架构逐点二次验证通过：**

1. **模板加载无缓存**：`AIBriefService.generateAndPersist`（briefType 1/2/4）与 `PolicyTendencyService.judgeAndPersist`（3）每次生成调用 `loadActiveTemplate` → `findActiveByBriefType` 直查 SQLite；`prompt_template` 不在 ConfigCenter 快照（那是 runtime_config 的机制，ADR-0017/0020）、无任何内存副本。
2. **LLM 响应缓存天然失效**：`LlmCache.keyOf = briefTypeKey + sha256(messages + model + temperature + maxTokens + responseFormat)`，messages 为**渲染后全文**——模板内容变更或激活切到不同内容的版本 → 渲染结果不同 → 新哈希 → 不命中旧缓存条目（新条目按新模板产出落缓存，TTL 语义不变）。
3. **无其他缓存层**：全链路唯一响应缓存即 LlmCache；`SourceCache` 缓存的是数据源原始数据（喂上下文，与模板无关）；`ai_brief` 表仅落 `template_version` 留痕（展示用，不回流生成）。
4. 唯一边界情形：切换激活到与当前激活**内容完全一致**的另一版本行（如误存重复内容）会命中同一缓存条目——产出与缓存内容一致，无害，不需处理。

> 因此 M5 **不需要** RuntimeConfigChangedEvent 式的变更广播，也不需要给模板加缓存（加了反而要管失效）——方案库 04 裁剪不采用的依据（§2）。

## 🛡️ 5. 非功能设计（逐项过）

- **性能**：模板表个位数~几十行、全量读走 `uq_prompt_template_brief_version` 索引前缀，列表 P95 < 20ms（SQLite 本地）；校验与版本生成均为内存纯函数（模板 ≤ 64KB，正则毫秒级）。无性能敏感点。
- **容量**：版本行增速 = 人工编辑频率（低频）；置废版本可物理删除自清理，无清理任务需求（区别于 job_execution_log，M4 风险项不复发）。
- **安全**：6 端点全部受 JWT（JwtAuthFilter 既有链，不入白名单）；模板内容非敏感数据（无密钥），无脱敏需求；无越权面（单人、无行级归属）；写操作前端二次确认 + 后端守卫。
- **可观测**：create / activate / delete 各记一条 INFO 审计日志（briefType + version + 操作结果，对齐 M4 配置变更日志风格）；`PromptTemplateService` 既有"加载提示词模板"日志保留（生成侧天然可见当前版本）；渲染期 `IllegalStateException` 链路不变。
- **降级预案**：本方案无新增外部依赖与组件，无依赖方可挂；写失败即事务回滚零变更（旧激活继续生效）；校验器为纯函数无运行态。生成链路因**零改动**，其既有降级语义（fallback 链/预算守卫，ADR-0008/0015）原样继承。

## 🧪 6. 测试要点（可测性预留）

- **版本生成器**：MINOR/MAJOR 两档；多版本取 max（v1.9 → v1.10 次版本、排序断言 1.10 > 1.9）；非法格式忽略 + WARN；空集 → v1.0。
- **校验器规则表**：V1 三态（缺 SYSTEM/缺 USER/顺序颠倒）、V2 大小写不敏感、V3 边界（空/65536+1）、V4 基准为 `baseVersionId` 底稿行（含缺省回落激活版、无激活版基准空集两分支）、V5 注册表差集（场景 2 eventTitle 落 unknown 且不拦截）；确认数组：部分确认仍拦（30068）、全确认放行、超集确认无害（多余键名忽略）；unknown 单独存在不拦且 201 回带 warnings。
- **不变量事务**：create 后旧版 RETIRED 新版 ACTIVE 且同时刻无中间态（同事务断言）；activate 回滚路径（v1.1→v1.0）唯一激活；activate 幂等（重复激活自身）；delete 激活版 30069、置废版物理删且他版不受影响；UNIQUE 冲突 30070 路径。
- **注册表同源**：三装配器 `build()` keySet == `provided()` keySet（防漂移闸门）；Registry 聚合 4 场景完整性（1/2 共 17、3 共 7、4 共 6）；briefType 过滤参数。
- **契约（MockMvc 既有模式）**：6 端点 happy path + 404/30066 + 400/30067（msg 含具体缺失项，故事 2 场景 3/4）+ 409/30068 data 结构（removed/unknown）+ 409/30069 + 409/30070；JWT 拒绝未认证。
- **即时生效集成**（对齐故事 2 场景 2）：改模板保存激活 → 手动触发生成 → 断言 LlmRequest 消息含新模板文本且未命中旧缓存（mock 网关捕获消息，LlmCache keyOf 变化断言）。
- **回归红线**：后端 902 基线全绿（重点 `PromptTemplateServiceTest` 守护等价重构）；前端 vitest 全绿 + navConfig 快照更新（运维组 6 项）。

## 🧾 决策留痕（ADR 摘要）

### ADR-0021 · 提示词版本号受控生成与排序：零 DDL + 服务端 bump 生成 + Java 数值排序

- 背景：version 为 TEXT，`ORDER BY version DESC` 字典序在 v1.9/v1.10 类场景错序；至今版本号全由 Flyway 迁移手写，无运行时通道。
- 决策：prompt_template 零 DDL（不加 created_by/备注列，PRD Won't + 最小改动）；版本号由服务端生成器受控产生（MINOR 默认 / MAJOR 归零，用户不可自由填写），UNIQUE 索引兜底冲突；真实版本序只由应用层数值排序表达，DB 字典序仅存于防御性兜底。
- 被否：双 INTEGER 列（迁移连带面大且无人需要 SQL 排序）/ 零填充字符串（存量回填 + 观感差 + 99 后仍要扩位）。
- 后果：详见 [adr/0021-提示词版本号受控生成与排序.md](/docs/02-设计/adr/0021-提示词版本号受控生成与排序.md)。

### ADR-0022 · 占位符注册表单一事实源：装配器自带描述符 + 注册表聚合 + 同源单测

- 背景：占位符清单分散在三个上下文装配器（17+7+6 键）；PRD 要求对照区与校验基准同源，注册表若为第二份硬编码清单必然漂移。
- 决策：每装配器新增 `providedPlaceholders()`（描述符与 `ctx.put` 同文件同序），`PromptPlaceholderRegistry` 聚合并同时供只读接口与校验器 V5 消费；同源单测断言 build() keySet == 描述符 keySet 作机械闸门；对生成链路纯增量。
- 被否：独立目录类硬编码第二份清单（漂移高风险）/ 运行时从 build() 推导（样本依赖不稳定）。
- 后果：详见 [adr/0022-占位符注册表单一事实源.md](/docs/02-设计/adr/0022-占位符注册表单一事实源.md)。
