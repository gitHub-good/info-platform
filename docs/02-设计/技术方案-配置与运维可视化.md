## 🎯 1. 背景与目标

### 背景（设计前代码核实结论）

v1（M1~M3）配置与运维侧现状，逐点核实如下：

| 现状 | 核实结果 | 热生效可行性 |
| --- | --- | --- |
| `LlmConfig`（@ConfigurationProperties `llm.*`） | 单例 bean 常驻；`providerByName()/fallbackChain()` 每次调用现读 | 链/单价已具备热读基础 |
| `LlmGatewayImpl` | `timeout` 在**构造器固化**（`this.timeout = config.timeout()`）；fallback 链/单价每次调用现读 | 超时需改运行时读取 |
| `LlmCostGuard` | 预算/告警阈值为构造器 **final 字段** | 需改为运行时读取 |
| `LlmCache` | TTL 分档函数活绑 `LlmConfig.Cache`（可热）；`defaultTtlSeconds/maximumSize` 建缓存时固化 | 分档 TTL 可热；容量重启生效 |
| 数据源 adapter | `adapter.mock.enabled` 以 `@ConditionalOnProperty` 启动期**互斥装配** mock/real 各 7 个；各源 `resilienceSpec()` 硬编码常量；client URL/条数构造期 `@Value` | 需无条件装配 + 运行时路由 |
| 定时任务（5 个） | `@Scheduled(fixedDelayString/cron)` 表达式启动期解析；3 个 `@EnableScheduling` 配置类 + Job bean 均 `@ConditionalOnProperty` 条件装配；留痕走 `JobExecutionAspect`（AOP 拦 `@Scheduled` 方法）→ `job_execution_log` | 需调度集中化改造 |
| `SourceCache` | 各源 TTL/容量硬编码 `specFor()` | 需按 LlmCache 模式热化 |
| `AggregationService` | 总超时构造期 `@Value` | 需改运行时读取 |
| API key | 仅环境变量注入（`LlmConfig.Provider.apiKey`），`AbstractOpenAiCompatProvider` 每次调用现读 | 已具备热读基础，缺页面录入通道 |

### 目标（对齐 PRD，可量化）

- 三域配置（LLM / 数据源 / 任务）前端可看可改，保存后持久化（重启不丢）。
- Must 级热生效参数（日预算/告警阈值/单价/缓存 TTL）保存后**对新请求立即生效**，不重启。
- 5 个平台任务可总览（调度状态/上次执行/下次执行）、可手动触发（防重入）、可启停与调间隔/cron（热切换，自下一周期生效）。
- 概览仪表盘一屏五卡片（成本水位/异动/政策/任务健康/数据源健康），口径明确（§4.6，PM 已授权架构裁定）。
- API key 明文永不回显、不留痕（ADR-0018）。

### 验收红线逐条对齐

| PRD 红线 | 方案落点 |
| --- | --- |
| 重启后配置不丢 | `runtime_config` 表持久化（§4.1），启动 DB 值优先于 yml |
| 历史成本留痕不随调价重算 | `llm_call_log.cost_micros` 调用时即落死值（ADR-0015 既有设计，报表只聚合存量列，天然满足）；调价新调用按新单价（§4.2） |
| API key 明文永不回显/不留痕 | 脱敏态回显 + AES-256-GCM 加密存储（ADR-0018，§4.7） |
| 防重入（同一任务单实例） | `JobExecutor` 每 job 一个运行守卫，冲突 409/30063（§4.5） |
| 重启生效项必须明示 | 契约带 `effective: "LIVE" | "RESTART"` 字段，UI 据此标示（baseUrl / 缓存容量） |
| 前后端双侧校验 | 后端表驱动校验器（§4.1 键空间表），错误码 2001 + 字段级原因 |

### 非目标（防范围蔓延）

- 不做配置变更审计与回滚、多用户权限（Won't，沿用 ADR-0002 裁剪 RBAC）。
- 不做新增/删除 provider 条目（仅编辑既有 4 条）。
- JWT/DB/端口等启动期基础设施不前端化；`llm_call_log` 清理任务等 M4 候选不在本期。
- 既有业务页视觉重做不做（仅导航收编，见 UI 方案 T44 清单）。

## 🗺️ 2. 方案总览

### C4 · Container 增补视角（新增/改造组件，8 元素；系统上下文不变，见主方案 §2）

```
┌────────────────────────────────────────────────────────────────┐
│ 浏览器 SPA（React19 + shadcn/ui，hash 路由）                    │
│  新增页: #/overview 概览  #/llm-config 模型配置                 │
│         #/datasource-config 数据源  #/task-center 任务中心      │
│         #/feed 信息流   + AppLayout 统一导航（UI 方案）         │
└───────────────────────┬────────────────────────────────────────┘
                        │ REST /api/v1/*（JWT，沿用主方案契约）
┌───────────────────────▼────────────────────────────────────────┐
│ 后端单体（DDD 四层不变，新增 common 域两个横切组件）            │
│  ① 配置中心 RuntimeConfigService + ConfigCenter                 │
│     内存快照(写时替换+Spring事件) ←→ SQLite runtime_config      │
│  ② 任务调度中心 JobRegistry + JobScheduler + JobExecutor        │
│     (TaskScheduler+Trigger, 5 Job 去 @Scheduled 收编注册)       │
│  消费点改造: LlmGateway/LlmCostGuard/LlmCache/SourceAdapter 路由 │
│             /各 client/AggregationService → 运行时读取          │
└───────────────────────┬────────────────────────────────────────┘
                        │ 既有外部依赖不变（6 数据源 + LLM 厂商）
```

核心思路（外行能懂）：给后端装一个"运行时配置中心"——配置从 yml 单向种子导入 SQLite 配置表，之后以数据库为权威；内存里放一份不可变快照供各处零开销读取，页面保存 = 校验 → 落库 → 换快照 → 发事件，消费方（网关/守卫/缓存/适配器）从"启动时拿一次值"改为"用时拿当前值"，于是保存即生效。任务侧把 5 个散落的 `@Scheduled` 收编到统一调度中心，注册/取消/改周期都由配置驱动，手动触发与定时调度走同一执行通道（天然防重入、同一张留痕表）。

## ⚖️ 3. 候选方案对比

### 3.1 热生效机制（spring-cloud @RefreshScope / 自建配置中心快照 / 每读查库）

| 维度(1-5,高优) | A @RefreshScope + /actuator/refresh | B 自建配置中心（快照+事件+用时读取） | C 每次读直查 SQLite |
| --- | --- | --- | --- |
| 成熟度 | 4 | 5（不可变快照+事件，常规手段） | 5 |
| 社区生态 | 4 | 5（零新依赖） | 5 |
| 学习成本 | 3（scope 代理/销毁时序） | 4 | 5 |
| 可替换性 | 3（绑定 spring-cloud 体系） | 5（纯 JDK/Spring 核心） | 4 |
| 运维成本 | 3（多一套 refresh 端点与依赖） | 5（无新组件） | 4（热路径加 DB 读） |

**选择：方案 B。** 理由：A 的 `@RefreshScope` 整 bean 重建会把 `LlmCache`（缓存全失效）、`LlmCostGuard`（当日计数清零）等**有状态 bean 的状态一起销毁**，与"调个预算不丢缓存"直接冲突，且为单人本地场景引入 spring-cloud-context 过重；C 在 LLM 每调用/聚合每请求的热路径加一次 SQLite 读与 JSON 反序列化，还要与业务写竞争单写者。B 只动"值的获取时机"，bean 结构与状态全保留。决策记 **ADR-0017**（含任务启停热切换裁定）。

### 3.2 配置存储模型（单表 key-value / 域分表 / 继续 yml+重启）

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 单表 `runtime_config`（域前缀键 + JSON 值 + 类型化访问器） | 一张表一套读写/种子/校验框架；新增配置键零 DDL；JSON 文档与域结构自然对齐 | 值结构约束靠应用层校验器（非 schema） | ✅ 采用 |
| B 三域分表（llm_config / source_config / job_config） | 列级类型约束 | 三套 DDL/POJO/校验；结构演进频繁动表 | ❌ 否决 |
| C 继续 yml + 重启 | 零改造 | 直接违背需求 Must（保存即生效、重启不丢） | ❌ 否决 |

### 3.3 API key 存储（仅环境变量只读 / DB 加密存储 / 明文 / 外部 secret 管理）

| 方案 | 满足"页面录入新 key" | 安全 | 成本 |
| --- | --- | --- | --- |
| A 仅环境变量 + 页面只读状态（PM 降级预案） | ❌（改 key 仍登服务器） | 高 | 零 |
| B DB AES-256-GCM 加密 + 脱敏回显 + DB优先/ENV回落 | ✅ | 高（防库文件/备份/日志泄露） | 低（JDK 内置，无新依赖） |
| C 明文落库 | ✅ | ❌ 违反红线 | 零 |
| D 系统 keychain / vault | ✅ | 高 | 跨平台运维过度 |

**选择：方案 B，CONFIG_SECRET 未配置时运行时降级为 A**（写接口返回 30064、页面只读态）。决策记 **ADR-0018**。

### 3.4 任务调度（保留 @Scheduled+入口开关 / 集中式 JobScheduler）

| 维度 | A 保留 @Scheduled，方法入口查运行时 enabled | B 集中式 JobScheduler（TaskScheduler + 配置驱动 Trigger） |
| --- | --- | --- |
| 启停热切换 | ✅（跳过执行） | ✅（取消/重注册） |
| 间隔/cron 热切换 | ❌（表达式启动期定死，只能重启） | ✅（重注册，自下一周期生效） |
| 手动触发 | 受条件装配限制：`recommendation.schedule.enabled=false` 时 Job bean 根本不存在，"立即执行每日推荐"无 bean 可调 | ✅ Job bean 无条件装配，调度与执行解耦 |
| 改造面 | 极小 | 5 Job 去 @Scheduled + 删 3 个 SchedulingConfig + AOP 退役（~1.5 人天） |

**选择：方案 B。** A 无法满足"手动触发全部 5 个任务"（每日推荐生产默认 `enabled=false`，bean 未装配）与"间隔热切换"。裁定：**任务启停/间隔/cron 热切换可行**，不启用 PM 预案"明示重启生效"；语义为**自下一调度周期生效**（进行中的一轮跑完，页面明示），见 ADR-0017。

## 🔧 4. 详细设计

### 4.1 运行时配置存储模型（V15 / U15）

```sql
-- T34 · 运行时配置表（配置中心权威存储：页面可改的运行时配置持久化，重启不丢）
-- 来源：REQ-20260922-02 故事 2 场景 6「重启不丢」+ ADR-0017（自建配置中心快照方案）。
-- 模型：单表 key-value；config_key 域前缀命名（llm./datasource./job./aggregation.），config_value 存 JSON 文档。
-- 写入方：RuntimeConfigService（校验通过 → upsert → 刷新内存快照 → 发 RuntimeConfigChangedEvent）。
-- 种子：启动 seed-if-absent 从 yml 导入（DB 已有该键则不动，DB 为权威；改过 yml 不再覆盖页面值）。
-- 读取方：ConfigCenter 启动全量载入不可变快照（volatile 引用整体替换），热路径零 DB 读。
-- 不设 version 列：单用户单写者无并发竞争；并发防呆用请求携带 expectedUpdatedAt 比对 updated_at（30065）。
CREATE TABLE runtime_config (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  config_key   TEXT    NOT NULL,                 -- 如 llm.global / llm.provider.deepseek / datasource.QUOTE / job.POLICY_FETCH
  config_value TEXT    NOT NULL,                 -- JSON 文档（结构由各域校验器约束，见键空间表）
  description  TEXT,                             -- 人读说明（种子导入时写入）
  created_at   TEXT    NOT NULL,                 -- ISO-8601 整秒（UTC），对齐既有表惯例
  updated_at   TEXT    NOT NULL,
  UNIQUE(config_key)
);

-- T42 · 概览仪表盘聚合窗口索引（既有表补索引，取数口径见 §4.6）
CREATE INDEX idx_anomaly_time   ON anomaly_event(trigger_time);
CREATE INDEX idx_policy_created ON policy_item(created_at);
CREATE INDEX idx_job_log_time   ON job_execution_log(created_at);
```

回滚脚本 `U15__drop_runtime_config.sql`：反向 `DROP INDEX IF EXISTS` 三条 + `DROP TABLE IF EXISTS runtime_config`（对齐 U1~U14 惯例）。

**键空间清单**（种子来源 = 首次启动从 yml/代码缺省导入的值）：

| config_key | 域 | JSON 主要字段（校验规则） | 生效级别 |
| --- | --- | --- | --- |
| `llm.global` | LLM | timeoutSeconds(正整数) / retry(0~3) / dailyTokenBudgetPerUser(>0) / budgetWarnRatio((0,1]) / cacheDefaultTtlSeconds(正整数) / cacheTtlSeconds{brief-type-N:正整数} | LIVE |
| `llm.provider.{name}`（既有 4 条） | LLM | model(非空) / enabled(bool) / isDefault(bool，全局恰一) / fallback(须为存在且 enabled 的 provider) / input·outputPricePerMillion(≥0) / baseUrl(URL，**RESTART**) / apiKeyCipher·apiKeyLast4(§4.7，只写) | LIVE（baseUrl 除外） |
| `datasource.{SOURCE_CODE}`（7 条） | 数据源 | enabled(bool) / mode(MOCK\|REAL) / timeoutMillis(正整数) / retries(0~3) / cacheTtlSeconds(正整数) / params{各源自由参数：URL(合法格式)/pageSize(正整数)/fields…} | LIVE |
| `job.{JOB_KEY}`（5 条） | 任务 | enabled(bool) / scheduleType(FIXED_DELAY\|CRON) / intervalMillis(正整数，FIXED_DELAY) / cron(合法表达式，CRON) / userIds(逗号分隔，仅 DAILY_RECOMMEND) | LIVE（间隔/cron 自下一周期） |
| `aggregation.global` | 聚合 | detailTimeoutMillis(500~10000) | LIVE |

| jobKey | jobName | scheduleType | 种子默认（来自现 yml） |
| --- | --- | --- | --- |
| POLICY_FETCH | PolicyFetchJob | FIXED_DELAY | interval=3600000，enabled=true |
| POLICY_TENDENCY | PolicyTendencyJob | FIXED_DELAY | interval=1800000，enabled=true |

### 4.2 热生效机制（配置中心）

**组件**（common 域，横切四层）：

- `RuntimeConfigService`（应用层）：读 `current()`（快照）；`write(key, json, expectedUpdatedAt)`（校验 → DB upsert → 换快照 → 发事件）。写失败（DB 异常）返回 50000，快照不动，旧值继续生效（降级预案）。
- `ConfigCenter`（基础设施层）：启动加载（`ApplicationReadyEvent` 后、端口服务前）+ seed-if-absent 导入；暴露类型化视图 `RuntimeConfigView`（`llmGlobal()` / `provider(name)`（含 key 解析 DB>ENV）/ `source(code)` / `job(key)` / `bootValue(key)`）。
- `RuntimeConfigChangedEvent`（Spring 事件）：JobScheduler、页面刷新等订阅；快照本身整体替换，消费方**用时读取即热**，不依赖事件（事件只用于需要"重绑"的场景：任务重注册）。

**生效级别分级**（对齐 PM 热生效分级拍板，页面按 `effective` 字段明示）：

| 参数 | 级别 | 语义 |
| --- | --- | --- |
| 日预算/告警阈值/单价/LLM 超时与重试/缓存 TTL 分档与默认 TTL | LIVE | 保存后**下一次调用/新缓存条目**生效；已用计数与历史留痕不变（调价只影响未来调用，见 §1 红线） |
| provider 启用/默认/fallback/模型名/API key | LIVE | 下一次调用生效（fallback 链/模型/key 每调用现读） |
| 数据源 enabled/mode/超时/重试/条数/URL/缓存 TTL、聚合总超时 | LIVE | 下一次聚合请求生效 |
| 任务 enabled/interval/cron/userIds | LIVE | 启停立即（取消/注册）；间隔与 cron **自下一调度周期生效**（进行中一轮跑完） |
| provider baseUrl、LLM 缓存 maximumSize | RESTART | 保存持久化，页面明示"重启后生效"；消费点读**启动期冻结快照**（`bootValue`） |
| JWT/DB/端口 | 不可编辑 | 仍走环境变量/yml（Won't） |

**与启动期条件装配的两处冲突及解法**（ADR-0017 核心）：

1. **mock/real 互斥装配 → 无条件装配 + 运行时路由**：14 个 adapter（真实 7 + mock 7）去掉 `@ConditionalOnProperty` 全部装配为内部 bean；每源新增一个 `RoutingSourceAdapter` 作为该源唯一对外 `SourceAdapter`，`fetch` 时按 `datasource.{CODE}.mode` 路由，`enabled=false` 直接返回 MISSING（分区"暂无数据"，不阻断）。`AggregationService` 注入 `List<SourceAdapter>` 的既有代码零改动。yml `adapter.mock.enabled` 降级为**种子默认值**（true→各源初始 mode=MOCK），测试 profile 继续用它控制初始模式。
2. **@Scheduled 启动期定死 → 集中式调度**：见 §4.5。

### 4.3 消费点改造清单（文件级，给开发）

### 4.5 任务注册表与手动触发

**组件**（common 域新增 `jobrun`）：

- `ManagedJob`（应用层接口）：`jobKey()` / `displayName()` / `description()` / `scheduleType()` / `run()`——5 个 Job 实现并注册为无条件 bean（逻辑不动，只摘 `@Scheduled`/条件注解）。
- `JobRegistry`（应用层）：收集 `List<ManagedJob>` + 运行时配置 + `job_execution_log` 最近执行 → 任务总览视图（§4.4.3）；`running` 态来自 JobExecutor。
- `JobScheduler`（基础设施层）：自有 `ThreadPoolTaskScheduler`；按 `job.{KEY}` 注册（FIXED_DELAY 用 `scheduleWithFixedDelay`，CRON 用 `CronTrigger`）；订阅 `RuntimeConfigChangedEvent` → 取消旧 future 重注册（热切换，**下一周期生效**：进行中一轮跑完）；`nextExecutionTime` 从调度器/触发器推算。
- `JobExecutor`（基础设施层）：每 jobKey 一个 CAS 运行守卫（`AtomicBoolean`）——定时触发与手动触发**共用**，运行中一律拒绝（手动→409/30063，定时→跳过本轮记 DEBUG）；执行前后显式调 `JobExecutionRecorder.start/success/failed`（替代退役的 AOP，留痕语义与字段完全一致）；手动触发异步提交（虚拟线程执行器）即返 202。

**防重入与 SQLite 单写者**：守卫保证同任务不并发；跨任务并发维持现状（`@Scheduled` 时代即并行，SQLite 靠 WAL + busy_timeout=5000 排队，个人量级无锁风险）。手动触发执行链路与定时完全一致（同一 `run()` + 同一留痕表），故"触发→效果→日志"三处闭环（故事 4 场景 2/3）。

### 4.6 概览仪表盘取数口径（裁定，PM 待澄清项 1）

时间口径：存储为 UTC ISO-8601 文本（字典序即时间序）；「今日」= 系统时区当日 00:00 起（对齐用户直觉与 `LlmCostReportService` 日界）；「近 24h」= 滚动窗口。

| 卡片 | 指标定义 | 数据来源 | 窗口 |
| --- | --- | --- | --- |
| 今日 LLM 成本水位 | tokenUsed=SUCCESS 行 token 合计；costMicros=cost_micros 合计；budgetTokens=**运行时当前预算**；status 三态 OK/WARNING/EXHAUSTED（阈值同成本报表，同源 `LlmCostBudget` 端口） | 复用 `GET /llm-cost-report?window=today` 聚合（`LlmCostReportService`） | 今日 00:00 起 |
| 今日异动条数 | `anomaly_event.trigger_time` 落今日行数 | `anomaly_event`（V15 补 `idx_anomaly_time`） | 今日 00:00 起 |
| 政策动态 | 入库时间近 24h 行数 + 最新 5 条（id/title/publishedAt） | `policy_item.created_at`（V15 补索引）——**裁定用入库时间而非 published_at**：gov 页仅挂最近条目，published_at 可回填历史导致计数失真 | 滚动 24h |
| 任务健康 | windowRuns/windowFailed=近 24h 执行总数/FAILED 数；unhealthyJobs=失败>0 或最近一次执行 FAILED 的 jobKey | `job_execution_log.start_time`（V15 补 `idx_job_log_time`） | 滚动 24h |
| 数据源健康 | 每源最近一条事件（含 OK 心跳）类型/时间 + errors24h（type∈1~4 计数） | `data_source_event`（既有 `idx_dse_source_time` 可用） | 滚动 24h |

> 政策卡与异动卡窗口不同（滚动 24h vs 今日日界）为**有意裁定**：政策"最近 24h"对齐 PRD 文案与抓取节奏，异动/成本"今日"对齐用户当日直觉；前端卡片副标题标注窗口。空态：各计数为 0、latest 为空数组，不报错（故事 5 场景 2）。

### 4.7 API key 安全设计（ADR-0018 摘要）

- **存储**：`llm.provider.{name}` 键内存 `apiKeyCipher` = base64(randomIV ‖ AES-256-GCM 密文) + `apiKeyLast4`（明文，展示用）；主密钥 = 环境变量 `CONFIG_SECRET`（≥32 字节，缺失不阻断启动，仅禁写）。
- **解析顺序**：DB（该 provider 已写入）> 环境变量（`LlmConfig` yml 绑定值）> 空串（inert）。env 仍为一等来源，部署脚本零改动。
- **回显**：接口只返回 `status/source/last4`；明文仅在请求体与内存瞬时存在，不落日志（`LlmCallLogger`/日志框架无 key 字段维持，写路径统一脱敏工具拦截）。
- **降级**：`CONFIG_SECRET` 未配置 → 写接口 30064（503），页面显示只读态"key 走环境变量"（PM 接受的降级实现）。

## 🛡️ 5. 非功能设计（逐项过）

- **性能**：配置读 = 内存快照（纳秒级，热路径零增负）；配置写 = 单行 upsert；概览聚合走 §4.6 三条新索引 + 既有索引，目标 P95 < 500ms（个人量级窗口行数有限）；连通性测试受 LLM 超时约束（默认 30s，前端请求超时 35s）。
- **容量**：`runtime_config` ≈ 13 行（1 全局 + 4 provider + 7 源 + 5 任务 + 1 聚合）；OK 心跳节流后 ≤ ~1.4k 行/日/源上限（实际 ~百级）；`job_execution_log` 既有增速（异动 10s 轮询 ≈ 8.6k 行/日）**M4 不动**，风险与建议见 §7。
- **安全**：新接口全部受 JWT（不入白名单）；key 加密存储 + 脱敏回显（§4.7）；任务触发/配置变更记 INFO 审计日志（键级，不含敏感值）。
- **可观测**：配置变更发 `RuntimeConfigChangedEvent` + INFO 日志（old→new 值，key 相关键只记"已变更"不记值）；手动触发记 INFO（jobKey/executionId）；连通性测试落 `llm_call_log`（scene_key=test，成本可见）。
- **降级预案**：配置写 DB 失败 → 50000，快照不换、旧值继续生效；ConfigCenter 启动加载失败 → fail-fast（配置权威不可用属启动故障）；`CONFIG_SECRET` 缺失 → key 只读降级；调度中心注册失败（cron 非法已在校验拦截）→ 拒绝保存，原调度不动。

## 🧾 决策留痕（ADR 摘要）

### ADR-0017 · 运行时配置热生效机制：自建配置中心快照 + 消费点用时读取 + 调度集中化

- 背景：配置全静态绑定（@ConfigurationProperties/@Value/条件装配），PM 分级要求预算/阈值/单价/TTL 保存即生效（Must），任务启停/间隔热切换为 Should（允许降级明示重启生效）。
- 决策：SQLite `runtime_config` 权威 + 内存不可变快照（写时整体替换 + Spring 事件）+ 消费点从构造期取值改为用时取值；mock/real 互斥装配改无条件装配 + `RoutingSourceAdapter` 运行时路由；5 Job 去 `@Scheduled` 收编集中式 JobScheduler。**任务启停/间隔/cron 热切换裁定可行**（自下一周期生效，页面明示），不启用 PM 降级预案。
- 被否：spring-cloud `@RefreshScope`（有状态 bean 重建丢缓存/计数 + 依赖过重）/ 每读直查 DB（热路径增负）。
- 后果：详见 [adr/0017-运行时配置热生效机制.md](/docs/02-设计/adr/0017-运行时配置热生效机制.md)。

### ADR-0018 · API key 存储：DB AES-256-GCM 加密 + 脱敏回显 + DB 优先/环境变量回落

- 背景：PM 红线明文永不回显、不留痕；故事 2 场景 4 要求页面可录入新 key。
- 决策：`CONFIG_SECRET` 环境变量为主密钥，密文与尾 4 位存 `runtime_config`；解析顺序 DB>ENV>空；缺 `CONFIG_SECRET` 时写接口 30064、页面降级只读（PM 接受的降级实现）。
- 被否：仅环境变量只读（无法页面录入，PM 降级预案保留为运行时降级态）/ 明文落库（违红线）/ 外部 secret 管理（单人本地过度）。
- 后果：详见 [adr/0018-api-key存储安全方案.md](/docs/02-设计/adr/0018-api-key存储安全方案.md)。
