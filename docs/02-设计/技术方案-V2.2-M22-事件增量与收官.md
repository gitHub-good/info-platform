### 1.2 目标（对齐 REQ 六拍板）

1. **增量重评链路**：HIGH 事件入库 → 受影响标的集（subjects ∪ IndustryAssociator 投影，与 F2 同源）→ 当日快照行局部重算（同纯函数同 weight_basis 零漂移）→ 留痕，端到端 P50 ≤15min / P90 ≤30min。
2. **榜单联动**：分数差阈值（缺省 0.5 可配）挤入挤出判定 → 同日 version+1（trigger_source=EVENT）+ 变动归因到触发事件 id + 新入榜必要补深析（FACTOR_ONLY 兜底）；联动最小间隔 10min 可配。
3. **兜底互斥自愈**：17:30/18:00 双 Job 零重构；增量异常不阻塞全量、全量自然修复；互斥显式化。
4. **时间戳双层语义**：value-score 端点增 increment updatedAt；页头双时间戳。
5. **命中统计 v1（Should）**：T+1/T+5/T+20 上涨家数占比 + 中位数涨跌幅，惰性回算 + 对账 + 免责。
6. **V2.2 收口支撑**：时效 P50/P90 可由留痕 SQL 直出（北极星首测数据前提）。

```
event_item(HIGH 未消费) ──► [INCREMENTAL_REEVAL_JOB 第18 Job, FIXED_DELAY 60s]

                                    │ UNIQUE UPSERT 当日行 + increment_at 留痕列
                                    ▼
        subject_factor_snapshot(当日行覆盖) ──► [SqueezeJudge 挤入挤出判定（domain 纯函数）]
                                    │ 分数差阈值超限 ≥1 变动                │ 未超阈
                                    ▼                                     ▼
        [IncrementalTopService 联动：version+1(EVENT) + RankDiffer 同日 diff    NO_LINK 终态
         + 新入榜补深析(护栏内/FACTOR_ONLY 兜底) + trigger_events 归因]
                                    │
                                    ▼
        market_top_rank/batch + incremental_reeval_log ──► [ValueScore/MarketTop 查询端点（双层时间戳）]
                                              └──► [HitStatsService 惰性回算（读侧零新表）]
```

一段话核心思路：**第 18 个 FIXED_DELAY 60s 短轮询 Job 扫「未消费的 HIGH 事件」（RECOMMENDATION_FEED 同款扫描模式），按事件并集算受影响标的集，走 FactorSnapshotService 既有单标的计算路径覆盖当日快照行（零第二套口径、天然零漂移），纯函数 SqueezeJudge 按分数差阈值判挤入挤出，超阈才以 version+1（EVENT）联动榜单并只对新入榜标的补一次深析；全量 Job 运行时增量让路、版本号唯一冲突重试兜底，17:30/18:00 双 Job 一行不改。**

## ⚖️ 3. 形态决策（ADR-0061 三主裁决 + 次级裁量）

### 3.1 裁决一 · 触发消费 = 独立 Job INCREMENTAL_REEVAL 60s 短轮询（否决挂 RECOMMENDATION_FEED 同轮 / 后置钩子 / 事件订阅）

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| a) 独立 ManagedJob FIXED_DELAY 60s 扫 HIGH 未消费事件 | 与推荐消费**完全解耦**（停推荐不动增量、反之亦然）；重启免疫（扫描无内存态，消费进度全在留痕表）；复用 M16 已验证的「LEFT JOIN 判重 + 落库缓冲 + 补跑窗」扫描模式；可独立热改间隔/停启 | 多一个常驻 Job（调度池 15→16） | ✅ 采用 |
| b) 挂 RECOMMENDATION_FEED 同轮 | 零新 Job | 耦合两条语义无关链路：推荐停用/改间隔连带影响增量时效红线；推荐 tick 用户级段异常的容错语义不适用；消费判重口径不同（卡片表 vs 留痕表）互相污染 | ❌ 否决——时效红线链路不搭便车 |
| c) 事件落库后置钩子（L2 写路径内联触发） | 时延最低 | 写路径同步耦合重计算（评分/榜单联动秒~分钟级会拖慢 L2 落库）；L2 批量管道无单事件边界；触发丢失无补救 | ❌ 否决 |
| d) 事件流订阅/Spring 事件 | 架构「标准」 | 进程内事件重启即丢（触发丢失=红线失守，仍需落表扫描兜底）；单体无跨进程诉求，订阅是伪需求 | ❌ 否决（REQ 蓝图「不新建通道」既定） |

**理由（五维度）**：成熟度——M16 RECOMMENDATION_FEED 同模式已运行两迭代（60s tick 判重消费）；运维成本——任务中心可视/热改/手动补触发全套继承；可替换性——消费入口是 tick() 单方法，未来换长轮询/订阅零牵连；学习成本零新概念；风险面——独立 Job 把增量故障爆炸半径与推荐隔离（故事 3 场景 2 自愈语义更干净）。**合并去抖窗口 = tick 间隔本身**：60s tick + 20s 落库缓冲（缓冲内事件留待下轮）→ 同窗多事件按标的并集一轮重算（每标的每 tick 恰一次），相邻 tick 到达的同标的事件相隔 ≥60s 重算两次——重算幂等且 <1s，无需时间轮。多事件合并后时效 = 感知 P50 3.22min + 均值等待 30s + 缓冲 20s + 重算 <2s + 联动 <20s ≈ **P50 ≈ 4min / P90 ≈ 6min**，红线 15/30min 余量 2.5 倍+。

### 3.2 裁决二 · 增量重算与留痕 = 提取 FactorSnapshotService 单标的重算方法 + `increment_at` 留痕列 + 事件粒度留痕表

**重算路径（最小改动裁量）**：不复制计算逻辑，在 `FactorSnapshotService` 提取公开方法 `recomputeIncremental(LocalDate date, Collection<Long> subjectIds)`——阶段 1 投影**与 snapshotAll 完全同源**（同一 W2 窗事件/回联/热度/成员投影查询、同一 marketMap 截面），仅阶段 2 循环裁剪到目标标的、阶段 3 一次批 UPSERT。`rowOf()` 从 private 提为包内可见共用。**零漂移由构造保证**：同一投影查询 + 同一纯函数 + `settings.params()` 热读同一权重版本——验收场景 3（增量覆盖后重跑全量零漂移）在代码路径上不存在分叉点。

- 覆盖行差异仅两处：`increment_at` 置为本轮时刻（全量路径显式置 NULL）；`computed_at` 语义不变（本行计算时刻）。
- 回填触发点（拍板四-3）：**维持 MARKET_TOP_JOB 阶段 0 现状不加钩子**——增量只消费「已落库事件」，subject 回联 T+1 生效语义不变；增量重算的 subjects 投影读的是事件落库时的既有 subjects 快照 + 当下行业成员表，**不等待、不依赖当日未完成回填**（需求锁语义满足）。

**留痕形态（ALTER 列 vs detail JSON 裁量）**：`factor_detail` 是 §4.5 五维明细契约，塞审计信息污染下游解析（榜单 topEventsOf/evidenceCountOf 直读该 JSON）——**否决 detail JSON**；ALTER 加 `increment_at` 一列（V33），全量 UPSERT 置 NULL 自然复位，查询层直用。事件粒度留痕表 `incremental_reeval_log`（V33）：一行一事件（UNIQUE(event_id) 判重键 + 审计真相源），`subjects_json` 携带 [{id, code, before, after}] 前后分——验收要求的「触发事件/标的集/前后分/联动版本号」四要素一表全覆盖，北极星时效 SQL 直出（§4.4.4）。

### 3.3 裁决三 · 榜单联动 = 判定集「当日 Top10 ∪ 受影响标的」纯函数挤入挤出 + 重 Job 让路互斥 + 版本唯一冲突重试（三层，从简）

**联动形态**：**不走 MarketTopService.generate() 全四阶段**（粗筛 40 只深析 = 成本放量，违反护栏语义），新建 `IncrementalTopService.link()`：

1. 判定集 = 当日最新版本 Top10 ∪ 受影响标的（含粗筛排除规则复检：ST/无信号标的不入判定集）；**静态近榜候选（第 11 名起）不参与**——其相对序未变，留给 18:00 全量修正，边界如实留痕（增量判定是「快照式局部正确」，非全序重算）。
2. `SqueezeJudge.judge()`（domain 纯函数，新文件）：按 final 分对判定集排序，**换入换出同一迟滞阈值 `minScoreGap`**（缺省 0.5，0~10 可配）——entrant.final > exit.final + gap 才换位（挤出同理，双向同阈）；排序后成员不变或变动未过阈 → NO_LINK（防抖红线：无有效变化不重排）。final 口径沿用 M21 `final = max(total, 0.8×total + 0.2×dive)`，未深析标的 final = total。
3. 过阈变动 ≥1 → 同日 version+1 追加：不变成员**深析成果直继承**（dive_detail/dive_method/generation 沿用前版本行，零重析）；仅「新入榜且当日无 FULL 深析」标的补一次深析（护栏 scene-10 内，失败/触顶 FACTOR_ONLY 兜底——M21 降级语义沿用）。
4. RankDiffer 扩展：EVENT 版本 diff 基准 = **同日前一版本**（无则回落既有昨日口径）；归因 = batch 级 `trigger_source='EVENT'` + `trigger_events` JSON（V33 ALTER 列，事件 id+摘要）——该版本全部 NEW/UP/DOWN/dropped 归因到触发事件（故事 2 场景 4 版本级归因口径）。
5. **联动防抖**：距上一 EVENT 版本 `linkMinIntervalMinutes`（缺省 10min，0~60 可配）内 → 本轮置 DEFERRED 状态，留痕表挂起，下轮 tick 自动重试（事件标的分已在详情页可见，仅榜单延后——最坏 +10min 仍在 P90 红线内）。

**互斥三层（评估结论：不建显式锁表，三层从简）**：

| 层 | 机制 | 覆盖的冲突 |
| --- | --- | --- |
| ① WAL + busy_timeout=5000（既有） | SQLite 单写者排队 | 秒级以下事务交错（快照 UPSERT 批、rank 落库批） |
| ② 重 Job 让路（新，薄） | tick 入口查 `isRunning("FACTOR_SNAPSHOT") ‖ isRunning("MARKET_TOP_JOB")` → 本轮整体 DEFERRED，事件留待下轮（60s 后） | 17:30/18:00 窗口（<2min / 4~12min）的输入投影读到半量行情、maxVersion 读旧值竞态 |
| ③ 版本唯一冲突重试（新，薄） | `MarketTopRepositoryImpl.insertVersion` 捕获唯一冲突 → version 重取 +1 重试一次（DAILY/EVENT 两路径共用） | ②的反向缝隙（增量联动进行中 DAILY 起跑——联动 ≤20s，概率极低但 DAILY 失败不可接受） |

实现接线：应用层新增 `RunningJobIndicator` 接口（`boolean isRunning(String jobKey)`），`JobExecutor` 实现之（基础设施实现应用接口，仓储同款依赖倒置）——**M20/M21 两个 Job 类零改动**。反向（MARKET_TOP_JOB 起跑时增量在飞）由 ③ 兜底：增量联动最多 1 次补深析 5~15s + 落库 <1s，18:00 CRON 与其交叠概率低，冲突即重试，语义闭环。

### 3.4 裁决四 · 命中统计 = 惰性回算零新表（否决回算 Job + market_top_hit_stats 物化表）

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| a) 惰性计算（查询服务现算） | 零新表零新 Job；**读时永远新鲜**（无物化过期）；数据量微（榜单日 +1/日、每日 10 行 × 3 窗 join，180 天留痕上限 ~180×30 行毫秒级） | 重复计算（个人量级无感） | ✅ 采用 |
| b) 回算 Job 物化 market_top_hit_stats 表 | 读侧零计算 | 新 Job + 新表 + 物化一致性问题（每日新窗滚动开窗、T+20 迟到补算）——为不存在的读压力付双重复杂度 | ❌ 否决 |

**口径（hits-v1，留档于 basis 串）**：榜单日取当日最大 version（EVENT 版本计入——日终语义 = 最后立场）；交易日序列 = market_daily_snapshot 去重 snapshot_date 升序（库内交易日历代理）；窗口目标日 = 榜单日后第 1/5/20 个交易日；涨跌幅 = (目标日 close − 榜单日 close) / 榜单日 close ×100；**有价样本** = 两端 close 均非 NULL 的标的（停牌/无价剔除，计数标注不隐藏）；窗口目标日未到来 → 该窗 `INSUFFICIENT`（首跑校准条款）。**T+20 首测如实**：价格快照 09-26 起、榜单留痕 09-27 起——首测时 T+1 仅 0~1 日样本、T+5/T+20 全部 INSUFFICIENT，呈现「样本不足」不硬凑（§1.1 核实结论）。

### 4.3 核心流程

#### 4.3.1 增量 tick 状态机（IncrementalReevalService.tick() 伪码）

```
tick():
  if isRunning(FACTOR_SNAPSHOT) or isRunning(MARKET_TOP_JOB):     # 互斥层②让路
      return detail("defer=heavy_running")                        # 事件不动，下轮重扫
  events = scan(HIGH, created_at ∈ [now-24h, now-20s], LEFT JOIN log 判重, cap 200)
  if events.isEmpty() and noPendingLink(): return detail(idle)    # 空转防抖：零重算零版本
  for e in events: insert log(e, status=SCANNED)                  # UNIQUE(event_id) 幂等
  affected = ⋃ (e.subjects 池内代码标的) ∪ IndustryAssociator 投影(e.affected_industries)
             # 投影与 F2 同源：同一 associate() 输入的成员边（同源复用，非第二套关联）
  before = 读当日快照行(affected)                                   # 前分留痕
  rows = factorSnapshotService.recomputeIncremental(today, affected) # §3.2 路径
  judge = SqueezeJudge.judge(当日最新版本Top10, rows, minScoreGap)    # domain 纯函数
  update log(events, subjects_json=before/after, snapshot_at, judge_passed)
  if !judge.passed: mark(NO_LINK); return                          # 防抖红线：不过阈不重排
  if now - lastEventVersionAt() < linkMinIntervalMinutes: mark(DEFERRED); return  # 联动防抖
  version = incrementalTopService.link(today, judge, events)       # §3.3 联动（含补深析/冲突重试）
  update log(events, LINKED, top_version, top_version_at)          # 终态
# 任何段异常：该轮事件标 FAILED(error) 不上抛（ManagedJob 惯例）；次日 17:30 全量自然修复（自愈）
# noPendingLink(): 留痕表存在 judge_passed=1 且 status ∈ {RECOMPUTED, DEFERRED} 的挂起轮 → 重走联动段
```

状态机：`SCANNED → RECOMPUTED → {NO_LINK | DEFERRED → LINKED | LINKED}`，FAILED 旁路；终态 LINKED/NO_LINK/FAILED。

#### 4.3.2 挤入挤出判定（SqueezeJudge，domain 纯函数）

```
judge(top10: List<RankRow>, affected: List<PoolRow>, gap):        # 判定集 = top10 ∪ affected
  candidates = (top10 ∪ affected 粗筛排除复检通过者) 按 final 分降序
  newTop10 = candidates.first(10)
  swaps = [ (entrant, exit) | entrant ∈ newTop10−top10, exit ∈ top10−newTop10,
            entrant.final > exit.final + gap ]                     # 迟滞双向同阈（挤出对称成立）
  return (swaps.isNotEmpty, newTop10, swaps)                       # 空或未过阈 → NO_LINK
```

确定性：纯内存列表排序，无时钟无随机——同输入同判定（可单测穷举边界：恰差 gap、并列、>1 换位、affected 全在榜名次不变）。

#### 4.3.3 端到端时序（预算分解）

| 段 | 预算 | 说明 |
| --- | --- | --- |
| 事件感知（源→L2 落库） | P50 3.22min | ns-v1 实测（需求给定） |
| tick 等待 + 落库缓冲 | ~50s（均值 30s+20s） | FIXED_DELAY 60s |
| 重算（投影 + N 标的 + UPSERT） | <2s | 投影与全量同源秒级；数百行内存计算（M21 先例） |
| 阈值判定 | <10ms | 纯函数 |
| 联动（version 落库 + ≤2 只补深析） | <20s | 深析 5~15s/只（0~2 只典型） |
| **合计** | **P50 ≈ 4min / P90 ≈ 6min** | 红线 15/30min；最坏叠加联动间隔 10min ≈ 16min 仍 <30min；17:30/18:00 让路窗（<2min/4~12min）内到达的事件顺延，晚间时段如实计入 P90 统计 |

### 4.4 关键技术点

**① 零漂移构造性保证（验收场景 2/3）**：受影响集内 = 同投影同纯函数同 weight_basis（重算路径唯一）；集外 = 不触碰（只 UPSERT affected 行）——「其余标的当日快照逐字节不变」由写入范围保证，md5 对账用例作运行时验证。成员投影变化（回填）**不进增量触发面**：增量触发只有「新 HIGH 事件」一个入口，回填按日界随 17:30 全量生效（拍板一防抖条款/OBS-M21-04）。

**② 事务边界**：重算 UPSERT 一批一事务（≤500 行既有惯例）；联动落库两表一事务（insertVersion 既有）；留痕表更新独立小事务（失败只丢审计不丢业务——业务状态以快照/榜单表为准，log 可由对账修复）。

**③ 自愈对账**：增量期任何偏差（FAILED/DEFERRED 遗留）由 17:30 快照（全量覆盖含 increment_at=NULL 复位）+ 18:00 榜单（version+1 DAILY）自然修复；偏差可对账 = 同日版本链 + log 状态机反查（故事 3 场景 2 验收 SQL：`SELECT * FROM incremental_reeval_log WHERE status='FAILED' AND event_created_at >= date(now)`）。

**④ 北极星增量时效 SQL（T194 直用）**：

```sql

SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY
         (julianday(l.top_version_at) - julianday(l.event_created_at)) * 86400) AS p50_seconds,
       percentile_cont(0.9) WITHIN GROUP (ORDER BY
         (julianday(l.top_version_at) - julianday(l.event_created_at)) * 86400) AS p90_seconds,
       COUNT(*) AS linked_events
FROM incremental_reeval_log l WHERE l.status = 'LINKED'
  AND l.top_version_at >= :window_start;   -- SQLite 无内建 percentile_cont → 应用层排序列插值（测试断言同式）
```

## 🛡️ 5. 非功能设计（逐项过）

- **性能**：tick 全程 <25s（含深析）；重算 <2s；hit-stats 现算 <100ms（180 天上限数据量）；无新 QPS 面（个人量级）。
- **容量**：HIGH 事件日增个位数 × 行业投影数十~数百标的 → 日增量写 ≤ 数千行；incremental_reeval_log ≤ ~10 行/日；180 天留痕（RetentionWindows 增表，沿 M10 治理）；存储增量 <10MB/年。
- **安全**：沿既有 JWT 体系零新面；统计面免责常驻（hits-v1 basis + 前端文案）；无敏感数据新增。
- **可观测**：JobRunStats detail 段式留痕（`incr=scan:n;recompute:rows:x;judge=pass:y/n;link=v;z;defer=heavy|interval`）；incremental_reeval_log 审计真相源；北极星 SQL（§4.4-④）；异常留痕可查（FAILED + error_message）。
- **降级预案**：LLM 补深析失败 → FACTOR_ONLY 入榜页面明示（M21 语义）；重算失败 → FAILED 留痕 + 次日全量修复；触发丢失 → 24h 补跑窗 + 全量兜底 + T194 首测观察项；heavy Job 运行 → 让路 DEFERRED。
- **成本护栏**：补深析仅「新入榜且当日无 FULL 深析」（每日增量联动 ≤ 数次 × 1 只）计入 scene-10 既有 30% cap；无预算新增机制。
