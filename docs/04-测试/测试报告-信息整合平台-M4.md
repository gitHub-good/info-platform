## 4. 缺陷清单（定级与复现）

### DEFECT-1【P1】SourceCache / LlmCache 条目被读取后永不过期——Caffeine Expiry 语义误用

> **状态：已关闭（2026-09-23，复审验证通过——修复 `37eca48` + 红态复验 + C2/G3 E2E 复测反转，证据见 §7.2）**

- **现象**：数据源 mode 热切换在「缓存已有 OK 条目且曾被读取」的稳态下不生效；缓存 TTL（含页面热改）对存量条目无效。
- **根因**：`SourceCache.java`（SourceExpiry）与 `LlmCache.java`（LlmExpiry）的 `expireAfterRead` 均返回 `Long.MIN_VALUE`，注释假设「= 不变」。**Caffeine 3.1.8 实测语义并非不变，而是使条目永不过期**（离线探针：put + 5s TTL + 读一次 → 40s 后仍命中；对照组 `expireAfterRead` 返回 `currentDuration` 则 5s 正常过期）。
- **复现步骤**（模式 1，沙箱 mock）：
  1. `GET /api/v1/subjects/1/detail?sections=quote` 两次（第二次命中缓存，即完成「读」）；
  2. `PATCH /api/v1/datasource-configs/QUOTE {"mode":"REAL"}`（响应/GET/DB 三处确认 mode=REAL）；
  3. 等待 >TTL（12~15s）后再次 detail → **仍返回 mock 旧数据（1680.5/123456/9876543210）**，sourceStatus=ok；
  4. 旁证：期间无新 OK 心跳、无 ERROR/TIMEOUT 事件（未发生真实取数）；重启后同操作立即正确（REAL→MISSING、MOCK→mock）。
- **影响**：① PRD 场景 3.2「切 mock 即生效」在稳态不生效（需重启），Should 级验收场景不通过；② 真实模式行情 5s TTL 失效 → 行情冻结 → **异动检测/推送链路（M1 核心故事）静默退化**；③ LlmCache 同族：AI 简报 1h / 每日推荐 24h TTL 失效，简报永不过期；④ 缓存 TTL 热改对存量条目无意义。
- **为什么自动化没拦住**：`SourceCacheTest`/`LlmCacheTest` 仅覆盖 put/get/分区/供应器语义，**无任何基于时间的过期用例**（未注入 Caffeine Ticker）。
- **修复要求**：`expireAfterRead` 返回 `currentDuration`（对照组已验证）或等价语义；**必须附带能复现本缺陷的失败用例**（Ticker 假时钟：写→读→推进 TTL→断言 miss），SourceCache 与 LlmCache 各至少一条；修后全量回归 + 本报告 C2/G3 用例复测。
- **定级依据**：核心功能异常（热生效红线场景 + M1 异动链路退化 + 简报新鲜度），有绕行方案（重启可短期恢复）→ P1，24h 内修复。

### DEFECT-2【P3】Feed 游标分页非法 cursor 返回 500

> **状态：已关闭（2026-09-23，复审验证通过——修复 `99ae12d` + F3 真实服务复测 400/2001，证据见 §7.2）**

- **复现**：`GET /api/v1/feed/personal?cursor=zzz` → HTTP 500 `{code:50000,msg:服务异常}`。
- **期望**：参数类型不匹配应 400/2001（与三域配置校验口径一致）。前端哨兵游标逻辑不会发出坏 cursor，实际触发面低。
- **定位**：`FeedController.personal` 的 `@RequestParam Long cursor` 类型转换异常被全局兜底捕获为 50000。建议在 GlobalExceptionHandler 增加类型不匹配映射。本迭代内修复。

### DEFECT-3【P3】provider fallback 校验不完整——可指向已禁用 provider，静默失去 fallback 保护

> **状态：已关闭（2026-09-23，复审验证通过——修复 `738f215` + B 组真实服务补测双向拒绝 + qwen 启停往返，证据见 §7.2）**

- **复现 a**：`PUT /api/v1/llm-config/providers/deepseek {"fallback":"kimi"}`（kimi enabled=false）→ 200 接受；技术方案 §4.1 键空间表要求「fallback 须为存在且 **enabled** 的 provider」。
- **复现 b**：`PUT .../providers/deepseek {"enabled":false}`（glm/qwen/kimi 均引用 deepseek 作 fallback）→ 200 接受，无交叉校验或告警。
- **影响**：运行时 fallback 链跳过禁用 provider（`LlmGatewayImpl` 已按 enabled 过滤，无报错），用户以为有灾备实际没有。建议：写入时校验拒绝，或禁用被引用 provider 时返回告警信息。本迭代内修复。
